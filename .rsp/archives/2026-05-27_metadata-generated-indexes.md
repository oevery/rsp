# Change: metadata-generated-indexes

## Proposal
- Summary: Use lightweight frontmatter metadata for generated INDEX.md files
- Why:
  - Generated `INDEX.md` files currently rely on a human-readable footer signature to identify generated content.
  - Page-level metadata makes generated indexes easier for agents, tools, and future CLI checks to classify without scanning prose.
- Scope:
  - Add lightweight YAML frontmatter to generated `.rsp/specs/INDEX.md` and `.rsp/archives/INDEX.md`.
  - Use that metadata as the generated-index signal in diagnostics instead of the `_Auto-generated by `rsp update`._` footer.
  - Remove the generated footer from regenerated index bodies after metadata is present.
- Non-goals:
  - Do not introduce a broad index schema, tags, filters, or sorting configuration.
  - Do not require additional metadata on normal spec, rule, change, or archive files.
  - Do not change the RSP lifecycle model or archive readiness rules.

## Spec
### ADDED
- Requirement: generated index metadata
  - Generated `INDEX.md` files include YAML frontmatter that identifies the page as a generated RSP index.
  - The metadata includes only lightweight fields needed for classification and basic display: `title`, `summary`, `kind`, `index_type`, `source_dir`, and `entry_count`.
  - `kind` is `generated-index`.
  - `index_type` distinguishes `specs` from `archives`.
  - `entry_count` matches the number of indexed entries.

### MODIFIED
- Requirement: generated index signature
  - CLI diagnostics identify generated index files through frontmatter metadata rather than the `_Auto-generated by `rsp update`._` body footer.
  - Regenerated index bodies no longer include `_Auto-generated by `rsp update`._` once frontmatter metadata is emitted.
  - The human-readable Markdown table/body remains simple and readable without requiring a metadata-aware renderer.

### Acceptance
#### Scenario: specs index is regenerated
- GIVEN an initialized RSP project
- WHEN `rsp update` regenerates `.rsp/specs/INDEX.md`
- THEN the file starts with YAML frontmatter containing `kind: generated-index` and `index_type: specs`
- AND the frontmatter `entry_count` equals the number of additional spec files beyond `design.md`
- AND the body does not include `_Auto-generated by `rsp update`._`

#### Scenario: archive index is regenerated
- GIVEN an initialized RSP project
- WHEN `rsp update` regenerates `.rsp/archives/INDEX.md`
- THEN the file starts with YAML frontmatter containing `kind: generated-index` and `index_type: archives`
- AND the frontmatter `entry_count` equals the number of archived change files
- AND the body does not include `_Auto-generated by `rsp update`._`

#### Scenario: diagnostics validate generated indexes
- GIVEN generated index files with valid generated-index frontmatter
- WHEN `rsp doctor` checks generated indexes
- THEN it accepts the files based on metadata rather than requiring the old footer text

## Design
- Approach:
  - Add a small shared helper for generated index frontmatter emission or keep the metadata construction local to the two index builders if that remains simpler.
  - Update `buildSpecsIndex` and `buildArchiveIndex` to prepend frontmatter before the existing headings and table content.
  - Update `doctor` generated-index checks to parse frontmatter and verify `kind: generated-index` plus the expected `index_type`.
  - Keep the Markdown body focused on human-readable index content; move generated identity into metadata.
- Affected areas:
  - `src/commands/specs-index.ts`
  - `src/commands/archive-index.ts`
  - `src/commands/doctor.ts`
  - tests covering generated index output and doctor validation
- Constraints:
  - Keep metadata optional for non-index Markdown files.
  - Keep generated index metadata lightweight and stable enough for tools to consume.
  - Preserve deterministic index generation; avoid date-only churn when indexed content has not changed.
  - Avoid changing archive naming, focus handling, or durable writeback behavior.
