# Change Group: structural-simplification

## Goal
- Reduce structural duplication and clarify ownership without changing public behavior

## Scope
- Remove the runtime dependency cycle and broad helper ownership in `src/core/`.
- Make the Skill Control Model the single durable owner of transient control vocabulary and reduce inactive detail in the always-loaded Core Skill.
- Strengthen evergreen documentation semantics and split the CLI integration-test corpus into domain-owned modules.
- Preserve public CLI behavior, artifact formats, Skill authority boundaries, and package contents.

## Shared Constraints
- Follow the implementation order declared by the child dependencies.
- Prefer owner extraction and conditional loading over mechanical shortening.
- Preserve fail-closed filesystem behavior, canonical machine values, multilingual boundaries, and all existing public command output.
- Keep generated `.agents/skills/`, `.rsp/rsp-rules.md`, and historical release records out of direct authored edits.
- Use existing repository tooling and retain focused tests for every moved behavior.

## Slices
- `structural-simplification/core-dependency-layering`: remove Core runtime cycles and split broad helper responsibilities into cohesive modules.
- `structural-simplification/control-contract-concision`: consolidate durable control ownership and reduce inactive Core Skill context without losing authority or stop semantics.
- `structural-simplification/verification-structure`: detect evergreen documentation drift and split the integration-test corpus by stable verification owner.

## Completion Conditions
- [x] All three child Changes are independently verified, reviewed, and archived in dependency order.
- [x] Full build, typecheck, lint, test, documentation checks, doctor, and diff checks pass after integration.
- [x] Public CLI behavior, machine output, package inventory, and Skill authority boundaries remain unchanged.

## Durable Outcomes
- Current facts: update the smallest owning Core, Skill-system, control-model, CLI-contract, and distribution Specs when implementation establishes new module or verification boundaries.
- Lasting rationale: no new Decision Record unless implementation exposes a hard-to-reverse architectural choice not already owned by the existing Specs.
