# Change Group: harden-adoption-routing

## Goal
- Make RSP routing deterministic for the adoption failures observed in `boats-cloud`: qualification must not depend on parallelism, lifecycle closeout must require qualified Manage, direct work must be reclassified when scope grows, and design/dirty-owner transitions must preserve the correct capability and WorkRef.

## Scope
- Coordinate four ordered Skill and contract-test changes covering Core, Manage, Pre-Change Design, and worktree owner transitions.

## Shared Constraints
- Preserve automatic Manage activation without expanding planning, product-mutation, lifecycle, Git, publication, or approval authority.
- Keep runtime process data transient and avoid adding controller state or implementation-detail fixtures.
- Update authored sources under `skills/`, then build and sync the self-hosted fallback before final validation.

## Slices
- `harden-adoption-routing/clarify-manage-qualification`: define long/recovery qualification so lack of parallel slices cannot reject an otherwise eligible continuation.
- `harden-adoption-routing/gate-qualified-closeout`: make lifecycle presets dormant unless Manage was selected and qualified.
- `harden-adoption-routing/rederive-scope-escalation`: require direct work to rederive routing when later turns materially expand the task.
- `harden-adoption-routing/stabilize-owner-routing`: reliably select Pre-Change Design and prevent overlapping dirty work from silently moving to another WorkRef.
- `harden-adoption-routing/integrate-fallback-routing`: align the authored fallback, self-hosted projection, and final integrated verification with the four completed routing slices.

## Completion Conditions
- [x] Authored Skills and fallback rules express one consistent route across all four adoption scenarios.
- [x] Focused contract tests cover each observed failure without depending on transcript wording or elapsed wall-clock time.
- [x] Build, lint, full test suite, self-hosted update, and `rsp check` pass from a clean logical boundary.

## Durable Outcomes
- Current facts: update the smallest existing RSP workflow Spec if the final behavior is not already represented.
- Lasting rationale: none unless implementation exposes a new material tradeoff.

## Blockers
