# Change: streamline-workflow-ownership

## Proposal
- Outcome: Preserve RSP's task-to-Skill routing, delegation, dependency-aware safe parallelism and automatic review/repair while giving each workflow decision one owner and selecting depth from current evidence.
- Scope: Authored Skills, fallback, workflow/work-model/CLI contracts, explicit configuration migration, bilingual guidance and focused native evaluation fixtures with deterministic calibration.
- Non-goals: A new controller or runtime state store, lite artifacts, package-name changes, model/provider reconfiguration, broad or matched evaluation campaigns, commit or publication. The 2026-10-14 follow-up authorizes one live attempt each for correction-review and correction-limit with existing settings and retained failures.

## Spec
### MODIFIED
- Routine knowledge writeback updates justified facts and related records without final whole-Change convergence. Final delivery or closure retains the existing convergence, evidence and authority gates. An unavailable RSP upgrade blocks only actions depending on its missing evidence; Commit still decides separately authorized checkpoint eligibility.
- Review distinguishes confirmed defects or explicit verification-contract violations from insufficient evidence. Missing decisive evidence blocks only affected judgments; draft/out-of-scope choices are not automatic ambiguity findings. Required checks and independent review remain binding.
- The post-seventh-run consolidation supersedes the detailed reading, batching and encoding prescriptions from recent trace refinements. Core owns routing and result acceptance; executors choose applicable methods and inspect sources. Existing context and evidence may be reused while relevant inputs remain valid, without prescribing an exact command sequence.
- Dependent writes still require successful prerequisites; uncertain effects require inspection before safe replay. Permission boundaries, actual outcomes, required checks and independent review remain binding. Tool-call counts and minor recoverable deviations are diagnostics, not new acceptance gates.
- Review selects methods from the actual judged content and risks; supporting references do not enlarge that target. Compact reports cover applicable judgments and material limits, while explicit consumer formats and canonical status values remain supported.
- Document rules preserve meaning and technical literals, distinguish wording from structural changes, and organize by reader purpose. Doc owns writing/self-checks; Review owns separately required judgment. General writing guidance stays outside Core.
- Core owns the cross-capability correction/re-review loop; Implement owns one bounded correction and its checks, and Review owns the fixed-scope judgment. Direct capability use remains supported without a mandatory Core preflight.
- RSP retains decisions about whether to delegate, eligible dependency waves and safe concurrency. Hosts supply actual worker, isolation, waiting and cancellation mechanisms and evidence.
- Pure existing Tasks/Verify refreshes stay direct while the accepted contract, design and stable knowledge remain accurate and no lifecycle/terminal delivery is being prepared; contradictions and necessary knowledge updates leave that path.
- Settled direct tasks use the minimum applicable method; material decisions, required review, independent execution and protected operations retain their gates.
- Reuse traceable evidence only while its tested boundary and relevant inputs apply. Review still supplies current semantic judgment; task completion and transport success never replace required acceptance.
- Necessary knowledge writeback and final Change consistency remain required; already-converged records need no cosmetic rewrite. The authorized architecture follow-up replaces Manage with independent delegation and final-delivery closeout policies. Git and external actions retain separate authority.

### Acceptance
#### Scenario: Direct entry and bounded coordinator reading
- GIVEN an authorized direct task without a selected or required WorkOwner
- WHEN the task needs configuration or worker acceptance
- THEN missing tracking does not create a plan, setup requirement or false stop; needed configuration is validated independently, and worker execution details are loaded by their owners without weakening Core's result validation.
#### Scenario: Natural request and remaining correction budget
- GIVEN a natural repair request whose repository authority requires independent review
- WHEN an accepted finding has either no completed corrections or one ineffective correction followed by new decisive evidence
- THEN the task completes authorized correction and independent review without an invented planning phase, user continuation prompt or premature exhausted-budget stop; other genuine stop conditions still apply.
#### Scenario: Ordinary task stays bounded
- GIVEN a clear authorized correction with applicable checks
- WHEN RSP completes it
- THEN it does not manufacture a tracked owner, planning phase, worker or extra verification responsibility without a concrete need.
#### Scenario: Evidence refresh does not imply closeout
- GIVEN an existing Tasks/Verify refresh with accurate scope, contract, design and stable knowledge
- WHEN no lifecycle or terminal delivery is being prepared
- THEN Core updates actual outcomes directly and preserves all Required obligations, failures and separately required Review without manufacturing whole-Change writing.
- WHEN lifecycle or terminal delivery is selected instead
- THEN necessary writeback, whole-Change convergence, Review, current readiness and exact delivery authority still apply.
#### Scenario: Correction has one coordinator
- GIVEN an authorized repair and required review
- WHEN a reviewer returns an accepted finding
- THEN Core carries the existing scope through one Implement correction and fresh Review; Implement cannot self-certify review-clean or run a competing loop.
#### Scenario: Accepted finding and exhausted recovery have explicit probes
- GIVEN a fixture-supplied accepted finding and correction/review authority
- WHEN the correction-review task runs
- THEN acceptance requires an actual correction followed by fresh independent review of the corrected target, not the supplied finding report or implementer self-certification.
- GIVEN a synthetic recovery history in which the same finding survived two completed corrections
- WHEN the correction-limit task resumes
- THEN it observes the current failure, preserves the target and returns the unresolved finding without a third correction or counter reset; supplied history is never described as fresh execution.
#### Scenario: Delegation and parallel work remain useful and safe
- GIVEN ready independent work or a required independent reviewer
- WHEN RSP selects dispatch
- THEN actual host evidence establishes worker attribution and writer/resource isolation; blocked dependencies and incompatible resources remain serial or stopped.
#### Scenario: Evidence and closeout remain truthful
- GIVEN passing, stale or unavailable evidence and existing user work
- WHEN completion is assessed
- THEN only applicable results are reused, required evidence and review remain binding, and archive/Git authority is not inferred or expanded.

### Architecture acceptance (2026-10-15)
- Direct needs no durable owner; Change retains one recoverable delivery boundary; Group needs independently acceptable children and dependencies/integration, never file or worker counts alone.
- Automatic delegation defaults off. When allowed, the user or main agent chooses worker count without RSP tiers or limits; host constraints, ownership and independence still apply.
- workflow.delegation (off | auto) and workflow.closeout (ask | auto | manual) replace manage. Defaults are off/ask. Legacy configuration fails with explicit migration guidance; update does not silently reinterpret or mutate it on refusal.
- Ordinary completion and checkpoint commits keep Change open. Explicit close requests or established final delivery activate closeout; ask is default, auto applies only at eligible final delivery, and manual needs an explicit close request. No setting authorizes Git.
- Evidence follows relevant inputs and acceptance. Independent review may consume traceable implementer checks; explicitly independent execution remains binding. Corrections use affected checks and scoped re-review.
- Necessary knowledge precedes final Change convergence; these can be one operation, with no edit when already accurate. Final delivery reconciles evidence rather than mandating repeated full verification.

## Design
The current consolidation removes recent execution-detail prescriptions in their existing owners, with no new phase, configuration, resource or runtime helper. Keep the three work shapes, delegation/closeout policies, protected delivery gates and independent review. Pause live tuning; use package/resource, security, document, offline schema and author-path checks only. Earlier run records retain their original candidates and outcomes.

Use the existing suite and conditional references. Centralize cross-capability loop ownership in Core while retaining the existing separate worker-correction and finding-resolution ceilings and early stops with one counter owner. Keep execution methods local to capabilities, use existing host observations, and add no new runtime transport or state. Add focused natural-task and resource-safety fixtures to the existing Harbor catalog rather than a new evaluator. Runtime model acceptance remains a separate evidence boundary when its environment is unavailable. The architecture revision separates work shape, worker dispatch and final-delivery closure. Replace the existing configuration projection with workflow policy rather than adding a second controller; reject legacy manage settings before mutation so the former local Git grant cannot survive implicitly. Merge coordination qualification into Core/worker guidance, keep exceptional recovery conditional, and test new delivery policies with real setup evidence plus independent semantic review of the candidate.
