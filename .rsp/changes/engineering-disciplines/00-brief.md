# Change Group: engineering-disciplines

## Goal
- Complete the standalone RSP 3.0 engineering-discipline surface with concise diagnosis and TDD Skills, then prove that Core routes into them without recursive orchestration or Superpowers-style workflow overhead.

## Scope
- Coordinate two independently executable Skill slices and one terminal installed-suite validation slice.
- Replace the current manual-fallback-only qualification with demonstrated diagnosis and red-green-refactor behavior while preserving the existing Change as owner.

## Shared Constraints
- Assume a capable model: encode only the non-obvious sequence, evidence gates, stop conditions, authority rules, and return contract needed for predictable behavior.
- Keep each canonical Skill host-neutral, concise, independently invocable, and free of hidden state, recursive Skill invocation, automatic retries, Git delivery, or publication authority.
- Use progressive disclosure only for a demonstrated branch that would otherwise burden every invocation; do not copy upstream tutorials, catalogs, or always-on routing.
- The validation slice must use isolated installed-package tasks and must report latency, context cost, conflicts, omissions, and authority restraint truthfully.

## Slices
- `engineering-disciplines/add-rsp-tdd`: publish and validate a compact test-first discipline from a clear behavior through observed red, minimal green, safe refactor, and return to one Change.
- `engineering-disciplines/add-rsp-diagnose`: publish and validate a compact diagnosis discipline from reproducible symptom through discriminating evidence to a confirmed cause without speculative production mutation.
- `engineering-disciplines/validate-discipline-composition`: validate Core selection, both Skills, fallback compatibility, context cost, and conflict restraint against the installed suite.

## Completion Conditions
- [ ] Both discipline Skills are archived with focused contract and behavior evidence.
- [ ] Installed-suite validation demonstrates one diagnosis task and one TDD task in fresh contexts, including correct return ownership and no unauthorized delivery action.
- [ ] The evaluation compares concise RSP behavior with the retained upstream risks without claiming generic debugging, testing, or cross-host completeness.
- [ ] `release-3-0-0` depends on the archived terminal validation before release preparation resumes.

## Durable Outcomes
- Update `research/models/rsp-skill-system.md`, `research/models/rsp-capability-coverage.md`, and `.rsp/specs/design.md` only after behavior is promoted and validated.

## Blockers
- none
