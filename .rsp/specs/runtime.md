# Local Runtime, Broker, and Web Observatory

## Purpose
- Define the optional user-level Broker, checkout-scoped runtime observation store, local read-only Web Observatory, compatibility and discovery protocol, exact checkout-session identity, transport security, bounded context reuse, and disposable lifecycle without changing repository authority.

## Stable Facts
- One resolved user-cache root owns at most one authoritative Broker discovery record and startup lock. Compatible clients reuse the healthy process even when package versions differ; compatibility is determined independently by Broker protocol and runtime-schema versions.
- The managed-observability-capable Broker protocol is `1.2`; the first runtime-store-capable Broker compatibility identity remains runtime schema `1.1`. A Broker with an incompatible protocol major, runtime-schema major, or older required minor is never reused, while a compatible newer minor may serve the client. The client never starts an implicit side-by-side Broker.
- Startup serializes through a complete-record atomic `start.lock`, rechecks discovery after acquiring the lock, and launches the packaged `dist/broker-daemon.mjs` entry only when no compatible owner exists. The client passes a one-time startup claim that exactly one daemon atomically takes over; the daemon revalidates that claim and publishes discovery exclusively before releasing the lock, while a late or losing daemon exits without overwriting another owner.
- Discovery metadata records one instance ID, PID, process-start identity, exact loopback endpoint, protocol and schema identities, package version, start time, and private control token. Human and JSON CLI projections omit the control token and process-start identity.
- Discovery classifies metadata as stale only when the PID is absent or its observed process-start identity differs. If a live PID identity cannot be observed, startup and stop fail closed without removing metadata. Recovery first atomically quarantines the path and removes only the same inspected file identity; a concurrently replaced owner is restored or preserved and is never deleted or signaled.
- Explicit stop is cooperative through the authenticated owned endpoint. Shutdown closes project sessions and HTTP/SSE connections, removes only its own unchanged discovery record, and leaves ordinary repository files untouched.
- The endpoint binds an ephemeral port on exact `http://127.0.0.1`. Every request requires a loopback peer, exact request target, and exact `Host`; browser requests with `Origin` require the exact bound origin. Control routes require the discovery control token, project routes require the exact in-memory project token, and Web API routes require a separately scoped in-memory Web bearer. Responses disable caching and MIME sniffing and apply no-referrer, frame denial, a strict `default-src 'none'` Content Security Policy, and a restrictive Permissions Policy.
- Request JSON is bounded to 16 KiB, every JSON response is serialized and checked before headers against a 64 KiB limit, and discovery/lock metadata is bounded to 64 KiB. Status reports the exact loaded-session count plus a bounded session list and explicit truncation flag. Discovery and lock files are private regular files read with no-follow and file-identity checks; the Broker cache root is private on supported POSIX hosts.
- Cache resolution uses `RSP_BROKER_CACHE_HOME` when explicitly set, otherwise `$XDG_CACHE_HOME/rsp/broker`, `%LOCALAPPDATA%/rsp/broker` on Windows, `~/Library/Caches/rsp/broker` on macOS, or `~/.cache/rsp/broker` on other hosts.
- A project session is created lazily from one canonical Git checkout top-level. Its `projectId` hashes the real checkout root plus filesystem device and inode, so separate repositories and distinct worktrees of one common Git directory remain separate identities. Concurrent registration of one `projectId` is serialized to one canonical loaded session and access token.
- Each loaded session owns one random access token and one namespace under `projects/<projectId>`. Tokens, roots, namespaces, status, and SSE subscriptions never cross project IDs. Project-relative paths reject absolute, backslash, empty, dot, or parent segments and revalidate the nearest existing real path against the canonical checkout root.
- `rsp web` explicitly starts or reuses a protocol-compatible Broker and registers the exact current checkout. The normal command path opens a URL whose fragment carries one short-lived, one-use bootstrap; URL fragments are not sent in the initial request or Referer, the browser removes the fragment before API access, and the bootstrap is exchanged only from the exact Broker origin for a bounded in-memory Web bearer. Normal human and JSON output shows only the credential-free project URL. Explicit `--print-url` and interactive browser-open failure are the only terminal fallback paths that reveal the expiring bootstrap.
- The base Web Observatory serves only package-authored `index.html`, CSS, and JavaScript from an exact no-follow allowlist. The bundle contains no checkout data, paths, credentials, or environment configuration, uses no browser framework/runtime dependency, and keeps authorization only in page memory without cookies or browser storage.
- The base browser shell uses English for its small set of presentation-owned labels. WorkRefs and projected repository content remain unchanged; additional browser locales require a separately selected presentation change rather than reading project artifact-language configuration.
- Overview, Specs, and History are read-only server projections. Overview derives current WorkRef, goal, state, blockers, diagnostics, and next action in an isolated projector process rooted at the exact checkout; Specs and History reuse their presentation-neutral current-file inspection, bounded search, query, and detail seams. The browser renders those projections and never derives workflow meaning from Markdown.
- A Web snapshot carries projection version `1.1`, project and Git freshness, per-section identities, generation time, and one snapshot identity. Successful refresh replaces the complete cached/browser snapshot atomically. A failed or incompatible refresh retains the previous complete snapshot, marks it visibly stale, and returns only a bounded redacted error plus the stale snapshot identity.
- Runs and Attention consume only bounded Manage-owned project projections. They present actor topology, dispatch and receipt identity, duplicate delivery counts, evidence references, changed paths, stop boundaries, freshness, and the committed-sequence timeline without deriving completion or acceptance. Missing receipts, boundary changes, truncation, stale repository relationships, and runtime absence or incompatibility remain explicit; runtime failure does not disable Overview, Specs, or History.
- The Web-bearer managed SSE route uses project-local monotonic event IDs and a bounded replay buffer. Reconnect supplies `Last-Event-ID`; retained events replay once, an old or future cursor emits an explicit gap, and the browser performs one fresh atomic snapshot before continuing. Unchanged polling does not create another projection event. Duplicate or conflicting delivery may update delivery metadata, but never duplicates the accepted timeline effect; active authorized managed SSE subscribers prevent idle session unload.
- Web routes use an exact GET/POST, path, and query allowlist. There are no lifecycle, filesystem, command, Git, runtime-mutation, Markdown-write, account, cloud, or remote-binding routes. Text projections omit absolute checkout roots and external issue URLs, bound records and detail, and redact credential-shaped values before transport.
- Each project namespace may contain one `runtime-v1.sqlite` database whose schema major is `1` and current migration version is `3`. The filename remains stable across compatible minor migrations; an incompatible schema major, newer migration version, incomplete migration history, project-identity mismatch, or corrupt database fails closed for that checkout without preventing unrelated sessions from operating.
- `rsp doctor` inspects optional Broker discovery, the exact current Git checkout namespace, runtime schema/integrity, and at most 32 retained context packets without starting Broker, registering a session, opening a writable database, or creating an absent cache. It snapshots and revalidates real namespace/database/sidecar parent and file identities, rejects symlink, swap, and oversize state before SQLite, copies at most the declared 64 MiB per-file bound into one private disposable namespace, and opens only the verified snapshot. It distinguishes absent, healthy, stale, invalid, unhealthy, incompatible, migration-required, incomplete, and corrupt state. Existing POSIX cache/project/namespace directories may grant no permissions beyond `0700`, and discovery/lock/database/sidecar files no permissions beyond `0600`; doctor reports but never chmods, while Windows skips POSIX mode semantics. Fresh context additionally requires canonical finite ordered `updated_at` and `expires_at`; malformed, reversed, expired, or future-updated packets fail closed as stale/corrupt. Caller-controlled inspection time is not part of the packaged API. Resume still owns dirty-path and authority-aggregate revalidation.
- The runtime store lazily loads the built-in `node:sqlite` module only when a Broker project session or direct runtime adapter opens it. The package requires Node.js `>=22.13.0`, ships `dist/runtime-store.mjs` plus the host-neutral `dist/manage-runtime.mjs` adapter, and installs no native SQLite addon. `--no-experimental-sqlite` produces `runtime_sqlite_unavailable` for runtime opening while ordinary one-shot CLI commands remain usable and do not load SQLite.
- Writable databases use WAL, foreign keys, a five-second busy timeout, short `BEGIN IMMEDIATE` transactions, bounded page count, integrity checks, and atomic versioned migrations. Transactions never span model calls, tools, shell commands, tests, network requests, or human decisions.
- Runs, dispatches, events, and receipts are exactly project- and run-namespaced. Dispatches, events, and receipts are append-only; every newly committed observation boundary, including dispatch, receives one transactional per-run sequence independent from worker clocks. Stable idempotency keys make duplicate and conflicting deliveries observable, and duplicate content retains one committed effect at its original sequence without advancing the run revision. Missing or later parents remain explicit out-of-order observations rather than being silently reordered.
- Broker protocol `1.2` adds project-token-scoped capability discovery and service endpoints for optional managed observability. The capability identity is `rsp.manage-runtime@1.0`; discovery inspects only an already running compatible Broker and never starts one. Direct store adapters expose the same capability contract without HTTP.
- The managed adapter records only host-confirmed run, dispatch, event, receipt, attention, pause, resume, terminal, and context boundaries. Dispatch is recorded only after the host returns the exact dispatch and worker identities; every worker event requires an existing dispatch and the exact matching worker identity, and receipts require the same pair. Duplicate delivery retains one committed effect, while missing, unavailable, or `boundary-changed` receipts remain incomplete observations and may project attention without manufacturing success.
- Runtime observation never changes Core or Manage routing, authority, dispatch limits, worker obligations, acceptance, review, closeout, lifecycle, Git, publication, deployment, approval, or human acceptance. Runtime absence, incompatibility, corruption, or an individual observation failure returns a bounded diagnostic and leaves the canonical no-runtime control result unchanged.
- Managed run and attention projections are read-only, explicitly non-authoritative, and bounded to at most 32 returned items each. Each projection reads the current run revision, events, dispatches, and receipts from one short SQLite read snapshot so every returned row is attributable to its committed source sequence; source references carry exact project, WorkRef, run, dispatch, event, or receipt identity and sequence. `terminalDeliveryObserved` is a narrow host-delivery projection: it requires an explicit host-confirmed terminal run observation whose sequence equals the current committed source sequence, at least one observed dispatch, no truncation, and a retained non-unavailable, non-`boundary-changed` receipt for every observed dispatch. It becomes false after any later committed observation until another current terminal boundary is recorded, is false for zero dispatches or any incomplete delivery, and never represents managed completion, acceptance, review, or closeout. Truncation, missing receipts, explicit attention, and boundary-changing receipts remain visible without becoming frontier, acceptance, or closeout inputs.
- Projection checkpoints use projector identity, projector version, committed source sequence, monotonically increasing version, and compare-and-swap. A stale writer receives the current version and must replay from committed observations.
- Context packets are bounded disposable projections containing only owner and authority references, phase, decisive observation summaries, blockers, attention, evidence pointers, changed paths, freshness identities, and next action. They never contain raw prompts, hidden reasoning, complete conversations, credentials, arbitrary command logs, or unbounded process output.
- Managed context packets use the fixed `manage-resume` packet key, are at most 12 KiB, and expire no later than 24 hours after update. Public save and hydrate requests contain no caller-controlled update, expiry, or current-time fields; the runtime service clock assigns update and expiry and decides hydration age. Save compares the packet source sequence with the current committed run revision inside the same short ownership transaction that applies its version check and write; a stale source sequence returns a not-applied conflict and never persists a falsely current packet. Hydration compares that source sequence again before reuse, so every later committed dispatch, event, receipt, attention, pause, resume, or terminal observation invalidates the prior packet while a duplicate delivery does not invent another revision. Context hydration also revalidates project, checkout root, WorkRef, Git HEAD, dirty-path hash, authority hash, packet schema, expiry, authority references, and the complete source-key set. Unchanged packets still require rereading current authority pointers; changed or newly added evidence sources trigger targeted reread with stale evidence removed, while absent runtime, expired or revision-stale context, changed authority, or checkout-wide identity drift forces the ordinary full reread. Selective hydration and full reread must derive the same canonical control result; current authority always wins.
- Event, receipt, checkpoint, and context payloads are JSON-only, depth- and collection-bounded, byte-bounded, credential-filtered, and value-pattern redacted before persistence. Database, run, dispatch, event, context-packet, projection, and retention limits prevent unbounded accumulation.
- Retention deletes expired context packets and old or excess runs inside short transactions. The database and its WAL sidecars are project-local disposable files removed through identity-scoped cleanup after open handles close. Missing runtime data returns an unavailable projection without changing Markdown inspection, readiness, history, or lifecycle behavior.
- Repository migration never disposes runtime state. Cache disposal requires explicit authority and closed owning Broker/session/store handles. The packaged `@oevery/rsp/dist/runtime-store.mjs` entry exposes `resolveRuntimeDisposalTarget()` to derive the current checkout's project ID, exact cache root, projects root, and namespace without starting Broker, plus `disposeRuntimeDatabase(target)` to require that complete target, bind `projectsRoot` to `<cacheRoot>/projects`, bind `namespacePath` to `<projectsRoot>/<projectId>`, and remove only identity-verified runtime database/sidecar paths after revalidating the complete real chain before and around every mutation. Hand deletion, root deletion, identity guesses, target substitution, cache-root/projects-root/namespace symlink or swap state, and another project namespace remain unsupported.
- Inactive project sessions unload from memory after five minutes by default. Active SSE subscribers and bounded Web heartbeats keep a session loaded; closing the page stops heartbeats and permits normal idle unload. Unload closes the lazily opened runtime handle and discards Web tokens, bootstraps, and snapshots without deleting the disposable project namespace or changing repository truth. Re-registration after unload issues new tokens and may reopen a compatible retained database.
- Both SSE routes authenticate before sending headers. The base project-token route emits session lifecycle events; the Web-bearer managed route emits only redacted projection, gap, and terminal events. Explicit Broker shutdown emits `broker-stopping` to connected subscribers.
- `rsp broker status` is non-starting and cache-free when the Broker is absent. `rsp web` is the explicit browser operation that may start and register with the Broker. `rsp status`, `rsp check`, `rsp show`, `rsp specs`, lifecycle, Git, and other one-shot commands neither require nor automatically start the Broker.

## Boundaries
- In scope:
  - User-level discovery, compatibility, singleton startup, cooperative shutdown, process identity, loopback HTTP/SSE transport, canonical checkout identity, lazy project sessions, token isolation, path scoping, read-only base Web presentation, atomic snapshots, runtime observations and receipts, host-neutral managed observation and correlation, bounded run and attention projections, guarded checkpoints, bounded context packets and selective hydration, migrations, retention, disposal, and idle unload.
- Out of scope:
  - Repository semantics, planning, product mutation, lifecycle decisions, Git, publication, deployment, approval, a general agent scheduler, worker creation, lane selection, automatic retry, remote access, OS services, permanent analytics, and authoritative managed-run state or timelines.

## Constraints
- Repository Markdown and current checkout evidence remain authoritative. Discovery, sessions, tokens, namespaces, committed runtime observations, checkpoints, context packets, and transport responses are operational state; only the committed observation sequence is authoritative for what the runtime observed inside its retained namespace.
- Incompatibility, incomplete process identity, endpoint-owner mismatch, invalid cache metadata, unsafe paths, cross-project credentials, stale context, corrupt storage, and incomplete migration history fail closed.
- No runtime or transport success grants authority beyond the invoking RSP operation.
