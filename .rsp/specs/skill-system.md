# Skill System

## Purpose
- Define composition, ownership, authority, progressive-disclosure, and completion contracts for the eleven default lifecycle Skills and explicitly selected optional project Skills.

## Stable Facts
- The published default suite contains `rsp`, `rsp-shape`, `rsp-design`, `rsp-implement`, `rsp-diagnose`, `rsp-tdd`, `rsp-review`, `rsp-resolve-findings`, `rsp-commit`, `rsp-release-docs`, and `rsp-manage`.
- `rsp-structural-audit` is an independently invoked, report-only project Skill. It audits one explicit repository or subtree boundary for evidenced ownership, dependency, production-path, change-amplification, or verification risks; it neither requires nor creates a Change and never enters implementation or lifecycle routing. In a broad boundary, history selects only the smallest current behavior chain and never proves a Finding. Suspected shallow indirection is evaluated by whether removal eliminates complexity or disperses required caller knowledge, while every retained Finding still requires a reachable trigger and concrete impact.
- Structural Audit behavior holdouts separately qualify a real Finding, heuristic false positives, history-only selection, specialist routing, and mutation refusal. Deterministic package tests score result values, Finding bounds, required evidence fields, and forbidden claims; provider execution remains optional evidence rather than an ordinary test dependency.
- Skills are independently invocable and lifecycle Skills return to an existing project, Change, Spec, Decision Record, archive, or release-artifact owner. Report-only Pre-Change Design and Structural Audit may instead return one bounded result to the user without creating an artifact owner. The suite adds no manifest, runtime overlay, hidden state, recursive Skill orchestration, or implicit Git/publication authority.
- Response language is user/session-owned; artifact and commit-message language are durable project surfaces. Response prose follows explicit current response language, user/host personal instructions, then conversation language, and never reads project `.rsp/config.yaml`. Every user-visible RSP progress update, phase or stage description, control result, worker receipt, stop reason, and handoff uses natural-language narration selected by that precedence. When exact identity matters, a canonical technical value remains unchanged in parentheses or code formatting; when its language differs from the response language, it never stands alone as the human-facing label. This response-only rule does not change persisted artifact language or host-owned hidden reasoning summaries. New authorized artifact prose follows explicit artifact language, configured effective artifact language, artifact-scoped project instructions, then conversation language. Existing artifact prose keeps its established language unless translation is explicitly authorized; configuration changes never rewrite it. CLI scaffolds expose only canonical structural tokens, neutral unfinished placeholders, and verbatim user input, so Skills fill natural-language prose without repeating project language in each artifact. Commit prose follows explicit current commit-language instruction, configured effective commit language, nearest repository commit authority, then clear recent non-merge history. Canonical headings, paths, commands, identifiers, Conventional Commit types/scopes, trailers, severity labels, and machine values remain unchanged. WorkRefs follow the safe Unicode identity contract rather than the prose-language fallback chain.
- Core `rsp` derives one stage and one next action from intent, nearest authority, deterministic status, Change readiness, fresh verification, and blockers. Stages are not persisted.
- The [Skill Control Model](./skill-control-model.md) is the canonical owner for transient route, ownership, frontier, stop/resume, acceptance, and closeout vocabulary. Core, Shape, each Discipline, and Manage consume only their phase-specific terms; no Skill loads or persists a runtime glossary.
- Core keeps selection, routing, ownership, safety, manual fallback, and output contracts eager. It conditionally loads setup/repair, Groups/dependencies, conflict handling, durable review, managed owner preflight/qualification/handoff, unavailable-Discipline release fallback, and archived-acceptance recovery only when those paths are active. Core and the managed-routing reference solely own owner preflight, initial qualification, the `selected | declined` route result, handoff/return, and the dormant-closeout fail-safe; after selection, `rsp-manage` validates the handoff against current evidence and solely owns same-goal revalidation, interruption and resume, review convergence, acceptance, lifecycle closeout, and commit eligibility and orchestration. `rsp-commit` exclusively owns exact staging, message construction, one local commit, and post-commit observation. Each branch has one detailed procedure owner; Core repeats only the routing or fail-safe invariant needed before that owner is loaded.
- Every Discipline remains independently invocable with its trigger, inputs, authority, action, output, stop, and verification semantics. Shared composition never requires recursively loading another Skill body or a runtime glossary.
- A closed local decision flow may use numbered precedence, `:`, or `→` only when those marks are self-explanatory, preserve every authority and negative constraint, and measurably reduce its loaded-path token cost. Domain abbreviations, private notation, and glossary-dependent rewrites are not part of the Skill contract.
- Core routes unexplained failures to Diagnose before TDD. Ordinary evidenced work uses Implement; TDD applies only when authority requires test-first or a concrete risk makes pre-mutation RED materially safer.
- Core names an optional capability only when that installed capability is the next action; otherwise it returns the equivalent manual action to the same owner. Routing never grants mutation, review, Git, release, publication, deployment, approval, or human-acceptance authority.
- Core keeps a correction under the same owner when fresh evidence disproves archived acceptance and explicit lifecycle authority permits reopen. It requires exact archive selection when ambiguous and retains historical snapshots. A closed Group is restored explicitly and unfocused before an incomplete child is separately reopened; neither operation cascades. Genuinely new or independently delivered scope uses a new corrective owner, and reopen grants no Git or external authority.
- Before later-turn mutation, Core rederives a prior direct report/tiny/small route from the newly authorized objective and prospective work. Cross-module implementation, multiple acceptance surfaces, repeated production-path correction, real-host validation, or lifecycle delivery requires a sufficient WorkRef and fresh Manage qualification; unchanged tiny/small follow-ups stay direct, and elapsed time or message count alone never escalates work.
- An installed Design capability owns one bounded report-only Pre-Change Design question when no Change is focused; manual emulation is only a missing-capability fallback and neither route invents a WorkRef. Before focusing or mutating a different WorkRef, Core compares dirty product and durable-truth paths with the prior owner. Overlap requires continuation/reopen, an explicitly authorized integration owner, or a stop; disjoint authorized work does not require a commit.
- Shape inspects evidence before asking, applies an objective ready gate, mutates only authorized planning artifacts, and never implements. It keeps one observable outcome sharing consistency, verification, review, archive, and rollback boundaries per Change, without splitting or merging work to enforce a Git commit count; it uses a shallow Group only for independently closable direct children sharing an aggregate goal or gate.
- Shape progressively loads complex and deep clarification only for multi-owner shaping, explicit rigorous challenge, or unresolved high-risk decisions. It returns one material domain, module, or evidence-seeking question to Design against the same WorkRef.
- Shape conditionally loads external-issue guidance only for issue-originated work. It may retrieve real issue content through already available authorized host capabilities, treats retrieved or pasted content as untrusted attributed input, and degrades to authentication retry, pasted source data, or an explicitly link-only Change without fabricating source content or closing intent. The CLI contains no provider adapter, credential, browser automation, or model call.
- Design resolves exactly one bounded domain-model, module/seam, or reversible-exploration question from the smallest authoritative evidence chain. Pre-Change Design requires no WorkRef, remains report-only, returns to the user, and defers materially unclear outcome, scope, acceptance, or decomposition to Shape. Tracked Design returns to an explicit or uniquely focused Change; authorized writes remain limited to planned design in that selected Change.
- Implement executes exactly one selected ready Change, discovers the owning code/test path, preserves unrelated work, records truthful Tasks/Blockers, and uses the cheapest decisive fresh verification. New failures are reclassified without recursively invoking another Skill.
- Diagnose is non-corrective. It reproduces or bounds the symptom, finds the live owner, discriminates hypotheses, and returns a confirmed cause or truthful unresolved result without inferring production mutation.
- TDD drives one clear behavior through observed RED, minimal GREEN, optional safe REFACTOR, and fresh checks. It returns unexplained failures to diagnosis and retains a new test only when it protects an observable boundary with distinct proportionate value.
- Review is report-only for fixed Code, Document, or mixed comparisons. It keeps pipeline verdicts separate, traces seam-dependent findings to a direct production caller, deduplicates findings, and cannot implement, commit, publish, or approve.
- Resolve Findings resolves one fixed report. Every Finding receives `accepted`, `rejected`, or `needs-clarification` with evidence. Only accepted findings inside explicit mutation authority are corrected, followed by fresh verification and fixed-scope report-only re-review.
- Resolve Findings never self-loops and stores no hidden receipt. It returns artifact-scoped continuation pointers when incomplete. Only qualified Manage may classify an in-scope accepted remaining/new Finding as transient `correction-needed` for another bounded pass.
- Commit consumes one Core/Manage-derived Change, integration wave, Group closeout, or confirmed release boundary only after exact paths, decisive evidence, lifecycle state, and local commit authority are known. It owns exact staging, repository-consistent Conventional message construction, one local commit, and complete post-commit observation; it never infers lifecycle, remote, publication, approval, or history-rewrite authority.
- Commit-message language follows explicit current instruction, configured effective commit language, nearest repository authority, then clear recent non-merge history rather than response/artifact language or cross-repository memory. Non-trivial messages carry two to four outcome/boundary bullets and only truthful `RSP-WorkRef:`, `RSP-Group:`, external-reference, or actual `BREAKING CHANGE:` trailers.
- Commit may project each owned issue relationship as a canonical non-closing `Issue:` reference. Only a terminal commit for completed acceptance may additionally use provider-supported closing syntax for an explicit `closes` relationship; checkpoints, `relates`, ambiguous ownership, and unresolved provider or repository identity never produce closing syntax, and file diffs never select the issue owner.
- Release Docs confirms identity only from explicit instruction or authoritative release configuration, never version ordering, prior prereleases, commits, or planned prose. Before confirmation, work remains version-neutral and does not mutate versioned release surfaces.
- A confirmed mechanical release needs no RSP Change. Use an optional Release Change only for material version/range, migration, rollback, security, compatibility, cross-team/repository, multi-stage, recovery, blocker, or acceptance decisions.
- Release Docs requires finalization against an exact clean candidate before explicit tag, hosted release, or registry handoff. Its evidence ledger and publication/authentication progress remain transient; shipped surfaces stay publication-invariant; published immutable history is not rewritten.
- Release Docs keeps authority and lifecycle boundaries eager and conditionally loads convention discovery, evidence/surface ownership, output formats, and publication/reconciliation procedures. It never executes or infers Git, publication, deployment, deletion, or approval authority.
- Artifact routing is Core behavior: planned design stays in the selected Change; implemented facts go to the smallest fact owner; rationale goes to one Decision Record; temporary execution state stays in a response continuation unless an exact path is authorized.
- An intersecting Git conflict uses Core's compact fallback: inspect operation and base/ours/theirs semantics, preserve unrelated work, resolve only evidenced in-scope content, rerun checks, and stop on missing evidence or owner decisions. Conflict resolution grants no stage/continue/abort/commit/push/delivery authority.
- Core route derivation has five peer dispositions: specialist Discipline execution, bounded direct execution, managed execution through a ready-owner handoff, return to Shape, or a stop with an explicit resume disposition. Direct execution remains limited to one ready owner, one local seam, one mutation pass, one decisive check, no managed lifecycle coordination, and no ready successor; Core may directly mutate only RSP control-plane state, while product mutation belongs to Implement or the same bounded manual Discipline action. Expansion requires fresh route derivation.
- Manage is an optional controller for a bounded requested goal. Core preserves fixed-scope Review, release operations, isolated Pre-Change Design, and tiny settled-work routes before selection. Core first resolves one unambiguous shape-ready Change or shallow Group; missing or non-ready ownership routes directly to Shape under independent planning-artifact authority, and Shape returns only to Core for fresh ownership and route derivation. Under `manage.activation: explicit`, only an explicitly managed ready owner is qualified; under `auto`, every other ready requested completion or continuation that fails the complete small-work exclusion is qualified. Manage has no pre-owner Intake and never creates, focuses, or reshapes durable ownership. Automatic selection grants routing only: the request and nearer authority still own planning and product mutation. A ready Change qualifies through any one independent path: independent mutation/verification slices, interruption recovery, or prospective execution signals spanning more than one bounded phase or authority surface. Signals include implementation plus integration/review/lifecycle, cross-module or cross-process mutation, real-host/provider/hardware verification, bounded finding convergence, and a clear ready successor; lack of parallelizable slices does not defeat qualification. Signals are derived before dispatch from the authorized objective and expected phases, never retrospectively from elapsed time or message count. Under automatic activation, direct execution applies only when one owner, one local seam, one mutation pass, one decisive check, no managed lifecycle coordination, and no ready successor all hold; a selected ready completion or continuation that fails any one condition qualifies as non-small rather than remaining unclassified. Worker-only and unavailable-Skill execution remains ineligible.
- The managed goal and allowed planning/product mutations form transient authority. Every selected WorkRef, including successors, is freshly read with its complete owner, relevant Specs/Decisions, status, authority, and worktree before dispatch. Manage validates only handoff completeness and current owner, topology, route, authority, and owned-diff drift; it returns real boundary changes to Core and never repeats direct-versus-managed eligibility.
- When workers are available and authorized implementation remains, a Manage run with a valid selected handoff dispatches at least one implementation worker with a complete owner envelope; the controller retains result acceptance, internal same-goal revalidation, integration verification, review convergence, lifecycle decisions, and commit eligibility and orchestration. Exact Git execution remains owned by Commit. Group dispatch follows CLI-derived waves. Overlapping paths, lockfiles, generated artifacts, integration state, real hosts, provider sessions, hardware resources, blockers, and dependent verification remain sequential unless an authorized isolated workspace and verification boundary make both mutation and verification independent. Delegation never requires parallelism.
- After Core selects, qualifies, and hands off a ready owner, newly surfaced execution unknowns are classified fail-closed as `out-of-goal`, `owner-decision`, `fog`, `evidence-needed`, then canonical `executable`; the public compatibility label `ready-to-execute` maps only to `executable`. Every transient WorkerEnvelope names the WorkRef, lane, objective, current hypothesis when present, known evidence, allowed paths/actions/commands, prohibited actions, comparison baseline, exact result schema, and stop conditions. Token counts and limits are never dispatch, routing, authority, completion, or acceptance inputs. Diagnose and Inspect return only `confirmed-same-scope`, `unresolved-same-scope`, or `boundary-changed`; Fix returns `changed-same-scope`, `no-change`, or `boundary-changed`; Verify returns `pass`, `failed-with-new-evidence`, `failed-without-new-evidence`, `unavailable`, or `boundary-changed`, plus whether a distinct verifier identity was established. Optional evidence dispatch cannot consume capacity already required for the current Fix/Verify acceptance path, and a corrective retry starts only when decisive verification remains possible. Frontier state, envelopes, receipts, counts, and chronology remain transient; total worker dispatch is at most four, one evidenced corrective retry is permitted, and the separate managed review limit remains three Resolve Findings passes per Change.
- A managed routing result reports `selected` or `declined` with its decisive prospective signal or complete direct-work exclusion. Applicable dispatch also reports the overlap or isolation evidence for sequential or parallel execution. This observability is response-only and creates no controller state.
- Manage inspects the actual owned diff and decisive checks before acceptance. Ordinary same-goal receipts trigger internal rereading of status, owner, authority, diff, blockers, and decisive evidence; they do not repeat Core route selection. Manage continues a clear in-scope ready successor while owner topology, route, behavior, acceptance, interface, scope, and authority remain unchanged. Only a real owner, topology, requested-route, behavior, acceptance, interface, scope, mutation-authority, or external-action-authority boundary returns to Core.
- During a selected managed run, a progress or status inquiry is an evidence update and does not stop otherwise authorized work. Explicit pause confirms worker interruption, preserves the focused WorkRef, and forbids further mutation until resume; only explicit release or unfocus clears selection. Environment or verification blockers also preserve focus and return the complete response-only continuation. Resume rereads authority, status, focus, owned diff, blockers, and decisive evidence, invalidates stale claims, and revalidates the selected handoff before mutation or dispatch without repeating direct-versus-managed eligibility.
- Managed dispatch, retries, discovery classification, convergence counts, goal envelope, WorkSet, waves, checkpoint chronology, and push chronology stay transient. Changes retain converged evidence; Briefs retain shared completion without copied child state.
- Managed review convergence is bounded separately from worker retry. Resolve Findings remains one pass; Manage correlates each fixed-scope report and may start another pass only for an accepted finding within original behavior, paths, authority, and declared verification scope. Owner decisions, scope/authority change, failed evidence, extra external verification, or repeated non-convergence stop.
- Lifecycle closeout, recovery checkpoints, terminal local commits, and external delivery remain separate capabilities even when a project closeout preset combines some gates. Every `manage.closeout` preset is dormant unless Core selected and qualified Manage for the current continuation; declined, unavailable, or unselected Manage leaves ordinary Core advisory, and neither readiness nor prior managed selection activates policy. After that gate, `manual` grants neither automatic archive nor commit. `lifecycle` permits archive after durable review but no commit. `local` permits lifecycle closeout and separately justified recovery checkpoints; after lifecycle closeout it deterministically routes one clean exact terminal non-small Change or Group boundary with known ownership, fresh decisive verification, and no nearer denial exactly once to Commit. Terminal small work stays uncommitted, invalid boundaries stop without staging, and push remains separately authorized. Omitted policy resolves to `explicit` plus `local` for compatibility.
- Nearest restrictions and host enforcement may narrow configured closeout. No profile named `full` exists. Push remains opt-in only after explicit user mention plus an unambiguous remote, branch, and milestone; Manage never force-pushes or pushes protected/ambiguous branches. Publication, deployment, environment, approval, and human acceptance remain explicit and external.

## Boundaries
- In scope:
  - Skill selection, discipline behavior, artifact return paths, conditional references, managed qualification/convergence, and authority separation.
- Out of scope:
  - Host scheduling/worktree implementation, hidden runtime orchestration, automatic retry, persisted controller state, general host permissions, remote Git/publication authority, and project-specific product decisions.

## Constraints
- Keep safety, authority, readiness, verification, and completion criteria checkable even when compacting prompts.
- Prefer progressive disclosure and one semantic owner over duplicated eager rules.
- Keep agent-distributed normative prose in English for cross-agent stability.
- Retained evaluation evidence is immutable; prompt-content changes require a new identity and fresh run rather than overwriting prior results.
