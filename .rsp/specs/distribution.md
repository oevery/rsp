# Distribution and Maintainer Research

## Purpose
- Define package identity, published artifacts, Skill installation, release-candidate checks, repository layering, and upstream-research promotion boundaries.

## Stable Facts
- The npm package is `@oevery/rsp`, exposes the `rsp` binary, and accepts Node.js `>=22`.
- Published distribution contains the built `dist/cli.mjs` runtime, `rules/`, a portable default suite of twelve Skills, and the independently installable optional `rsp-structural-audit` project Skill. It contains no Broker daemon, SQLite runtime store, managed-runtime adapter, Web projector entry, or browser assets. Repository `.agents/` projections, `.codex/` host configuration, self-hosting `.rsp/` state, maintainer research, and host-specific prompts/metadata are not package runtime inputs.
- Published Skills use the portable intersection of Agent Skills and active target-client validation. They carry `license: MIT`, `metadata.author`, and independent quoted content CalVer versions that change for meaningful Skill-content releases rather than every CLI release.
- The source checkout dogfoods the published Skills through relative `.agents/skills/<name>` symlinks to canonical `skills/<name>` directories. Overlapping global workflow Skills are disabled in user configuration because project `.codex/config.toml` does not currently provide that disablement.
- `rsp skills install [--dry-run] [--force]` selects the fixed twelve-Skill default suite; `rsp skills install <name> [--dry-run] [--force]` selects only one exact bundled Skill. Unknown names fail before project-target mutation, and default installation never refreshes, replaces, or removes optional Skills.
- A packaged Skill may name another contract owner but must remain operable without repository-only `.rsp/` Specs or cross-Skill file loading. Exact-name installation creates no implicit Skill dependency graph.
- One presentation-neutral inventory classifies every validated bundled Skill by distribution kind as `default` or `optional` and its exact project target as `missing`, `unchanged`, or `divergent`. A target symlink is `unchanged` only when its resolved identity exactly matches that Skill's packaged source directory; every other symlink is `divergent`. Human `rsp skills list` output groups default suite and optional project Skills; `--json` keeps one flat inventory with explicit `kind` and does not expose runtime role or invocation mode. Both are non-mutating.
- Exact bare `rsp skills` opens the lazy interactive manager only on a dual TTY outside CI and `TERM=dumb`; all other Skills command paths remain static. The manager locks the default suite, starts optional Skills unselected, returns selection only after confirmation, separately confirms divergent replacement, and delegates one atomic write to the existing installer after terminal cleanup.
- Skill installation validates every bundled source before selecting targets, then preflights every selected package-owned destination before mutation. It rejects symlinked or unsupported entries, reports installed/unchanged/replaced/conflicting names, preserves unrelated Skills, treats identical trees as no-ops, and replaces divergent selected targets only with explicit `--force`.
- Installation creates no manifest, controller state, or second durable workflow truth. If rollback cannot fully restore originals, it reports and retains an exact recovery path.
- `pnpm test` owns deterministic code verification: it refreshes the CLI build exactly once, then runs source-level unit and contract tests plus isolated CLI integration files with ordinary bounded worker parallelism. Non-watch Vitest execution has no unconditional global build hook; the watch-only configuration rebuilds before the session and each rerun. Vitest discovers executable tests only under `test/`. Direct source tests mirror the stable `core`, `commands`, `cli`, `history`, `specs`, `status`, and `tui` owners, while cross-module and non-source contracts live under `integration`, `evaluation`, `skills`, `release`, `tooling`, and `architecture`; no executable test remains at the test root and no redundant `unit` layer is required. Small single-owner support fixtures may remain beside their owning test surface and are structurally excluded from collection. Reusable Skill and agent fixtures, unseen holdouts, beta plans, project-state pairs, and fake-provider inputs live under top-level `evaluation/`. Report-producing release project inputs live under top-level `acceptance/`. Neither data boundary is collected as repository Vitest tests.
- `release:acceptance` is the version-neutral Node.js acceptance runner. It dynamically discovers repository-owned manifests under `acceptance/projects/` and immutable sanitized or frozen inputs under `acceptance/fixtures/`, validates stable step and project coverage tags, directly invokes the repository's internal metadata and package checks plus the complete Vitest suite without file parallelism, and executes Skill security, bilingual documentation, build, types, and lint in serial fail-fast order. Deterministic Skill evaluation contracts in that Vitest suite may read `evaluation/`, but release acceptance never discovers those datasets as registered projects or triggers provider-backed evaluation. It writes one non-overwriting local JSON and Markdown report under `.cache/release-acceptance/`; `--plan` exposes the exact current steps, dynamic scenario count, coverage, anonymous fixture provenance, sanitization version, and fixture SHA-256 without executing checks. Test and scenario totals are observations rather than fixed gates. The clean-install package check drives the installed tarball through fresh initialization and Skill discovery, direct Specs inspection, a complete Change and Focus Capsule lifecycle, exact staged Commit behavior with unrelated dirty work, fail-closed unsupported configuration, and every registered isolated project scenario. Required project coverage includes fresh adoption, frozen published-version upgrade, complex existing RSP state, staged plus unstaged plus untracked Git work, nested monorepo files, and Unicode content. Every source fixture is copied to a temporary root, its declared project-owned files and Git state are preserved, and its registered source hash must remain unchanged. Ordinary development tests retain bounded worker parallelism; controlled concurrency remains inside tests that explicitly own that behavior. Package scripts expose only the three maintainer workflows `release:acceptance`, `release:provider-compare`, and `release:candidate-check`, plus the `prepublishOnly` lifecycle hook; internal checks are runner implementation details rather than additional release entry points. The repository-local `release-acceptance` maintainer Skill owns mode selection, evidence interpretation, and authority stops. `release:candidate-check` first requires a clean exact candidate identity and then invokes the version-neutral acceptance runner.
- A release candidate accepts `v${version}` only when absent or peeled to `HEAD`; a tag on another commit finalizes that version and requires a new package version. `prepublishOnly` uses the candidate check, while publication remains separately authorized.
- Retained evaluation evidence is immutable. Native-design evidence keeps the exact package, complete published-Skill fingerprint, and package inventory; current-checkout compatibility validates executed Skill/tree and behavior-file hashes, while other published-Skill drift stays diagnostic.
- Native Skill candidates begin with one demonstrated RSP gap and a concise capability delta. Draft validation covers portable structure, hard authority/mutation/truthfulness boundaries, and a small unseen real-task holdout; repeated provider matrices, cost calibration, and additional-host evidence are release-candidate gates. Evaluation considers task success, corrections, total tokens, elapsed time, and tool calls rather than input-token cost alone.
- Provider-backed release comparison runs outside deterministic acceptance and ordinary project acceptance. It is required only when compared Skill behavior changed or an explicit release evaluation needs old/new correctness or efficiency evidence. It binds one explicit prior `v*` release tag and the current candidate to exact Skill-composition hashes while sharing one current CLI, prompt, fixture, contract, model, effort, and evaluation harness. At least three baseline/candidate pairs run serially. The evaluation prompt supplies the exact complete receipt JSON shape and forbids identity wrappers or extra keys; the validator remains fail-closed. Every attempted comparison writes a non-overwriting sanitized report even when one provider arm throws before structured metadata is available, naming only the arm and bounded failure category. The report retains sanitized correctness dimensions, input/output/total-token medians, tool-call and elapsed-time medians, candidate deltas, and each arm's observed range; it retains no provider settings, sessions, prompts, raw errors, or workspace paths. Correctness, boundary, and task-result failures fail the comparison regardless of token reduction; missing usage, unavailable runs, incomplete pairs, or identity drift never pass. Token and latency deltas remain diagnostic until a separately calibrated threshold exists and grant no release or publication authority.
- Maintainer Skill evaluation summaries project Trigger, Compliance, Boundary, and task result as independent `passed`, `failed`, or `not-observed` dimensions. Corrections, first-fix result, worker dispatches, tool calls, elapsed time, and input/output/total tokens remain separate nullable measurements. Trigger, correction, first-fix, and worker-dispatch values require explicit structured harness receipt observations; missing evidence stays explicit and never becomes an inferred zero, success, routing observation, dispatch, or promotion verdict. Scenarios may declare composition-relative expected conditional references; retained observability then distinguishes expected, observed, unexpected, and missing resources. Observed resources derive only from successful supported host file-read events contained by declared installed Skills, while absent reliable host evidence remains unavailable rather than an inferred empty set; retained paths never expose absolute workspace locations or unrelated tool arguments.
- Deterministic catalog-routing evaluation derives the complete published Skill catalog from canonical `skills/*/SKILL.md` frontmatter and keeps versioned reusable cases under `evaluation/skill-routing/`. The initial focused corpus requires at least three realistic positive prompts and three hard-negative exclusions for each covered owner, plus pairwise expected/competing cases; description-collision checks cover the complete catalog at one explicit manifest threshold. This lexical gate runs under ordinary Vitest, emits bounded score diagnostics, and remains pre-provider regression evidence only: it does not prove host selection, semantic compliance, authority boundaries, or task success.
- The maintainer-only Skill candidate gate compares distinct immutable current and candidate identities on one to three explicitly unseen cases, each bound to one immutable acceptance-contract hash. Each current and candidate observation carries a validated composition identity, contract identity, receipt-content hash, and observability-content hash; mismatched identities, hashes, or receipt-derived values fail closed before behavior comparison. Every required Trigger, Compliance, Boundary, and task-result dimension must be observed and passing for candidate eligibility; a hard regression retains the current candidate, and incomplete evidence fails closed. Measurement deltas remain diagnostic without a pre-registered threshold, the command exits successfully only for `candidate-eligible`, and the gate grants no Skill mutation or publication authority. Its `managed-runs` adapter consumes two regular structured managed-run metadata files, reconstructs and validates their receipt and observability hashes, requires one shared case and acceptance contract, and writes one bounded manifest-plus-result comparison without retaining raw events, provider configuration, or workspace paths.
- The release-candidate Skill security preflight is deterministic and offline. It scans every bundled Skill in stable path order for unsafe file types or permissions, high-confidence embedded-secret signatures, executable egress/process/dynamic-code primitives, dependency manifests and install hooks, prompt-injection imperatives, and broad MCP metadata permissions. Findings are bounded and never reproduce suspected secret values. A reviewed exception must be repository-owned and bind one rule plus Skill-relative path to the exact file SHA-256 and a non-empty reason; malformed, duplicate, stale, or unused suppressions fail closed. Passing this static gate grants no behavior, installation, publication, provider, network, or vulnerability-freshness authority.
- The repository separates product runtime (`src/`, `bin/`), product distribution (`rules/`, `skills/`), host integration (`.agents/skills/`), maintainer tooling (`scripts/`), public guidance (`docs/site/`), repository records and maintainer knowledge (`docs/maintainers/`, `docs/migrations/`, `docs/releases/`, `research/`), deterministic code verification (`test/`), reusable Skill and agent evaluation data (`evaluation/`), report-producing sanitized release project inputs (`acceptance/`), self-hosting protocol (`.rsp/`), and transient/generated artifacts (`.cache/`, `dist/`, dependencies).
- `README.md` and `README.zh-CN.md` are concise distribution entry points. Detailed user guidance lives in matching `docs/site/en/` and `docs/site/zh-CN/` routes; VitePress uses `docs/site/` as its only source root and renders those tracked Markdown sources with localized navigation and local search. Repository-only maintainer, migration, and release records remain linked from the READMEs but are not generated or indexed by the site. `scripts/docs-check.mjs` enforces public page-pair integrity and internal-target integrity across the READMEs and all tracked Markdown under `docs/`. Generated documentation output is transient and is not a package runtime input.
- Product runtime does not import research, caches, host projections, self-hosting state, or maintainer-only scripts. Published rules and Skills operate without a source checkout or upstream cache.
- External Skill/workflow sources are declared in `upstreams.yaml` by repository, ref, tier, treatment, and required paths; ignored `.cache/upstreams/` holds prepared checkouts and `upstreams.lock` pins accepted revisions as a flat timestamp-free mapping.
- Preparation records fetched commits in dedicated candidate refs; checkout `HEAD` is not candidate authority. Only explicit maintainer `accept` updates the lock, and acceptance means the matching source distillation is complete.
- Mechanical preparation evidence is regenerable and ignored. Tracked source distillations and cross-source models live under `research/`; their recommendations reach product artifacts only through a normal selected RSP Change.
- Patch evidence is streamed and byte-hashed. Direct adaptation records license/reuse constraints. Status derives research state, required-path coverage, and next action from existing artifacts without another lifecycle state.
- Upstream registry values remain operational: `core` is the default review tier, `reference` is optional comparison material, and `conform`, `model`, `adapt`, and `tooling` route preparation and semantic review. Speculative policy stays in research until tooling consumes it.
- `scripts/upstreams.mjs` owns upstream manifest validation, cache lifecycle, candidate comparison, and atomic lock serialization; it is maintainer tooling, not published CLI behavior.
- `.agents/skills/distill-upstream/` is a maintainer capability, not a published product Skill.

## Boundaries
- In scope:
  - Package/runtime inventory, portable Skill packaging, installation, candidate validation, evaluation provenance, and maintainer upstream research.
- Out of scope:
  - Publication authority, automatic research promotion, executing cached upstream code, host-specific product commitments without a concrete consumer, and runtime dependency on repository-only state.

## Constraints
- Never run code from cached upstream repositories or overwrite a dirty managed cache.
- Every declared upstream path is required; a glob matching nothing fails preparation rather than broadening scope.
- Research and maintainer tooling may inspect product source but cannot mutate or enter product surfaces except through a selected reviewed Change.
- Cross-repository consistency takes priority over per-repository workflow freedom for published artifacts.
