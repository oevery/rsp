# RSP fallback protocol

This file is the minimal fallback protocol for agents that cannot load the `rsp` Skill. It is a compatibility and safety kernel, not a replacement for project instructions, installed Skills, or durable design documentation.

## Entry

- Read the nearest `AGENTS.md`, root `CONTEXT.md` when present, and relevant local `CONTEXT.md` before RSP work. CONTEXT owns vocabulary, domain relationships, and navigation. Check for a root legacy `CONTEXT-MAP.md`; when it or a relevant local map is found, use the context-migration branch below.
- Apply this fallback before operating `.rsp/` only after the Core Skill is absent or cannot be used.
- Treat `focus.d/` marker paths as the lightweight FocusSet of open executable work. A marker path identifies a current-work candidate; multiple markers are valid and do not create a second lifecycle or controller state. A marker may contain a short optional Markdown Focus Capsule with accepted recovery pointers, but its prose never selects work or grants authority, acceptance, lifecycle, Git, or worker coordination. A valid non-empty v1 capsule contains only one leading `<!-- rsp-focus:v1 -->`, blank lines, exactly one non-empty single-line `Current`, `Evidence`, and `Next`, and at most one non-empty single-line `Resume check`; unknown non-empty lines or fields are invalid. Legacy unversioned content is warning-only compatibility and makes no structured recovery claim. For grouped work, read the sibling Group Brief before the explicitly selected child Change. Then read only the relevant Specs and Decision Records under the configured authoritative path.
- If `focus.d/` is empty or has several candidates, use an explicit WorkRef, the user's mentioned Change, or current status/dependency evidence to resolve the default action. When a concrete request clearly identifies an open Change, the AI may create or switch its focus marker as a bounded RSP control-plane action. Do not infer product mutation, lifecycle, Git, or approval authority from automatic focus.

## Context migration (only when legacy context is found or migration is requested)

Read relevant legacy and current context before judging overlap. Without migration authority, preserve files and use relevant legacy context; report the pending migration without blocking unrelated work. A filename or an existing CONTEXT does not resolve conflicting definitions. Stop only dependent work for an unresolved meaning or authority decision.

With scoped authority, map useful terms, relationships, and navigation into root/local CONTEXT owners, preserve unrelated content, and update active references and entry instructions. Use Doc for substantial authorized writing when available. Retire the old map only after verifying preserved meaning and active links and confirming retirement authority. CLI update/doctor only detect the root legacy path and provide guidance; they do not merge semantics or delete context. Report the result and remaining limits without inventing migration state.

## Ownership

- `changes/` owns open work, `archives/` owns completed history, `specs/` owns current contracts, boundaries, and necessary constraints, and the configured Decision Record path owns lasting rationale and tradeoffs.
- A Change owns one executable outcome and its acceptance, Tasks, verification, and blockers. Executable WorkRefs are `<change>` or one direct `<group>/<change>` child. A Group Brief provides shared context but is not executable or focusable.
- For a new inferred WorkRef, preserve explicit valid user input first, otherwise follow an explicit nearest project or domain naming convention, otherwise use ASCII lowercase kebab-case from stable domain or technical vocabulary. Language or locale settings never select or translate WorkRef language. Valid Unicode remains available through explicit input or project/domain convention, and existing identities are never renamed by later guidance.
- Persist only `open` and `archived` lifecycle state. Readiness, blockers, routes, and acceptance remain derived from current artifacts and evidence. A Focus Capsule may project accepted current work, next action, evidence validity, and blockers for recovery without becoming lifecycle or controller state. Under `## Verify`, `### Required` owns acceptance-critical evidence and `### Optional` owns additional coverage; legacy unclassified items are Required. Incomplete Tasks, Required verification, or blockers fail the completion gate, while Optional omissions remain visible warnings.
- Project-owned `AGENTS.md` owns operating rules and checks; `CONTEXT.md` owns language, relationships, and navigation; README owns introduction and usage. RSP does not replace them. Classify by responsibility, not format: a design-reference table may be normative Spec content. Use summaries and links, not duplicate full definitions.
- Prefer RSP commands for deterministic setup, status, validation, repair, focus, Spec-index, history, archive, and reopen operations. Invalid identity, structure, dependency, managed path, symlink, or incomplete inspection fails closed.

## Authorized continuation

- Derive the authorized objective from user intent, authority, the selected WorkRef and Change/Group when tracked, relevant durable facts, worktree, and fresh status or verification. A bounded direct task needs no synthetic Change or WorkRef. Diagnose-only work is read-only and need not have a ready mutation owner.
- Continue one authorized objective through implementation, own proportionate checks and necessary writeback without a synthetic phase stop or another continue request. Mutation needs exact scope, settled acceptance and authority; a tracked implementation also needs a ready Change. Same-scope failure can be diagnosed and corrected while new evidence supports progress. Stop on non-convergence, repeated evidence, unavailable mandatory environment, changed owner/authority, or unsafe replay.
- The owning capability may change a permitted method while goal, scope, authoritative baseline, permissions and required evidence stay fixed. Diagnose tool-only faults and inspect actual effects before safe recovery; unknown mutation blocks replay. Named mandatory checks, immutable provenance, independent acceptance and command-owned RSP operations cannot be replaced by an easier result. Tool availability, status advice and exit codes grant neither authority nor semantic completion.
- Select the next responsibility before loading detail: Shape for authorized planning or read-only design; Implement for direct/tracked work, read-only diagnosis, risk-selected test-first, or fixed findings; Doc for repository-document, Skill and release writing; Verify for a separate read-only evidence pass; Review for fixed-scope read-only judgment, including release communication; Commit for exact local delivery. Ordinary own checks do not force Verify. A missing optional sibling permits only the same bounded safe action; it never supplies a required independent worker or reviewer.
- Doc handles authorized repository-document, Skill and release writing through conditional artifact methods. Small edits remain direct; read-only review stays Review. If Doc is unavailable, check reader purpose, facts, concise expression, ownership and references. Release communication additionally needs an evidenced range, confirmed identity or version-neutral draft, net delivered outcomes, required migration actions and explicit validation limits. Keep credentials out of retained output and artifacts; keep transient publication state outside shipped prose. Document checks grant no release-ready verdict or publication authority. Agreed writing requirements remain contracts; missing Skills grant no correction authority.
- Review fixes scope and authority, then selects Code checks for behavior/tool semantics and Document checks for explanation/usage within that content, not by file extension. Complete Skill instructions normally need both; comments, API guidance and examples receive proportionate applicable checks. Evidence-only reads never enlarge the target, examples grant no execution authority, and one text/behavior discrepancy yields one finding without assuming implementation is correct. Keep separate Code/Document results and one report; reference loading is not semantic acceptance.
- For a separate read-only pass over a WorkOwner-declared boundary, use `rsp-verify` when available. A Change uses its WorkRef and `Verify` boundary; a Group uses its reference and named `Integration:` condition. A request-only boundary must be written back before Group closeout. Verify owns only the evidence/result. Host observations, not self-report, establish required worker attribution and independence; absence keeps acceptance incomplete.
- For explicitly authorized release checks without a selected RSP WorkOwner, collect and interpret the project's declared checks at an exact candidate; a range is needed only when the checks require one. Require the check contract, baseline and authority for actual effects; stop dependent checks when these are missing. Do not invent a Change or pass an ownerless request to Verify. Preserve required independent acceptance; checks and Doc/Review results grant no Git delivery, publication or approval.
- Before later mutation or a different WorkRef, rederive authority and inspect dirty product and durable-truth paths. Continue the same owner, use an explicitly authorized reopen or integration owner, or stop for boundary resolution when ownership overlaps or remains uncertain.
- Multiple owners, incompatible resources, recovery, independent acceptance, or managed delivery need a qualified coordination branch in Core. This fallback does not simulate worker dispatch, concurrency, managed convergence, or closeout. If an actual required capability is unavailable, stop with the missing condition rather than inventing it. Before cross-session recovery refresh owner, authority, status/index, dirty paths, replay safety and decisive checks; cancelling a wait does not settle running work, and conflicting resources must be observed stopped before reuse.

## Durable routing

- Route planned future design to the selected Change; current contracts to the smallest authoritative Spec, terms/navigation to authorized CONTEXT, operating rules to authorized AGENTS, lasting rationale to the configured Decision Record path, and temporary continuation to the response. Resolve Spec/code discrepancies rather than automatically treating code as correct.
- Core maintains permitted recovery snapshots for tracked work needing continuity through `rsp focus <work-ref> --capsule-file <path|->`. Replace at meaningful checkpoints, pauses or handoffs, not every tool call. Use a selected child WorkRef for Group work; short direct tasks need no new Change or Capsule. Focus records progress, evidence status/pointers and next action, not logs, authority or acceptance; respect nearer mutation restrictions.
- Before archive, verify outcome facts, distill Focus and update knowledge as needed, then converge the entire Change before final consistency checks and authorized archive. These are dependencies, not new persisted phases or mandatory separate tool calls. No useful writeback means no edit; an authoritative contract left stale by delivered behavior requires correction. After writeback, reconcile all Change sections, retain the delivered delta, knowledge references, material failures, limits and evidence, and remove duplicated current specifications, stale operation permissions, session chronology and response-only handoff/readiness blocks. Substantive contradictions return to the decision, implementation or verification owner, not prose cleanup. Detailed records and original verdicts stay with their evidence owner. Earlier review or CLI readiness does not establish the final text's quality.
- Keep Change's six sections: Proposal owns intent/scope, Spec the delta/acceptance, Design the approach/tradeoffs, Tasks checkable work, Verify methods/results/limits, and Blockers unresolved dependencies/decisions. New domain Specs use Purpose, Boundaries, Contracts, Scenarios, and Constraints as guidance, not a required schema; specialized headings and omission of unnecessary scenarios are valid. Plain-prose HTML hints may stay or be removed, but never count as filled content or hide material requirements. Existing Specs and historical Changes are not rewritten for template conformity.
- Before authorized archive clears Focus, require converged Change evidence, completed or unnecessary stable-knowledge writeback, fresh applicable checks, required Review and readiness. Do not clear working notes instead of writing back; CLI success does not establish these semantic gates. Required verification must pass; Optional gaps remain explicit. Reclassifying Required evidence as Optional needs owner authority and fresh review/readiness. Change Spec deltas are never promoted automatically.
- Use the response language for user-visible narration while preserving exact WorkRefs, paths, commands, headings, and machine values. Preserve each existing artifact's established language unless translation is explicitly authorized.

## Safety ceiling

- This fallback does not emulate worker dispatch, managed convergence, execution-environment selection, or configured closeout. Configuration selects no capability and grants no planning, product-mutation, lifecycle, Git, publication, deployment, approval, or human-acceptance authority. The fallback never selects, prepares, or integrates an execution environment; the host, user, and Git own execution location and cross-branch integration.
- Do not create or repair command-owned RSP files directly. Do not create archives or restore archived content by editing files; use the owning RSP command only with explicit lifecycle authority.
- This fallback never archives, closes a Group, stages, commits, tags, pushes, publishes, deploys, deletes unrelated work, or records external approval. Those actions require their own explicit authority and available owning capability.
- Exact local delivery belongs to the default core rsp-commit capability, with checkpoint or terminal purpose independent from delivery kind. If unavailable, stop delivery without a manual fallback; an available CLI alone does not replace the owning Skill. Commit authority grants no archive, and checkpoints never claim completed acceptance.
- Do not claim completion or closeout with malformed or incomplete evidence, failed verification, unresolved ownership or decisions, or unavailable required capability. An authorized same-scope correction may continue when new diagnostic evidence supports progress; do not guess at a cause or mutate outside scope when the required environment is unavailable or failures do not converge. Multiple focus candidates alone are not an ambiguity: resolve one from explicit user intent and current status, or ask only when the requested mutation or delivery boundary remains materially ambiguous. State what was inspected, what is missing, who owns the next decision or action, and what evidence or authority permits resumption.
- Return an optional Core-owned response summary for the selected WorkOwner. A Change uses its WorkRef; a Group uses its Group reference and direct child Changes. Include `mode: solo | delegated | coordinated` and `status: running | waiting | completed` only when the response consumer needs them, along with the current outcome or stop reason, decisive evidence, changed artifacts when present, next owner/action, and optional recovery. State is presentation, not a persisted lifecycle state. Route, strategy, lane result, acceptance, and closeout remain nested details or gates rather than peer statuses. This response is not durable truth or a second state store. The fallback reports these semantics but does not emulate worker delegation, coordination selection, acceptance, or closeout.
