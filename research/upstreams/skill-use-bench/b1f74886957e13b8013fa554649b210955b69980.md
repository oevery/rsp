# Upstream Distillation: skill-use-bench

## Source Position

- **Evidence:** Skill-Use-Bench contains 79 real Skill rewrites, 177 executable tasks and trajectory rubrics across nine domains, plus Claude Code and Codex runners and scoring scripts (README.md, benchmark/**, evaluation/**).
- **Evidence:** It scores Trigger, Compliance, and Boundary separately and provides triggered-only variants, showing that invocation, procedure completion, and restraint are different observed capabilities (README.md, benchmark/_scripts/score_trace.py, benchmark/_scripts/score_matrix.py).
- **Inference:** This is the strongest reviewed model for challenging RSP's current tendency to aggregate task success and restraint into one result.

## Extracted Mechanisms

- **M1 — Progressive-disclosure trigger test:** the agent initially sees Skill name/description and must decide whether to load and use the full procedure (README.md, evaluation/docker/*entrypoint.sh).
- **M2 — Full-trajectory grading:** rubrics inspect tool calls and intermediate actions, not only the final answer (benchmark/*/rubrics/**, benchmark/_scripts/score_trace.py).
- **M3 — Three independent dimensions:** Trigger measures invocation; Compliance measures required actions; Boundary measures forbidden actions; triggered-only metrics separate routing failure from execution failure (README.md, benchmark/_scripts/score_matrix.py).
- **M4 — Harness is part of the result:** native progressive disclosure, preloaded instructions, and native Codex Skill installation are distinct run modes (evaluation/docker/**, evaluation/tasks/**).

## Applicable to RSP

- Report Trigger, Compliance, and Boundary independently for Skill candidates.
- Score required and forbidden trajectory events, not just final task success.
- Add triggered-only diagnostics so a routing failure is not misdiagnosed as instruction non-compliance.
- Treat model plus harness plus projection mode as the evaluated system.

## Rejected

- Importing the 79 rewritten benchmark Skills into the RSP capability catalog.
- Requiring Docker, paid APIs, or a broad model matrix for every maintainer edit.
- Using one LLM judge without deterministic checks or human review for high-impact boundaries.
- Claiming benchmark ranking proves general host compatibility.

## Recommendations

- **R1 — Adopt Trigger/Compliance/Boundary reporting (model-only).** Keep the three dimensions separately visible in RSP Skill evaluation.
- **R2 — Add trajectory rubrics for authority-sensitive Skills (independent-reimplementation).** Encode required reads/checks and forbidden mutations, Git, publication, or lifecycle actions.
- **R3 — Add triggered-only diagnostics (model-only).** Distinguish description/routing defects from Skill-body compliance defects.
- **R4 — Reserve broad host/model matrices for release candidates (model-only).** Routine candidate work uses deterministic checks and a small unseen real-task holdout.
- **R5 — Treat licensing as unresolved for reuse (model-only).** The reviewed tree has no root LICENSE even though README badges link to one; do not copy code or benchmark data until the discrepancy is resolved.
