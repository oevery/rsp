# Upstream Distillation: spec-kit

## Source Position
- **Evidence:** Spec Kit is an agent-neutral Spec-Driven Development toolkit whose default path is `constitution -> specify -> plan -> tasks -> implement`, with `clarify`, `checklist`, `analyze`, and `converge` as additional quality operations (`README.md`, `docs/reference/agentic-sdd.md`). Its value for this review is the domain model and artifact graph, not its CLI implementation or template content.
- **Evidence:** The source distinguishes three independent extension axes: presets change how existing commands and templates behave; extensions add capabilities; workflows orchestrate commands with persisted run state and human gates (`README.md`, `presets/README.md`, `workflows/README.md`). The bundled `lean` preset retains only five commands and one focused artifact per step (`presets/lean/README.md`, `presets/lean/preset.yml`).
- **Evidence:** Spec Kit explicitly leaves artifact persistence policy to each team and names flow-back, flow-forward, and living-spec models rather than enforcing one (`docs/concepts/spec-persistence.md`, `docs/guides/evolving-specs.md`).
- **Inference:** Spec Kit is therefore most useful to RSP as evidence that an engineering path can be explicit while its ceremony and automation remain layered. It is not evidence that RSP needs feature directories, a preset ecosystem, or a workflow engine.

## Extracted Mechanisms

### M1 — Artifact dependencies have named owners

- **Evidence:** `spec.md` owns technology-independent intent, prioritized user journeys, testable requirements, edge cases, assumptions, and measurable outcomes (`templates/spec-template.md`, `templates/commands/specify.md`).
- **Evidence:** `plan.md` owns technical context, architecture, project structure, and complexity justification. Its planning command derives separate research, data-model, contract, and quickstart artifacts before task generation (`templates/plan-template.md`, `templates/commands/plan.md`).
- **Evidence:** `tasks.md` is derived from specification and plan, organized by dependency and independently testable user-story slices, with exact target paths and parallel markers (`templates/tasks-template.md`, `templates/commands/tasks.md`). Implementation consumes these artifacts and mutates task completion state; convergence compares code to the artifact set and only appends missing work (`templates/commands/implement.md`, `templates/commands/converge.md`).
- **Inference:** The reusable mechanism is not the number of files. It is an explicit contract for each step: required inputs, one owner for each kind of decision, a produced output, a validation gate, and a next action.

### M2 — Durable constraints are checked before expensive derivation

- **Evidence:** The plan template places a Constitution Check before Phase 0 research and requires it to be rechecked after Phase 1 design; unjustified violations are errors and must be recorded in Complexity Tracking (`templates/plan-template.md`, `templates/commands/plan.md`). The project constitution treats governing principles as binding and requires amendments to propagate into dependent guidance (`.specify/memory/constitution.md`).
- **Inference:** This supports the previously discussed durable-decision gate: stable project constraints should be consulted before design and deliberately reviewed after implementation discoveries. It does not require a new lifecycle state or a second durable rules system.

### M3 — Quality gates are separable from the minimum path

- **Evidence:** The detailed agent path describes `clarify`, requirements checklists, read-only cross-artifact `analyze`, and post-implementation `converge`, but says only `specify` is strictly required before `plan` and recommends the extra gates for meaningful ambiguity (`docs/reference/agentic-sdd.md`).
- **Evidence:** `analyze` is explicitly non-destructive and returns problems to the artifact that owns them. `converge` leaves a complete task file byte-identical or appends traceable remaining work (`templates/commands/analyze.md`, `templates/commands/converge.md`).
- **Evidence:** The lean preset preserves `constitution -> spec -> plan -> tasks -> implement` with short prompts and one output artifact per step (`presets/lean/commands/speckit.constitution.md`, `presets/lean/commands/speckit.specify.md`, `presets/lean/commands/speckit.plan.md`, `presets/lean/commands/speckit.tasks.md`, `presets/lean/commands/speckit.implement.md`).
- **Inference:** A small deterministic protocol and richer optional engineering assistance can share one conceptual path without forcing every project through the richer path.

### M4 — Automation is an outer orchestration layer

- **Evidence:** Spec Kit workflows sequence commands, persist step/run state, resume after interruption, support conditional and repeated execution, and pause at explicit gates (`workflows/README.md`, `workflows/ARCHITECTURE.md`). The built-in full cycle has review gates after specification and planning before proceeding to tasks and implementation (`workflows/speckit/workflow.yml`).
- **Inference:** This supports an optional fully managed RSP mode that can autonomously implement, test, review, and continue until delivery while preserving approval points. It also shows why such run state belongs outside the core project protocol: it is orchestration state, not durable project truth.

### M5 — Current-work identity can be independent of Git and physical layout

- **Evidence:** The full specify command treats the feature directory name as independent from the Git branch and records the selected feature directory so downstream commands can resolve it (`templates/commands/specify.md`). The lean preset uses `.specify/feature.json` as an explicit handoff between commands (`presets/lean/commands/speckit.specify.md`, `presets/lean/commands/speckit.plan.md`).
- **Inference:** This supports the old path-abstraction concern at the mechanism level: downstream work should follow an explicit current-work handle, not infer it from branch names or directory scanning. It does not establish a need for a new `initiative` entity in RSP because `focus.d/` already provides the authoritative handle for a single-file change.

### M6 — Large work should be sliced at execution time before growing the model

- **Evidence:** For context-heavy features, Spec Kit first recommends limiting each implementation invocation to a task range or phase, then optional sub-agent delegation, and only then decomposition into multiple specifications (`docs/concepts/complex-features.md`).
- **Inference:** This favors a vertical-slice execution convention and bounded agent context over immediately adding hierarchy or multi-change aggregation to RSP.

## Applicable to RSP

### Current agreement

- **RSP fact:** `.rsp/rules/rsp-rules.md` and `.rsp/specs/design.md` already separate durable rules/specs from open work, make `focus.d/` the only current-focus source, keep one Markdown file per change, and use only `open -> archived`.
- **Supported by upstream:** Spec Kit's explicit input/output dependencies support making the RSP engineering path easier to discover. Its Constitution Check supports RSP's existing durable-update decision before archive. Its lean preset supports keeping a compact core while richer behavior remains optional.
- **Important correction:** Spec Kit's own persistence guide does not claim one universal artifact lifecycle. RSP can deliberately choose a flow-forward history (`changes -> archives`) plus selective durable writeback without copying Spec Kit's mutable feature artifact set.

### Concrete local gap: the file protocol is clearer than the engineering journey

- **RSP fact:** The current design precisely defines where rules, durable facts, open work, focus, and archives live, but it does not yet present one compact maintainer model from an incoming goal through clarification, change shaping, implementation, verification, durable review, and delivery.
- **Inference:** This makes external engineering skills harder to place. A future mechanism may be attractive yet have no explicit stage, owner, or optionality boundary, which risks letting imported skills reshape the core model.
- **Smallest correction:** Define an RSP-native engineering-path model whose nodes point to existing owners: user/agent conversation for clarification, one focused change for proposal/spec/design/tasks/verify/blockers, project code and tests for implementation truth, durable rules/specs for selected stable facts, and archive/Git for completed history. This is a conceptual routing model, not a new directory tree.

### Concrete local gap: progressive capability levels are implicit

- **RSP fact:** The repository already has deterministic CLI operations, a published RSP skill, maintainer research, and room for external engineering skills, but their relationship is not named as a product boundary.
- **Inference:** Spec Kit's core/lean, optional quality commands, and outer workflow orchestration support four RSP levels:
  1. **Protocol:** readable `.rsp/` files and deterministic commands.
  2. **Guided engineering:** the RSP skill helps shape and maintain one focused change.
  3. **Optional skill enhancement:** specialized clarification, modeling, diagnosis, testing, review, and issue flows attach to named engineering stages.
  4. **Managed delivery:** an opt-in controller repeats implementation and verification with explicit stop/approval gates.
- These levels should share existing RSP artifacts. Higher levels must not add core lifecycle states or make their transient run state durable project truth.

### Old-session proposals evaluated against evidence

- **Path abstraction — supported with limits:** explicit handoffs and ownership are valuable; branch or directory inference is fragile. RSP already has `focus.d/`, so the next step is documenting stage-to-owner routing, not adding a configurable path schema.
- **Initiative — not established:** Spec Kit decomposes only when bounded execution and delegation are insufficient. There is no current RSP gap proving a permanent parent artifact is needed. Cross-change coordination should remain outside the core until repeated local evidence demands it.
- **Durable decision gate — supported:** the Constitution Check and spec-persistence risks support reviewing stable constraints before design and carrying lasting rationale forward. RSP's archive readiness and durable-review guidance are the smaller native form and should remain advisory semantic judgment over a two-state filesystem model.
- **AGENTS/CONTEXT versus RSP ownership — supported:** Spec Kit separates agent integration/context from feature artifacts and governing memory (`src/specify_cli/integrations/**`, `.specify/memory/constitution.md`, feature artifacts under `specs/`). This is consistent with using `AGENTS.md`/`CONTEXT.md` for discoverability while RSP owns current work, durable facts, decision path, and archive history.

## Rejected
- **Copying the feature template tree:** `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, checklists, and `tasks.md` provide separation for Spec Kit's generator pipeline, but would contradict RSP's deliberate single-file change and add synchronization problems. Extract the dependency semantics, not the tree.
- **Making every phase mandatory:** Spec Kit itself keeps several gates optional and provides a lean preset. RSP should let tiny work remain untracked or use a lite change, and activate deeper clarification/modeling/testing only when risk warrants it.
- **Adding `initiative` or nested changes now:** the upstream recommends bounded runs and vertical slicing before decomposition. A new hierarchy would weaken `focus.d/` and the single-file invariant without a demonstrated coordination failure.
- **Adding configurable core paths or a path-resolution overlay:** RSP's fixed paths are a portability and determinism advantage. The useful abstraction is a stable logical owner and explicit focus, not user-configurable locations.
- **Importing presets, extensions, bundles, or catalogs:** these solve Spec Kit's distribution and customization goals and would move RSP toward the plugin/schema-heavy framework explicitly excluded by `.rsp/specs/design.md`.
- **Persisting autonomous run states inside `.rsp/`:** workflow `created/running/paused/failed/aborted/completed` states describe controller execution. They must not expand RSP's durable `open/archived` lifecycle or compete with `focus.d/`.
- **Treating specification as executable source:** RSP preserves human- and agent-readable project truth and implementation plans; it does not regenerate code as the only permitted consequence of editing a spec. Git, tests, and the codebase remain independent verification authorities.
- **Adopting Spec Kit's task defaults wholesale:** its template says tests are optional unless requested and encourages commits after tasks or logical groups (`templates/tasks-template.md`). RSP should continue to follow project-specific validation and explicit user authorization for commits.


## Recommendations
- **R1 — Model the RSP engineering path before adapting engineering skills (`model-only`).** In the requested cross-source synthesis, define stages for intake/clarification, durable-constraint read, change shaping, implementation slices, verification/review, durable-update decision, archive, and delivery. For each stage record required inputs, owning existing artifact, output, gate, next action, and whether it is core or optional. Preserve one focused single-file change throughout.
- **R2 — Make progressive capability a compatibility contract (`model-only`).** Require future Matt/Ponytail/Antfu recommendations to name which of the four levels they enhance and which existing RSP stage owns the result. A higher-level skill or managed workflow must remain removable without making the underlying `.rsp/` project unreadable or invalid.
- **R3 — Keep the durable-decision gate, but do not add state (`model-only`).** Clarify in future RSP skill/design work that durable constraints are read before design and durable writeback is reviewed before archive. Continue deriving readiness and guidance from current files; do not add `review`, `approved`, or `ratified` change states.
- **R4 — Treat autonomous delivery as an optional controller experiment (`independent-reimplementation`).** Prototype outside the core protocol a bounded loop of implement slice -> run project verification -> review against the focused change -> continue or stop. The experiment must keep transient run state outside `.rsp/`, stop on blockers or authority boundaries, and preserve explicit commit/delivery authorization.
- **R5 — Evaluate path clarity with one vertical slice before adding entities (`model-only`).** Run the same non-trivial change through the current RSP skill and record where an agent cannot determine the owner, prerequisite, or next action. Only a repeated inability to coordinate multiple focused changes should reopen an `initiative` proposal; naming preference alone is insufficient.
