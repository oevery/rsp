# Upstream Distillation: superpowers

## Source Position

- **Evidence:** superpowers provides a host-oriented engineering skill suite. This revision substantially restructures its subagent-driven-development loop around plan-scoped scratch workspaces, resumable review/fix rounds, scoped re-review, and a five-round breaker (`skills/subagent-driven-development/SKILL.md`, `skills/subagent-driven-development/re-review-prompt.md`, `skills/subagent-driven-development/scripts/sdd-workspace`).
- **Evidence:** RSP Manage already keeps controller process data transient, limits worker dispatches and corrective retries, requires diff and verification inspection before accepting results, and bounds review convergence (`skills/rsp-manage/SKILL.md`).
- **Inference:** The update is useful confirmation for bounded corrective loops and explicit residual-finding decisions. It does not establish that RSP should adopt a plan ledger, per-plan scratch directory, subagent self-commit, or model-tier escalation policy.

## Extracted Mechanisms

### M1 — Corrective review needs a finite breaker and a residual decision

- **Evidence:** The revised task loop introduces scoped re-review after a correction, caps the loop at five rounds, then adjudicates remaining findings and stops for human input when a remaining finding is load-bearing (`skills/subagent-driven-development/SKILL.md`, `skills/subagent-driven-development/re-review-prompt.md`).
- **Inference:** A correction loop is safer when it distinguishes “the finding is resolved,” “the finding needs owner judgment,” and “the finding may be explicitly parked” rather than repeatedly redispatching until context or budget ends.

### M2 — Recovery artifacts require a plan identity and isolated workspace

- **Evidence:** Each upstream plan receives a gitignored workspace and ledger keyed by the plan path; a mismatched or legacy ledger must not be reused, and recovery consults the ledger plus Git history (`skills/subagent-driven-development/SKILL.md`, `skills/subagent-driven-development/scripts/sdd-workspace`).
- **Inference:** If a controller stores operational recovery state, that state needs an explicit owner identity and isolation. This matches the root/identity lessons from planning-with-files, but remains outside RSP's durable work model.

### M3 — Review input should be scoped to the correction being judged

- **Evidence:** The revision uses a generated review package, task-specific briefs, and a dedicated re-review prompt so a reviewer receives the relevant task, base-to-head diff, and outstanding findings rather than a growing session transcript (`skills/subagent-driven-development/SKILL.md`, `skills/subagent-driven-development/scripts/review-package`, `skills/subagent-driven-development/re-review-prompt.md`).
- **Inference:** Fixed review scope and compact owner context reduce replay noise. RSP already requires a fixed comparison scope and bounded direct behavior chain for review; the mechanism is corroborating evidence, not a new owner.

## Applicable to RSP

- RSP already exceeds the core restraint in M1: it allows at most three Resolve Findings passes per Change, stops when the same finding remains after two completed corrections, and stops on a material scope, authority, or verification change (`skills/rsp-manage/SKILL.md`).
- M2 reinforces RSP's current prohibition on persisting a controller ledger or paused-state registry in Changes, Briefs, Specs, Decision Records, or `.rsp` lifecycle state. The only concrete conditional gap is a future host controller that needs run-local recovery storage.
- M3 agrees with current `rsp-review` behavior: compare a fixed scope, inspect only the smallest direct behavior chain, and reject findings that cannot establish production reachability or authority (`skills/rsp-review/SKILL.md`).
- No observed RSP task has shown that the present worker-retry or review-convergence limits are insufficient. This revision therefore produces constraints for a future controller experiment, not an immediate Skill change.

## Rejected

- **The plan-scoped workspace and ledger as default RSP artifacts:** these duplicate RSP's selected Change and would create a second execution state store.
- **Subagent self-commit as a normal loop step:** RSP deliberately retains Git ownership and commit authorization with the selected owner/controller.
- **Five fixed correction rounds and mandatory model-tier escalation:** the right cap and escalation policy are host-, cost-, and evidence-dependent. RSP's smaller current limits are intentionally conservative.
- **Parking unresolved findings merely to mark a task complete:** RSP must stop for unresolved load-bearing, authority, or verification issues; a transient parked note cannot substitute for a truthful blocker.
- **Copying superpowers scripts or prompts into RSP:** the reusable value is the bounded-loop constraint, not a portable implementation asset.

## Recommendations

- **R1 — Retain RSP's bounded corrective-review contract (`model-only`).** Keep the current retry and Resolve Findings limits, and require owner judgment or a blocker when the same meaningful finding survives the cap.
- **R2 — If an L3 host controller is proposed, isolate transient recovery state by explicit run and WorkRef (`independent-reimplementation`).** The state must remain outside RSP durable artifacts, have one writer, and never grant Git, lifecycle, or external authority.
- **R3 — Use scoped re-review as an evaluation property, not a copied workflow (`model-only`).** A future controller candidate should demonstrate that each retry is judged against its actual correction scope and original authority, including a repeated-finding stopper and a clean-case restraint test.
