# Upstream Distillation: deepseek-harness

## Source Position

- **Evidence:** DeepSeek Harness is a pre-release plugin-based agent harness whose current repository Skills include focused simplification and code-review disciplines, while repository rules separately define strict unit, coverage, real-API, snapshot, browser, and built-artifact verification surfaces (`AGENTS.md`, `.agents/skills/dsh-find-simplifications/SKILL.md`, `.agents/skills/dsh-code-review/SKILL.md`, `docs/testing.md`).
- **Evidence:** The candidate adds and updates product, testing, architecture, and simplification decisions, including a second SDK model-visible snapshot and an intentionally narrowed automation protocol (`.agents/notes/implemented/testing/2026-08-13-python-minimal-model-visible-snapshot.md`, `.agents/notes/implemented/simplification/2026-07-23-acp-automation-only-protocol.md`).
- **Inference:** Its strongest contribution to the current RSP gap is not the volume of its test matrix. It is the explicit classification of production consumers, trust boundaries, independent failure reasons, and tests that merely preserve speculative structure.

## Extracted Mechanisms

### M1 — A boundary needs an owner, a trust transition, and a reachable consumer

- **Evidence:** Repository rules trust statically typed same-process service and plugin calls and prohibit runtime validation, fallback behavior, or hostile-input tests solely for values required by the type. Validation remains mandatory at parser, configuration, queue, model/tool JSON, durable file, worker, process, and wire boundaries (`AGENTS.md`).
- **Evidence:** The simplification Skill asks reviewers to name where a value came from and who owns it next before retaining a copy, freeze, validator, or callback capture. Tests using hostile getters, fake typed objects, callback replacement, or post-handoff mutation are evidence of a potentially speculative contract rather than automatic justification (`.agents/skills/dsh-find-simplifications/SKILL.md`).
- **Inference:** RSP can turn the vague phrase `real boundary` into an evidence gate: current producer, current consumer, actual trust or lifecycle transition, and material consequence.

### M2 — Production-consumer classification precedes API and test retention

- **Evidence:** A strong simplification candidate includes a public method, event, config option, registry notification, helper, package, durable event, or test artifact with no production consumer; tests or docs as the only consumers do not make non-load-bearing behavior current product truth (`.agents/skills/dsh-find-simplifications/SKILL.md`).
- **Evidence:** The Skill separates production, non-production, and ambiguous corpora and requires reading call sites before accepting a deletion candidate. A production caller converts cleanup into a product decision; a test-only caller instead raises the question of whether the behavior should exist (`.agents/skills/dsh-find-simplifications/SKILL.md`).
- **Inference:** Test creation and API expansion should both start from the same live-path question instead of being justified independently after implementation.

### M3 — Tests must own an external consequence, not repeat the implementation

- **Evidence:** Code review requires assertions that fail on the intended regression and verify external state, logs, events, or disposal rather than restating the implementation or trusting an agent report. It treats coverage as necessary in this repository but not as evidence that a scenario is correct (`.agents/skills/dsh-code-review/SKILL.md`).
- **Evidence:** The testing policy prefers the real implementation and shipped entry path, mocks only expensive or nondeterministic boundaries, and externally re-reads files or reruns commands rather than accepting self-reported output (`docs/testing.md`).
- **Evidence:** The candidate Python snapshot exists because prior inline mock assertions could not observe the assembled model-visible surface. The new expected output owns that exact external projection while explicitly omitting platform-dependent and separately owned content (`.agents/notes/implemented/testing/2026-08-13-python-minimal-model-visible-snapshot.md`).
- **Inference:** A useful test can name both the externally observable consequence and the distinct failure reason it owns. A wrapper-send assertion or source-string assertion with no separate consequence is weak even when it raises coverage.

### M4 — Simplification preserves valuable coverage while deleting accidental surface

- **Evidence:** The ACP simplification removed editor UI, session browsing, selectors, and presentation branches from an automation transport but retained assembled snapshot scenarios that exercised backend behavior. Only tests driven exclusively through deleted UI methods were removed (`.agents/notes/implemented/simplification/2026-07-23-acp-automation-only-protocol.md`).
- **Inference:** Deleting an abstraction does not imply deleting every test near it. Coverage should move or remain with the behavior owner when the transport, wrapper, or presentation seam was incidental.

### M5 — Strict test policy is repository-specific evidence, not a universal default

- **Evidence:** DeepSeek Harness requires per-file 100% coverage, real-API tests, multiple snapshot suites, browser snapshots, real Loader or built-artifact entry paths, and expected-output updates for both SDK projections (`docs/testing.md`, `AGENTS.md`).
- **Evidence:** The same policy says an uncovered line is often dead code to delete, line coverage does not prove shipped behavior, local work should not default to the full suite, and CI owns exhaustive coverage and platform matrices (`docs/testing.md`, `AGENTS.md`).
- **Inference:** RSP should extract the selection logic and external-consequence standard without importing DeepSeek's repository-specific coverage percentage, snapshot obligations, provider economics, or package topology.

## Applicable to RSP

- `rsp-implement` currently asks for a `real boundary` and proportionate test cost but does not require the implementer to identify the producer, production consumer, trust transition, and material consequence before adding a validator, fallback, capability, state, or compatibility path. M1 closes that observed gap.
- `rsp-implement` and `rsp-tdd` judge test retention after a test exists. M2 supports a pre-mutation admission question: what live behavior and independent failure reason would this permanent test own, and why existing evidence cannot observe it.
- `rsp-review` already checks production reachability but does not explicitly classify tests/docs-only consumers as evidence that a changed public seam may be speculative. M2 and M3 support one bounded review check without adding another review pipeline.
- boats-cloud's sidebar-dismiss change is a suitable restraint negative: a typed event and real listener lifecycle are required, while a capability with no runtime policy owner and tests that only repeat shared-channel forwarding are suspect.
- boats-cloud's same-size window change is a necessary positive counterexample: one test owns user-visible no-flicker behavior and another owns suppression of native bounds writes, so fewer tests would reduce independent confidence.
- The current RSP candidate evaluation can express these as current-versus-candidate holdouts without importing DeepSeek's Agent Notes, snapshot catalog, or coverage gate.

## Rejected

- **Per-file 100% coverage as an RSP default:** coverage policy belongs to the host project and can itself create tests whose only purpose is executing lines.
- **A mandatory unit, e2e, snapshot, browser, and built-artifact matrix for each change:** DeepSeek has concrete product surfaces and CI economics for these tiers; RSP must select the smallest decisive evidence declared by the project and Change.
- **Every non-trivial change requiring a durable Agent Note:** RSP already owns planned work and lasting rationale through Changes, Specs, Decision Records, and archive decisions.
- **Broad simplification surveys as routine implementation:** repository-wide consumer classification belongs to an explicit audit or simplification request, not every bounded fix.
- **Deleting tests merely because their immediate wrapper disappears:** tests remain when they own still-current external behavior at another seam.
- **Treating DeepSeek's pre-release no-compatibility stance as portable:** compatibility authority remains product- and project-specific.


## Recommendations

- **R1 — Add a pre-mutation boundary evidence gate (`model-only`).** Before adding a validator, fallback, defensive copy, capability, state machine, compatibility path, or public option, require a current producer, production consumer, actual trust or lifecycle transition, and material consequence. Typed same-process values do not gain hostile-input handling without contradictory repository evidence.
- **R2 — Add a pre-retention test ownership gate (`independent-reimplementation`).** A permanent test names the observable consequence, one plausible regression in the owning production seam, why existing evidence misses it, and its maintenance cost. Tests or docs as sole consumers do not justify preserving otherwise unused behavior.
- **R3 — Add production-versus-non-production consumer classification to bounded review (`model-only`).** When a changed abstraction, API, event, capability, or compatibility branch appears generic, review its live consumers and flag test-only generality or implementation-mirroring verification only when removal has a concrete consequence.
- **R4 — Add paired restraint fixtures from independently rewritten real cases (`independent-reimplementation`).** One fixture must reject a fake boundary and hop-by-hop tests; one must retain two tests with distinct external consequences; one must reject source-string architecture assertions when lint, type, or behavior owners exist.
- **R5 — Preserve host-owned verification depth (`reject`).** Do not import DeepSeek's coverage percentage, universal snapshot rule, with-key economics, or full tier matrix into RSP. Fresh required verification remains mandatory, while test creation remains evidence-driven.
