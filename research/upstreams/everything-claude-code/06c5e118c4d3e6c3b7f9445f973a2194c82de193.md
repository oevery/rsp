# Upstream Distillation: everything-claude-code

## Source Position

- **Evidence:** ECC is a broad multi-host engineering Skill catalog. At this candidate revision its prepared diff changes only catalog presentation and a `nasiko-control-plane` capability; the implementation-restraint paths selected for this study are unchanged from the accepted base (`README.md`, `skills/nasiko-control-plane/SKILL.md`, prepared `diff.patch`).
- **Evidence:** Targeted current-revision inspection nevertheless confirms explicit TDD, eval, behavioral-compliance, and rule-distillation mechanisms in `skills/tdd-workflow/SKILL.md`, `skills/eval-harness/SKILL.md`, `skills/skill-comply/SKILL.md`, and `skills/rules-distill/SKILL.md`. ECC does not contain a directly applicable general code-simplification Skill in the selected source scope.
- **Inference:** ECC is useful here as a governance and adversarial-evaluation source, not as primary evidence for deciding whether a product boundary or test is valuable. DeepSeek Harness and the local friction cases supply that domain judgment.

## Extracted Mechanisms

### M1 — Behavioral compliance is tested independently of prompt cooperation

- **Evidence:** `skill-comply` derives an expected sequence, generates supportive, neutral, and competing prompts for the same task, captures tool-call traces, classifies semantic steps, and checks temporal ordering deterministically (`skills/skill-comply/SKILL.md`, `skills/skill-comply/prompts/scenario_generator.md`, `skills/skill-comply/fixtures/tdd_spec.yaml`).
- **Inference:** A restraint rule is not credible merely because an agent follows it when the prompt repeats it. Evaluation needs realistic prompts that omit the rule or pressure the agent to violate it.

### M2 — Rule promotion needs repeated evidence, deduplication, and a violation risk

- **Evidence:** `rules-distill` inventories deterministically, requires a principle to appear in at least two Skills, demands an actionable behavior and a concrete violation risk, checks semantic coverage in existing rules, merges duplicates across batches, and requires user approval before mutation (`skills/rules-distill/SKILL.md`).
- **Inference:** A single annoying implementation episode should first become a contrastive fixture or Skill-local behavior. It should become a cross-cutting RSP rule only after repeated independent evidence and an identified owner.

### M3 — Evaluation mixes deterministic, model, and human judgment

- **Evidence:** `eval-harness` separates code-based graders, model-based graders, and human review, prefers deterministic checks where possible, and recommends fast versioned evals with explicit capability and regression criteria (`skills/eval-harness/SKILL.md`).
- **Inference:** Boundary reachability and existing-consumer checks can be deterministic, while whether two tests own distinct regressions often needs a review rubric or human adjudication. One score cannot safely collapse both.

### M4 — TDD evidence mapping is useful when a concrete risk justifies TDD

- **Evidence:** `tdd-workflow` requires an observed RED caused by the intended missing behavior, the same target turning GREEN, and an evidence report mapping planned behavior to test target and observed results (`skills/tdd-workflow/SKILL.md`).
- **Inference:** This is strong evidence discipline for a selected test-first case. It does not prove that every implementation needs a new test or that the selected test owns a meaningful regression.

### M5 — ECC's universal test policy is an explicit overreach for RSP

- **Evidence:** The same TDD Skill activates for features, fixes, and refactors; mandates tests before all production code, 80%+ coverage, all edge cases, unit plus integration plus E2E coverage, checkpoint commits, and a durable TDD report (`skills/tdd-workflow/SKILL.md`).
- **Inference:** These requirements optimize process conformance rather than marginal confidence. Applied generally, they would recreate the observed failure: tests added to satisfy a matrix or sequence even when no independent production failure is exposed.

## Applicable to RSP

- Evaluate any future implementation-restraint behavior with the same task under supportive, neutral, and competing prompts. Include a prompt that asks for defensive handling of an unreachable typed state and one that asks to add tests for every touched file.
- Keep the candidate's deterministic gates narrow: identify production consumers, actual trust/lifecycle transitions, observable consequences, and duplicate test ownership before invoking model judgment.
- Use repeated friction plus violation risk as the admission gate for promoting a local lesson into shared `rsp-implement`, `rsp-tdd`, or `rsp-review` behavior. The current boats-cloud cases justify a candidate fixture set, not a new global rule file by themselves.
- Preserve RED/GREEN evidence only when TDD is selected by explicit policy or changed material risk. Ordinary implementation remains valid when an existing test, typecheck, lint rule, build, or focused behavior check owns the risk.
- Add a semantic test-value grader beside workflow-compliance evaluation: passing the expected sequence is insufficient if the test only mirrors a wrapper, source string, shared constant, or technical hop.

## Rejected

- **Universal TDD activation:** task type alone does not establish that a pre-mutation RED is the cheapest decisive evidence.
- **80%+ coverage and unit/integration/E2E as a default matrix:** host projects own coverage economics and verification tiers; quotas can reward low-value tests.
- **"All edge cases" as an acceptance criterion:** it is unbounded and encourages imagined states without a producer, reachable consumer, or material consequence.
- **Checkpoint commits and per-task TDD reports:** they exceed research and implementation authority and add durable artifacts without a demonstrated project need.
- **Compliance rate as test-quality proof:** `skill-comply` can show that an agent wrote and ran tests in the required order, but not that those tests protect independent behavior.
- **Whole-suite ECC adoption:** its overlapping lifecycle, host commands, hooks, runtime assumptions, and hundreds of domain Skills would create a second workflow overlay.


## Recommendations

- **R1 — Add prompt-independent restraint evaluation (`independent-reimplementation`).** Run the same small task under supportive, neutral, and competing prompts and retain full action traces so shortcut resistance is observable.
- **R2 — Gate shared-policy promotion on repeated evidence (`model-only`).** Require at least two independent occurrences, an actionable behavior, a concrete violation risk, semantic deduplication against current owners, and explicit approval before changing a shared Skill or rule.
- **R3 — Preserve RED/GREEN as conditional evidence (`model-only`).** Use it when policy or a concrete changed risk justifies test-first work; do not infer TDD from the mere existence of code mutation.
- **R4 — Grade test value separately from process compliance (`independent-reimplementation`).** A permanent test must own an observable consequence and distinct plausible regression; sequence, coverage, or file correspondence alone does not pass.
- **R5 — Reject ECC's universal coverage and test-matrix defaults (`reject`).** Keep verification project-owned, risk-proportionate, and bounded to the smallest decisive evidence.
