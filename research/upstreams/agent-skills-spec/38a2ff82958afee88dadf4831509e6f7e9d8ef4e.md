# Upstream Distillation: agent-skills-spec

## Source Position

- **Evidence:** `docs/specification.mdx` defines the portable Agent Skills directory and `SKILL.md` contract. It is a conformance source for RSP's published `skills/rsp/`, not a workflow to copy into RSP.
- **Evidence:** `skills-ref/README.md` describes `skills-ref` as a demonstration reference library and explicitly says it is not intended for production. Its behavior is useful as a pinned compatibility check, but the normative prose remains authoritative where the implementation is incomplete.
- **Evidence:** This initial review is pinned to revision `38a2ff82958afee88dadf4831509e6f7e9d8ef4e`; the prepared evidence covers 30 files and has evidence hash `sha256:b8b8fda74b5399e6a8ea9e6c229dcef1785cc66edc670b68f9e0c38f512bd5d9`.
- **Scope:** The concrete RSP target assessed here is the published `skills/rsp/SKILL.md`. The maintainer-only `.agents/skills/distill-upstream/` is not part of the npm artifact and is not used to claim published-skill conformance.

## Extracted Mechanisms

### Normative frontmatter contract

- **Evidence:** `docs/specification.mdx` requires YAML frontmatter followed by Markdown. Only `name` and `description` are required.
- **Evidence:** The allowed optional top-level fields are `license`, `compatibility`, `metadata`, and experimental `allowed-tools`. `skills-ref/src/skills_ref/validator.py` rejects any other top-level field through `ALLOWED_FIELDS`.
- **Evidence:** `name` is limited to 64 characters, must be lowercase alphanumeric plus hyphens, cannot start or end with a hyphen or contain consecutive hyphens, and must equal the parent directory name. `description` must be non-empty and no longer than 1024 characters.
- **Evidence:** `compatibility`, when present, must be a string no longer than 500 characters. It is intended for concise environment requirements and is unnecessary for most skills.
- **Evidence:** `metadata`, when present, is an arbitrary string-to-string mapping for client-specific properties. The specification recommends reasonably unique keys to reduce collisions.
- **Evidence:** `docs/specification.mdx` uses `metadata.author` and `metadata.version` as its explicit optional-field example. Therefore these two values are portable only when nested under `metadata`; top-level `author` or `version` would be invalid.
- **Evidence:** `skills-ref/src/skills_ref/parser.py` converts nested metadata keys and values to strings. `skills-ref/tests/test_parser.py` demonstrates that an unquoted YAML numeric-looking `version: 1.0` is exposed as the string `"1.0"`.
- **Evidence:** Neither `docs/specification.mdx` nor the reference models define ordering, comparison, release, timestamp, or compatibility semantics for `metadata.version`. It is an opaque client-specific string, not a standardized skill-version protocol.

### Runtime and validation implications

- **Evidence:** `docs/client-implementation/adding-skills-support.mdx` says the discovery catalog needs at minimum `name`, `description`, and location. Optional metadata is not required for routing or activation.
- **Evidence:** `docs/specification.mdx` recommends progressive disclosure: startup loads metadata, activation loads the complete `SKILL.md`, and referenced resources load on demand. It recommends fewer than 500 lines and 5,000 tokens for the main instructions; these are guidance, not frontmatter validity conditions.
- **Evidence:** `skills-ref/src/skills_ref/validator.py` mechanically checks allowed top-level fields, name, description, and compatibility. It does not fully enforce every documented nested metadata type constraint, so a passing reference-validator result is useful but not sufficient evidence of complete semantic conformance.

### Assessment of author and independent CalVer

- **Author:** Keep `metadata.author`. The upstream specification explicitly demonstrates this key, RSP has a concrete attribution value, and the value costs little. It is optional provenance, not routing input or an ownership/security guarantee.
- **Version:** The standard leaves `metadata.version` opaque, so RSP may define it as an independent skill-content version instead of coupling it to the CLI package release.
- **Selected RSP policy:** Use quoted CalVer (`YYYY.MM.DD`, with optional `.N` for multiple meaningful releases on one day). Update it only when the skill's behavior, instructions, resources, or contract change materially; do not bump it for CLI-only releases.
- **Identity boundary:** CalVer communicates human-facing content freshness. Git revisions and folder hashes remain the exact content and installation-update identity; do not replace them with the date.

## Rejected

- **Top-level `author` or `version`:** rejected because the validator permits only the six standard top-level fields; both values belong inside `metadata`.
- **Keeping `compatibility` solely because the standard permits it:** rejected for the current RSP artifact because an active target-client validator rejects the optional field and omission remains standards-conforming.
- **Binding the skill version to every RSP CLI release:** rejected because the independently useful skill can remain unchanged across CLI releases, producing meaningless metadata churn.
- **Updating CalVer on installation, build, formatting, or every edit:** rejected because those events do not necessarily represent a meaningful skill-content release and exact identity already belongs to Git or folder hashes.
- **Treating the reference validator as a production dependency:** rejected because its own README limits it to demonstration use. RSP can use the pinned implementation as a research/checking oracle while keeping a small local conformance test for its shipped artifact.
- **Copying the upstream client discovery and activation lifecycle into RSP:** rejected because RSP publishes a skill but does not implement an agent client; no local product gap requires that machinery.
- **Expanding the skill merely to repeat the specification:** rejected because the standard recommends progressive disclosure and a validator or concise release check is a stronger, smaller conformance mechanism.


## Recommendations

- **R1 — Remove the non-portable compatibility field.** Omit `compatibility` from `skills/rsp/SKILL.md`: the official standard makes it optional, and omission also satisfies the active OpenAI skill validator. Preserve execution requirements in the skill body, package metadata, and commands instead of duplicating them in frontmatter. Owning target: `skills/rsp/SKILL.md`.
- **R2 — Keep author and version the skill independently.** Retain `metadata.author: oevery`; define `metadata.version` as quoted content CalVer (`YYYY.MM.DD` or `YYYY.MM.DD.N`) and update it only for meaningful skill-content releases. Do not require equality with `package.json`; keep exact update identity in Git or folder hashes. Owning targets: `skills/rsp/SKILL.md` and the existing skill contract test.
- **R3 — Add a minimal conformance gate without adopting the reference package.** Extend RSP's local tests to parse the published skill and assert the portable top-level keys, scalar metadata values, name-directory match, length limits, and local CalVer format. The pinned `skills-ref` command may remain an optional cross-check rather than a runtime or npm dependency. Owning target: the existing skill contract tests.
- **R4 — Carry standalone reuse terms explicitly.** Add top-level `license: MIT` so a copied skill retains its reuse terms independently of npm metadata. Owning target: `skills/rsp/SKILL.md`.
