# Upstream Distillation: anthropic-managed-agents

## Source Position
- **Evidence:** Managed Agents separates reusable agent configuration, environments, sessions, event streams, session threads, multi-agent rosters, outcomes, and client-side orchestration (`skills/claude-api/shared/managed-agents-overview.md`, `managed-agents-core.md`, `managed-agents-environments.md`, `managed-agents-multiagent.md`).
- **Evidence:** Client patterns distinguish queued from processed events, interrupt request from eventual idle, transient idle from terminal idle, and terminal observation from later cleanup readiness (`skills/claude-api/shared/managed-agents-events.md`, `managed-agents-client-patterns.md`).
- **Inference:** This is strong interface evidence for a thin host port and observer-authored lifecycle facts, not authority to reproduce Anthropic's hosted runtime.

## Extracted Mechanisms
- **M1 — Stable interfaces isolate the harness.** Agent, environment, session, event, thread, and outcome APIs expose bounded responsibilities while implementation remains service-owned.
- **M2 — Enqueue and processing are separate observations.** Client-sent events can first appear queued and later processed; some event types acknowledge immediately (`managed-agents-client-patterns.md`).
- **M3 — Liveness and completion need stop-reason interpretation.** Idle may mean requires-action, end-turn, retries exhausted, or budget reached; clients must not collapse them.
- **M4 — Cleanup is a later boundary.** A stream may emit idle before queryable state permits archive, so clients reconcile status before release.
- **M5 — Multi-agent threads share a filesystem but not ambient conversation or tools.** Delegated context must be sent explicitly and nested roster depth is bounded (`managed-agents-multiagent.md`).

## Applicable to RSP
- Define a host-neutral worker capability projection rather than canonicalizing Codex, Claude, or another host's statuses and handles.
- Keep creation, Assignment admission, active liveness, cancellation acknowledgement, settlement, and release as distinct observations.
- Close or release a completed WorkerSession when no explicit compatible longitudinal successor remains and the host requires cleanup.
- Keep execution location and sandbox evidence separate from worker identity and product authority.

## Rejected
- Hosted session/event stores, server budgets, environment templates, webhook registries, thread rosters, outcome graders, and Files API artifacts as RSP state.
- Provider-specific statuses, event names, polling delays, thread ids, roster depth, or cleanup APIs in portable Skills.
- Treating idle, completed output, or a service-side outcome grade as RSP acceptance.


## Recommendations
- **R1 — Define a thin host observation port (`model-only`).** Hosts project create, admit, interrupt, settle, identity, isolation, and release facts into Manage without becoming RSP vocabulary.
- **R2 — Separate settlement from release (`independent-reimplementation`).** Reconcile host cleanup and outstanding owned work before releasing conflicting resources.
- **R3 — Keep host assumptions conditional (`model-only`).** Load host mapping only when dispatch occurs and never infer capabilities from a worker handle.
- **R4 — Reject hosted runtime entities as RSP artifacts (`reject`).** Preserve repository-native, one-shot workflow state.
