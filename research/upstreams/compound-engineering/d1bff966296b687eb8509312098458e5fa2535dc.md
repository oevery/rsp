# Upstream Distillation: compound-engineering

## Source Position

- **Evidence:** Compound Engineering is a broad plugin suite spanning ideation, planning, implementation, review, debugging, verification, Git/PR work, and knowledge compounding (`README.md`, `skills/**`, `docs/skills/README.md`).
- **Evidence:** The repository supports many agent harnesses and documents a beta-to-stable lifecycle, naming rules, cross-skill orchestration contracts, and behavior/testing lessons (`docs/solutions/skill-design/**`, `tests/**`).
- **Inference:** It is useful for capability lifecycle and composition patterns, but its product breadth and plugin conventions should not become the RSP core model.

## Extracted Mechanisms

### M1 — Capability lifecycle is explicit

- **Evidence:** Beta skills use a registry and promotion cleanup that updates discoverability, documentation, and orchestration wiring rather than only moving a directory (`docs/solutions/skill-design/beta-skills-framework.md`, `beta-promotion-cleanup-registry-wiring.md`).
- **Inference:** RSP candidates should remain research/evaluation assets until behavior, discoverability, packaging, and ownership gates all pass.

### M2 — Orchestration contracts name inputs and returned artifacts

- **Evidence:** Promotion guidance separates reusable capability behavior from orchestration and requires callers to pass the necessary artifacts (`docs/solutions/skill-design/beta-promotion-orchestration-contract.md`, `skills/ce-work/SKILL.md`, `skills/lfg/SKILL.md`).
- **Inference:** RSP composition should be typed by artifact ownership: a skill reads existing authorities and returns findings or proposed updates to named owners.

### M3 — Multi-pass review can specialize without merging authority

- **Evidence:** `ce-code-review` coordinates specialized review passes and aggregates findings, while documented lessons address confidence calibration and final fix/re-review dispatch (`skills/ce-code-review/SKILL.md`, `docs/solutions/skill-design/confidence-anchored-scoring.md`).
- **Inference:** Parallel reviewers may improve recall, but RSP needs one normalized finding contract and a bounded final synthesis to control duplicate context and fixes.

### M4 — Cross-host behavior needs execution tests

- **Evidence:** The repository documents harness/model differences in tool invocation and contains fake-CLI and cross-harness tests (`docs/solutions/skill-design/cross-harness-cross-model-tool-invocation.md`, `tests/**`).
- **Inference:** Schema compatibility alone does not prove a skill works on a host; RSP should maintain a small host matrix for published capabilities.

### M5 — Code and document review have different semantic contracts

- **Evidence:** `ce-code-review` fixes a Git/PR diff, selects correctness plus risk-driven code lenses, anchors findings to changed lines, and defaults to report-only (`skills/ce-code-review/SKILL.md`, `skills/ce-code-review/references/diff-scope.md`, `skills/ce-code-review/references/review-output-template.md`).
- **Evidence:** `ce-doc-review` first classifies requirements versus implementation plans by content shape, then applies coherence and feasibility plus conditional product, design, security, scope, and adversarial lenses to the whole authoritative document (`skills/ce-doc-review/SKILL.md`, `skills/ce-doc-review/references/synthesis-and-presentation.md`).
- **Inference:** RSP should share scope resolution, authority, read-only behavior, and finding normalization while keeping separate code and document pipelines. A mixed Change can execute both pipelines and synthesize one report without pretending their quality axes are identical.

## Applicable to RSP

- Add candidate, experimental, and stable lifecycle gates without exposing candidates to normal discovery.
- Declare each skill's required inputs, allowed mutations, output contract, stop conditions, and owning next stage.
- Normalize review findings before applying fixes; re-review only the changed finding set plus a final bounded whole-diff pass.
- Partition mixed changes by review object. Code review owns executable behavior and regressions; document review owns coherence, traceability, feasibility, scope, and ambiguity. Agent instructions and workflow Markdown are executable documents and need code-contract treatment first.
- Use a namespace only where ecosystem collision risk is real; avoid verbose prefixes in user-facing prose.

## Rejected

- Importing the whole ideate-to-PR suite or its command aliases.
- Making a “launch everything” orchestrator the default entry to RSP.
- Unbounded multi-agent review or one fixer per finding; both multiply context and verification cost.
- Equating registry presence or documentation completion with behavioral readiness.
- Automatic commit, push, PR, or babysitting without explicit user/project authority.
- Auto-applying supposedly safe document edits: semantic requirements, plans, and decisions often need owner judgment even when prose changes look mechanical.

## Recommendations

- **R1 — Define a candidate-to-stable promotion gate (`independent-reimplementation`).** Require behavior fixtures, restraint negatives, host validation, context budget, provenance, docs, and ownership.
- **R2 — Give every capability an explicit composition contract (`model-only`).** Inputs, outputs, mutations, stop/escalation, and returned owner must be visible.
- **R3 — Evaluate bounded specialist review (`adapt`).** Compare persona specialization with one artifact-partitioned RSP review capability on recall, duplicates, false positives, context, and fix cost.
- **R4 — Keep autonomous orchestration optional and outside the core skill suite (`model-only`).** It may compose stable skills but must not own RSP truth.
- **R5 — Separate code and document review pipelines inside one bounded RSP review capability (`independent-reimplementation`).** Share scope, authority, read-only mutation policy, and normalized findings; give each artifact kind its own axes and run both for mixed Changes.
