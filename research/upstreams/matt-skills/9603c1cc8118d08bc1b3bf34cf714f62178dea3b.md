# Upstream Distillation: matt-skills

## Source Position

- **Evidence:** Matt skills presents a collection of small, adaptable, composable engineering skills as an alternative to systems that own the whole development process. It offers either editable project copies or a managed read-only Claude plugin (`README.md`).
- **Evidence:** The repository separates user-invoked orchestration from model-invoked discipline. A user-invoked skill may call model-invoked skills, but not another user-invoked skill; `ask-matt` documents a main path and bounded on-ramps (`README.md`, `skills/engineering/ask-matt/SKILL.md`).
- **Evidence:** The repository contains canonical skills, capability-local resources, repository setup, general docs, scripts, plugin metadata, ADRs, changesets, deprecated and in-progress work, and explicit out-of-scope decisions. The repository tree is therefore a product-development workspace, not one installable capability package (`.agents/**`, `.claude-plugin/**`, `.changeset/**`, `.out-of-scope/**`, `docs/**`, `scripts/**`, `skills/**`).
- **Inference:** Matt is useful to RSP as an `adapt` source for capability boundaries, engineering-stage behavior, review, slicing, research, and handoff. It is not evidence that RSP should install the entire suite, copy its directory tree, or adopt its main flow as a second project protocol.

## Extracted Mechanisms

### M1 — Invocation class separates routing from reusable discipline

- **Evidence:** `ask-matt` is an explicitly user-invoked router. It selects a path but delegates actual discipline to skills such as TDD, diagnosis, research, domain modeling, code design, and code review (`skills/engineering/ask-matt/SKILL.md`, `README.md`).
- **Evidence:** The documented main path is conditional rather than universal: clarify, optionally prototype, choose same-session or multi-session shaping, implement bounded work, then review (`skills/engineering/ask-matt/SKILL.md`).
- **Inference:** RSP can distinguish navigation capabilities from stage capabilities. A router should derive a next action from the focused Change and current evidence; it should not persist a second flow state or preload every skill.

### M2 — Work is sliced as tracer bullets with explicit blocking edges

- **Evidence:** `to-tickets` requests end-to-end, demonstrable vertical slices, declares blocking relationships, and works the dependency frontier rather than grouping tickets by technical layer (`skills/engineering/to-tickets/SKILL.md`).
- **Evidence:** The upstream permits an expand-contract exception for wide refactors and can target either local issue files or an external tracker (`skills/engineering/to-tickets/SKILL.md`).
- **Inference:** Tracer-bullet slicing strengthens RSP's `Slice` and `Next Action` concepts. The useful adaptation is the slicing test and blocking-edge reasoning, not mandatory ticket generation or a new issue hierarchy under `.rsp/`.

### M3 — Implementation is a bounded loop with explicit verification seams

- **Evidence:** `implement` works from an agreed spec or ticket, identifies testable seams, delegates test-first work, tracks blockers, and closes with review before asking about commit (`skills/engineering/implement/SKILL.md`).
- **Inference:** This aligns with the RSP journey's recursive `implement slice -> verify -> review` loop, provided the focused Change remains the owner and Git mutations retain user/project authorization.

### M4 — Review preserves two independent axes

- **Evidence:** `code-review` pins a fixed comparison point, then reviews Standards and Spec independently. Findings remain separated rather than being merged or re-ranked, and a missing specification is reported rather than invented (`skills/engineering/code-review/SKILL.md`).
- **Inference:** Separating conformance from intent fidelity prevents one dimension from masking the other. This is the strongest near-term candidate for an RSP-aware capability because both axes can return findings to existing owners without adding state.

### M5 — Research delegates legwork but retains synthesis responsibility

- **Evidence:** `research` assigns background investigation against primary sources and requires a cited Markdown artifact; it explicitly delegates evidence collection rather than the caller's judgment (`skills/engineering/research/SKILL.md`).
- **Inference:** This validates RSP Maintainer Research's separation of prepared evidence, source Distillation, and cross-source synthesis. Parallelism should never bypass provenance or silently promote findings into product truth.

### M6 — Handoffs reference settled artifacts instead of duplicating them

- **Evidence:** `handoff` writes a compact temporary continuation artifact, links to authoritative specs/issues/files, records current state and next actions, and excludes secrets (`skills/productivity/handoff/SKILL.md`).
- **Inference:** A recovery mechanism should preserve pointers, evidence, and unresolved state rather than copying durable RSP content into another authority.

### M7 — Distribution mode is an explicit maintenance tradeoff

- **Evidence:** The editable installation copies skills so teams can modify them; the plugin supplies a managed, read-only, automatically updated bundle (`README.md`, `.agents/adr/0002-ship-as-a-claude-code-plugin.md`).
- **Inference:** RSP should choose per capability between owned adaptation and subscribed upstream behavior. Because RSP requires deterministic constraints and upstream-specific modifications, an accepted Matt-derived capability should be a small locally owned adaptation with pinned provenance, not a runtime overlay of the whole suite.

## Applicable to RSP

### Preserved behavior

- Map every capability to one RSP journey stage and declare whether it is navigation/orchestration or reusable discipline.
- Prefer vertical, demonstrable slices and make blocking dependencies explicit when work genuinely needs decomposition.
- Keep Standards review and Spec review independent, tied to a fixed diff base, and report missing authority instead of fabricating it.
- Use primary sources for research and retain citations through Distillation and synthesis.
- Make handoffs compact references to authoritative artifacts, with current evidence, blockers, risks, and next action.

### Required local modifications

- The Selected Change, not a generated PRD/ticket chain, remains the default owner of proposal, spec, design, tasks, verification, and blockers.
- Routing derives from current RSP artifacts and loads only the selected skill. It does not impose Matt's entire `idea -> ship` flow or require a setup skill.
- External issue trackers are optional execution surfaces for work that truly needs independent assignment; they do not replace `focus.d/` or the Change lifecycle.
- Review must follow project-local rules, validation commands, and explicit Git authorization. “Before committing” is a gate, not permission to commit.
- `AGENTS.md` and `CONTEXT.md` remain external discovery/context surfaces. Matt's repository setup and docs layout are not imported into `.rsp/`.
- Any derived skill must carry provenance to this report, recommendation ID, exact source paths, and base revision, then use a three-way comparison for future upstream updates.

## Rejected

- **Wholesale suite installation or repository-tree copying:** it would couple RSP to unrelated skills, setup, documentation, release, plugin, and historical surfaces and raise context and update costs.
- **A runtime router overlay over all upstream skills:** always-visible routing and overlapping triggers would make RSP behavior less deterministic. Load a capability after stage selection instead.
- **Replacing one Change with PRD -> tickets -> issue tracker as the mandatory path:** this creates a second current-work authority and weakens the single-file protocol for small and medium work.
- **Treating `CONTEXT.md` or setup-generated docs as RSP-owned durable truth:** discovery and domain context may remain adjacent, but RSP owns its rules, specs, changes, focus, and archives only.
- **Automatic commit after implementation/review:** upstream sequencing cannot grant Git authority.
- **Copying source prose without behavioral adaptation:** local constraints, trigger behavior, outputs, restraint, and context cost matter more than textual similarity.
- **Adopting plugin subscription for modified deterministic behavior:** automatic upstream updates would bypass the pinned-review and three-way adaptation boundary.

## Recommendations

- **R1 — Evaluate a two-axis RSP review capability (`adapt`).** Preserve fixed-point comparison, independent Standards and Spec passes, and missing-spec restraint. Modify it to read the Selected Change and project instructions, return findings to `Tasks`/`Verify`/`Blockers`, and never infer commit authority. Compare current RSP review with the candidate on seeded standards defects, seeded spec omissions, a missing-spec case, a clean diff restraint negative, and token/context cost.
- **R2 — Add tracer-bullet slicing to the engineering rubric (`model-only`).** Test whether one non-trivial Change can be divided into independently verifiable slices with explicit blockers while remaining one Change. Only adapt ticket output if repeated execution shows that Change-local tasks cannot support parallel ownership.
- **R3 — Keep routing as compact derived guidance (`independent-reimplementation`).** If navigation remains unclear after the journey model is exercised, expose the current stage, recommended optional capability, required input, and returned owner. Do not install an always-on router or enumerate every upstream skill in runtime context.
- **R4 — Reuse the implementation loop only through an L3 experiment (`model-only`).** A future controller may repeat bounded implementation, project verification, and two-axis review, but controller state stays ignored outside `.rsp/` and all stop, escalation, and authority gates remain explicit.
- **R5 — Treat Matt's directory structure as packaging evidence, not a template (`model-only`).** Every future adapted skill must include only its instructions and owned resources, with repo maintenance scripts and research remaining in their current owners.
