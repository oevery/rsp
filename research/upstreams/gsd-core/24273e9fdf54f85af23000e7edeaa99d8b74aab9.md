# Upstream Distillation: gsd-core

## Source Position

- **Evidence:** GSD Core is a multi-runtime, spec-driven orchestration system built around Discuss → Plan → Execute → Verify → Ship and fresh-context specialized agents (`README.md`, `docs/explanation/context-engineering.md`, `docs/explanation/the-phase-loop.md`).
- **Evidence:** It persists extensive project and orchestration state under `.planning/`, generates runtime-specific assets, and maintains many agents, commands, workflows, adapters, and ADRs (`docs/ARCHITECTURE.md`, `src/**`, `agents/**`, `commands/**`).
- **Inference:** It is useful as a model for optional high-autonomy delivery and context budgeting, not as the baseline RSP protocol or initial skill suite.

## Extracted Mechanisms

### M1 — Fresh contexts are scoped by durable artifacts

- **Evidence:** Heavy work runs in bounded subagents that receive selected project, decision, research, and plan artifacts; durable files bridge session boundaries (`docs/explanation/context-engineering.md`).
- **Inference:** Context isolation works only when inputs and returned artifacts are explicit; spawning agents alone does not prevent drift.

### M2 — Work size selects ceremony

- **Evidence:** The full phase loop is recommended for complex work, while quick/fast paths exist for tasks that fit a short prompt and one turn (`docs/explanation/context-engineering.md`, `docs/explanation/the-phase-loop.md`).
- **Inference:** RSP's progressive levels should select capability depth from work risk/size without changing the underlying Change authority.

### M3 — Orchestration and capabilities can be separated

- **Evidence:** ADRs describe an embeddable orchestration engine, capability ecosystem, descriptor-driven conversion, and skill mapping across runtimes (`docs/adr/1239-gsd-embeddable-orchestration-engine.md`, `docs/adr/1244-capability-ecosystem.md`, `docs/adr/1593-skill-mapping-converter-methodology.md`).
- **Inference:** A future RSP controller should depend on stable skill contracts and host adapters rather than being fused into each skill.

### M4 — Context is an explicit budget

- **Evidence:** GSD uses fresh agents, compact payloads, effort hints, lifecycle signals, and an agent-size budget ratchet while documenting latency and maintenance costs (`docs/explanation/context-engineering.md`, `docs/adr/1610-workflow-agent-size-budget-ratchet.md`).
- **Inference:** RSP needs measurable context budgets and stop/fallback behavior, not claims of unlimited autonomy.

### M5 — Review categories are most useful as an artifact taxonomy

- **Evidence:** GSD exposes separate plan peer review, source-code review, UI audit, evaluation-coverage audit, security/validation routes, and a namespace router (`skills/gsd-review/SKILL.md`, `skills/gsd-code-review/SKILL.md`, `skills/gsd-ui-review/SKILL.md`, `skills/gsd-eval-review/SKILL.md`, `skills/gsd-ns-review/SKILL.md`).
- **Evidence:** Code review requires an explicit or derived file scope, distinguishes `skipped` from `clean`, and offers quick/standard/deep depth levels (`gsd-core/workflows/code-review.md`, `agents/gsd-code-reviewer.md`).
- **Inference:** The useful RSP lesson is to classify the review object, preserve exact scope, and distinguish “nothing reviewed” from “reviewed with no findings.” The GSD prompt contents and workflow graph are too coupled and uneven to adapt into the first RSP reviewer.

## Applicable to RSP

- Make optional managed delivery consume the focused Change, selected Specs, project rules, and explicit verification criteria.
- Keep orchestration state transient/ignored; return durable decisions and results to existing RSP owners.
- Select direct, assisted, or managed execution based on task complexity and user choice.
- Set size/context budgets for each published skill and adapter.
- Preserve review-object and scope vocabulary so future code, document, UI, security, or evaluation reviews can remain distinct capabilities or pipelines.

## Rejected

- Importing `.planning/`, milestones/phases, STATE, commands, agents, and workflow graphs as a second RSP project model.
- Making the orchestrator the only supported entry or requiring the full loop for small work.
- Automatic atomic commits and Ship behavior without user/project authority.
- Supporting many runtimes before the canonical skills and behavior tests stabilize.
- Importing GSD's review router, phase artifacts, generic regex/style heuristics, auto-fix/commit flows, or host-specific `allowed-tools` contracts into the first RSP reviewer.

## Recommendations

- **R1 — Define managed delivery as a separate optional controller (`model-only`).** It consumes stable RSP skills and returns results to the focused Change.
- **R2 — Specify artifact-scoped agent handoffs (`independent-reimplementation`).** Every dispatch names inputs, expected output, mutation scope, verification, and stop/escalation.
- **R3 — Add task-class and context-budget policies (`model-only`).** Tiny/small work stays direct; autonomy increases only when its overhead is justified.
- **R4 — Keep controller state outside durable RSP truth (`model-only`).** Recovery artifacts may be transient or ignored; durable conclusions return to Change/Spec/Decision owners.
- **R5 — Retain only the review-object taxonomy and scope-state distinction (`model-only`).** Code, document/plan, UI, security, and evaluation coverage are different review objects; `skipped` is not `clean`. Defer every category beyond code and document until a concrete RSP gap exists.
