# Upstream Distillation: andrej-karpathy-skills

## Source Position

- **Evidence:** This is a third-party interpretation published by `multica-ai`, not an official Andrej Karpathy repository. It packages one concise guideline as an Agent Skill, a Claude plugin, and a Cursor rule (`README.md`, `.claude-plugin/plugin.json`, `.cursor/rules/karpathy-guidelines.mdc`).
- **Evidence:** Its four recurring principles are think before coding, simplicity first, surgical changes, and goal-driven execution; examples contrast over-engineered and restrained responses (`skills/karpathy-guidelines/SKILL.md`, `EXAMPLES.md`).
- **Inference:** Its value is a small behavioral vocabulary and negative examples, not authoritative attribution, a complete engineering workflow, or validated implementation guidance.

## Extracted Mechanisms

### M1 — A compact restraint contract

- **Evidence:** The skill asks the agent to surface assumptions, stop on ambiguity, prefer the smallest adequate solution, limit edits to requested scope, and convert work into verifiable goals (`skills/karpathy-guidelines/SKILL.md`).
- **Inference:** These behaviors are suitable as shared evaluation criteria across RSP skills because they constrain how a capability acts without introducing another lifecycle.

### M2 — Equivalent behavior can be expressed on multiple hosts

- **Evidence:** The repository represents the same guidance through Agent Skills, Claude plugin metadata, and a Cursor rule (`README.md`, `.claude-plugin/**`, `.cursor/rules/**`).
- **Inference:** RSP should own one canonical skill behavior and generate or package thin host adapters only when distribution requires them.

### M3 — Contrastive examples make restraint testable

- **Evidence:** `EXAMPLES.md` presents paired bad/good cases for premature implementation, unnecessary abstraction, broad cleanup, and activity without a defined finish line.
- **Inference:** Seeded contrastive fixtures are more useful to RSP than copying slogans into every skill.

## Applicable to RSP

- Add assumption visibility, smallest-sufficient action, scope fidelity, and evidence-backed completion to a shared RSP skill evaluation rubric.
- Use clean and ambiguous prompts as restraint negatives: a skill must be able to do nothing, ask, or report missing authority when that is the correct behavior.
- Keep host-specific manifests outside canonical capability instructions.

## Rejected

- Treating the repository as an official Karpathy source or using its branding as authority.
- Loading the guideline as an always-on overlay in addition to project rules and task skills; this repeats policy and consumes context.
- Treating four principles as a complete review, diagnosis, implementation, or delivery system.
- Copying the same prose into multiple host-owned files without a canonical source and drift check.

## License and Reuse

- The repository text claims MIT in `README.md` and the skill frontmatter, but the reviewed tree contains no license file. Direct copying is therefore not recommended.
- Use the ideas model-only and independently express the four evaluation properties. Preserve this report and revision as research provenance.

## Recommendations

- **R1 — Add four restraint properties to the future skill evaluation matrix (`model-only`).** Test assumption visibility, minimality, scope fidelity, and verified completion with positive and negative fixtures.
- **R2 — Maintain one canonical capability with thin host packaging (`independent-reimplementation`).** Do not duplicate behavioral prose across adapters.
- **R3 — Do not publish a standalone “Karpathy” skill (`reject`).** The behaviors are cross-cutting quality criteria and the attribution is secondary.
