# Upstream Distillation: antfu-skills

## Source Position

- **Evidence:** The repository is a proof-of-concept curated skill collection combining hand-authored skills, skills generated from official documentation, and externally vendored skills (`README.md`, `meta.ts`).
- **Evidence:** Skills are intended for on-demand loading and sharing; the README explicitly says the collection is curated by preference and is not yet fully behavior-tested (`README.md`).
- **Inference:** It is strongest as evidence for source governance and provenance-aware generation, not as a source whose catalog RSP should mirror.

## Extracted Mechanisms

### M1 — Source classes have different ownership

- **Evidence:** `meta.ts` distinguishes generated sources, manually maintained skills, and vendor mappings.
- **Inference:** RSP needs equivalent ownership labels such as `native`, `adapted`, and `generated`; each implies different update, licensing, and review rules.

### M2 — Generated and vendored outputs retain provenance

- **Evidence:** The sync script records source revision and date in `SYNC.md`, copies vendor licenses, and generated skills retain `GENERATION.md` (`scripts/cli.ts`, `skills/**/GENERATION.md`).
- **Inference:** Provenance belongs in maintainer metadata and release evidence, while runtime SKILL content should remain concise.

### M3 — Progressive disclosure limits routine context

- **Evidence:** Representative skills keep a focused `SKILL.md` and move supporting material into references (`skills/antfu/SKILL.md`, `skills/vite/SKILL.md`).
- **Inference:** RSP skills should expose only routing-critical instructions initially and load references for the selected operation.

### M4 — Registry-driven sync is reproducible but destructive

- **Evidence:** `scripts/cli.ts` initializes/removes Git submodules, copies mapped trees, and rewrites generated/vendor outputs from `meta.ts`.
- **Inference:** A declarative source map is useful; submodules and wholesale overwrite are incompatible with RSP's pinned cache plus reviewed distillation boundary.

## Applicable to RSP

- Give each future skill an ownership class, canonical source directory, release metadata, and explicit host adapters.
- Track source report, recommendation, base revision, source paths, and local version outside the runtime prompt.
- Validate generated assets for drift and required files before packaging.
- Keep `SKILL.md` small; put examples, evaluation cases, and detailed references behind explicit links.

## Rejected

- Git submodules as runtime or maintainer dependencies; RSP's disposable `.cache/upstreams/` clones already isolate upstream acquisition.
- Generating full skills from large documentation corpora without behavioral evaluation.
- Automatically overwriting local adaptations when upstream moves.
- Installing the catalog or its routing rules wholesale.

## License and Reuse

- Root tooling and hand-authored repository content are MIT (`LICENSE`). Vendored skills retain source-specific licenses, so root licensing does not authorize copying every `skills/` subtree (`README.md`, `scripts/cli.ts`).
- Eligible direct-reuse scope is limited to the root tooling patterns and exact MIT-covered paths verified during a future implementation. Prefer independent implementation against this report.

## Recommendations

- **R1 — Define skill ownership classes and provenance metadata (`independent-reimplementation`).** Start with `native`, `adapted`, and `generated`; do not infer one update policy for all three.
- **R2 — Add a deterministic source-to-package manifest (`independent-reimplementation`).** It should validate canonical paths and adapters but must not fetch upstreams at runtime.
- **R3 — Require progressive disclosure (`model-only`).** Keep triggers and essential procedure in `SKILL.md`; move deep references and evaluations out of routine context.
- **R4 — Gate every generated or adapted skill on behavior, not file sync alone (`model-only`).** Provenance proves origin, not quality.
