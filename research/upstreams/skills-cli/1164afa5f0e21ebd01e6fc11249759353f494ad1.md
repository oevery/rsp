# Upstream Distillation: skills-cli

## Source Position

- **Evidence:** `skills` remains a cross-host distribution CLI for discovering, installing, removing, and updating Agent Skills. This revision extends the update path for well-known sources and adds direct `SKILL.md` or archive download ingestion (`README.md`, `src/update.ts`, `src/update-source.ts`, `src/download-source.ts`).
- **Evidence:** RSP has a deliberately narrower project-local package installer. It installs a selected, packaged skill tree into `.agents/skills`, verifies managed paths and file trees, fails closed on divergent package-owned directories unless `--force` is explicit, and stages replacement trees before activation (`src/commands/skills.ts`).
- **Inference:** This source is still distribution-tooling evidence, not an RSP workflow model. Its new remote-source features are only relevant if RSP later adds a remote skill input; they do not justify widening today's package-owned installer.

## Extracted Mechanisms

### M1 — Update provenance must be source-specific

- **Evidence:** Well-known sources now participate in `skills update`: the updater builds a concrete source, computes a source digest, detects upstream additions, and offers updates only for the installed source (`src/update.ts`, `src/update-source.ts`, `src/providers/wellknown.ts`).
- **Inference:** A generic package version is insufficient for a remote source. An updater needs a stable source identity and content comparison before it can safely present additions or replacements.

### M2 — Direct downloads are an untrusted ingestion boundary

- **Evidence:** The new download route accepts a direct URL for one `SKILL.md` or an archive, applies download, expanded-size, and entry-count ceilings, and validates archive structure before extraction (`README.md`, `src/download-source.ts`, `src/archive.ts`).
- **Evidence:** Archive parsing rejects invalid ranges, path traversal, absolute paths, unsafe integer sizes, and multi-disk archives (`src/archive.ts`).
- **Inference:** “Direct URL” is not a shortcut around provenance, containment, or resource limits. It is a distinct trust boundary that needs explicit limits and failure behavior.

### M3 — Installation availability and update eligibility differ

- **Evidence:** This revision adds source-specific update behavior for well-known installs while retaining separate parsing, lock, local-hash, and install-source construction paths (`src/update.ts`, `src/local-lock.ts`, `src/skill-lock.ts`, `src/update-source.ts`).
- **Inference:** Being able to install a skill from a source does not imply that it has a deterministic, supported update route. The installer must surface that distinction instead of silently substituting another source form.

## Applicable to RSP

- RSP's current `rsp skills install` has no remote URL, archive, or marketplace input. Its package-root inspection, managed-path containment, exact requested-name validation, divergent-tree detection, and staged replacement already address the local package boundary (`src/commands/skills.ts`).
- There is therefore **no current RSP product gap** for M1 or M2. Adding generic source locks, remote discovery, archive extraction, or update prompts would enlarge the deterministic project protocol and overlap the ecosystem installer.
- The concrete conditional gap is future-only: if RSP ever accepts a remote skill payload rather than an already packed RSP release, it must specify source identity, immutable content evidence, bounded fetch/extract behavior, path containment, explicit replacement selection, and host-projection verification before any install mutation.

## Rejected

- **Remote URL and archive installation in `rsp skills`:** RSP currently distributes its own packaged Skills. Adding arbitrary network ingestion creates a supply-chain, cache, timeout, and archive-parser maintenance surface without an observed RSP need.
- **Automatic installation of skills newly found upstream:** a source gaining a skill is not user authorization to install it. RSP's default/optional inventory and exact-name selection remain the correct boundary.
- **Using an upstream CLI lock as RSP protocol state:** a user or host installation lock is not a Change, Spec, or `.rsp` lifecycle owner.
- **Copying the archive parser or network client now:** MIT compatibility does not establish that the substantial maintenance burden is justified while RSP has no matching feature.

- **Eligible paths for a future review:** `src/download-source.ts`, `src/archive.ts`, `src/update.ts`, `src/update-source.ts`, `src/local-lock.ts`, `src/skill-lock.ts`, and their focused tests. No source file is approved for direct reuse by this report.


## Recommendations

- **R1 — Keep the current package-owned installer closed to remote sources (`model-only`).** Its exact-name selection, managed-tree checks, and explicit `--force` replacement boundary are the correct current design. Do not add a network update command merely to mirror `skills update`.
- **R2 — If remote skill ingestion is selected later, shape it as a security-sensitive RSP Change (`independent-reimplementation`).** Require immutable source identity, bounded network and archive handling, canonical path containment, a content/provenance record outside RSP lifecycle artifacts, dry-run preview, explicit replacement authority, and hostile-input tests.
- **R3 — Treat upstream skill discovery as notice-only (`model-only`).** A future compatibility command may report newly available optional skills, but it must never install or enable them without exact user selection and normal package verification.
