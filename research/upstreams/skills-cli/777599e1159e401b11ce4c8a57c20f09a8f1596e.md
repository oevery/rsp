# Upstream Distillation: skills-cli

## Source Position

- **Evidence:** `skills` is a cross-host CLI for discovering, installing, using, listing, removing, and updating Agent Skills from Git, provider, and local sources (`README.md`, `src/cli.ts`).
- **Evidence:** It supports a canonical copy with host-specific symlinks or independent copies and tracks installed provenance in a state lock (`README.md`, `src/install.ts`, `src/skill-lock.ts`).
- **Inference:** It is distribution/tooling evidence, not an engineering protocol or a source of RSP capability behavior.

## Extracted Mechanisms

### M1 — Discovery is metadata- and boundary-aware

- **Evidence:** Discovery requires string `name` and `description`, skips internal skills unless explicitly selected, understands common host directories and plugin manifests, deduplicates names, and bounds recursive search (`src/skills.ts`, `src/plugin-manifest.ts`).
- **Evidence:** Subpaths are resolved against the clone root and rejected when they escape it (`src/skills.ts`, `src/source-parser.ts`).
- **Inference:** RSP packaging should validate identity, trigger metadata, unique names, path containment, and intentional visibility.

### M2 — Canonical payload and host projections are separate

- **Evidence:** Installation can keep one canonical skill and symlink it into many host directories, falling back to copies where needed (`README.md`, `src/install.ts`, `src/agents.ts`).
- **Inference:** RSP should author one canonical skill suite and treat `.agents`, `.claude`, or other host layouts as generated/package projections.

### M3 — Update state tracks content, not only package version

- **Evidence:** The lock records source URL/type/ref/path, folder hash, install/update timestamps, and optional plugin grouping; update compares skill folder content (`src/skill-lock.ts`, `src/update.ts`).
- **Inference:** Published version and upstream provenance are distinct. RSP can retain independent CalVer while recording exact content/source evidence for maintainers.

### M4 — Source ingestion is an untrusted boundary

- **Evidence:** Parsing handles local paths, GitHub/GitLab and generic Git sources, validates subpaths, and sanitizes displayed metadata (`src/source-parser.ts`, `src/sanitize.ts`, corresponding tests).
- **Inference:** Any future installer must treat names, metadata, archives, symlinks, and paths as untrusted rather than simple file copies.

## Applicable to RSP

- Validate canonical skill packages and generated host projections separately.
- Keep published version, payload hash, source report/revision, and installed state as separate concepts.
- Default project installation to explicit selected skills, not an entire upstream catalog.
- Reuse the ecosystem's conventional skill directories instead of inventing an RSP-only host path.

## Rejected

- Reimplementing a general Git/provider installer inside the RSP core CLI.
- Adding runtime network discovery or marketplace search to the deterministic project protocol.
- Committing user/global installation state into `.rsp/`.
- Assuming symlinks work across every host or platform.

## License and Reuse

- The package declares MIT (`package.json`); bundled dependency notices are recorded in `ThirdPartyNoticeText.txt`. No root `LICENSE` file was in the configured evidence scope.
- Prefer interface-compatible independent implementation for RSP-specific validation and packaging. If source code is copied later, verify the repository license artifact and retain all applicable notices first.

## Recommendations

- **R1 — Define a canonical skill-package validator (`independent-reimplementation`).** Validate metadata, unique names, path containment, references/scripts, and internal visibility.
- **R2 — Generate thin host projections from canonical payloads (`independent-reimplementation`).** Keep projections disposable and drift-checkable.
- **R3 — Keep installation outside the RSP protocol core (`model-only`).** Document compatibility with ecosystem installers instead of cloning their feature set.
- **R4 — Separate release version, payload hash, and research provenance (`model-only`).** None substitutes for the others.
