# Upstream Distillation: openai-plugins

## Source Position

- **Evidence:** The repository is a curated collection of Codex plugin examples. Each plugin has a required `.codex-plugin/plugin.json` and may bundle skills, apps, MCP servers, agent metadata, commands, hooks, scripts, references, and assets (`README.md`, `plugins/**`).
- **Evidence:** Marketplaces are separate indexes over plugin directories, and rich examples group multiple skills around one domain/integration (`.agents/plugins/*.json`, `plugins/build-ios-apps/**`, `plugins/notion/**`).
- **Inference:** Plugins are an optional distribution/integration envelope above skills, not the correct unit for every RSP capability and not part of the RSP project protocol.

## Extracted Mechanisms

### M1 — Plugin and skill are different capability boundaries

- **Evidence:** Manifests can point to a skills directory plus MCP/app surfaces, while each contained skill retains normal `SKILL.md` structure and optional resources (`README.md`, `plugins/build-ios-apps/README.md`, `.codex-plugin/plugin.json`).
- **Inference:** RSP should publish plain skills first; use a plugin only when the bundle requires installation policy, UI metadata, tools/apps, or multiple cohesive capabilities.

### M2 — User-facing metadata is richer than invocation metadata

- **Evidence:** Plugin manifests carry version, author, license, capabilities, category, branding, default prompts, and integration pointers; `agents/openai.yaml` holds a smaller host-facing presentation projection (`plugins/build-ios-apps/**`, `plugins/notion/**`).
- **Inference:** Canonical package metadata should generate host presentation rather than being duplicated manually.

### M3 — Marketplace policy is deployment state, not project truth

- **Evidence:** Marketplace entries point to plugin sources and express installation/authentication policy (`.agents/plugins/marketplace.json`, `.agents/skills/plugin-creator/SKILL.md`).
- **Inference:** RSP must not place marketplace/install state under `.rsp/`; packaging and catalog publication remain release concerns.

### M4 — Licensing is per package

- **Evidence:** Example manifests declare different licenses, including MIT and product-specific license references (`plugins/build-ios-apps/.codex-plugin/plugin.json`, `plugins/figma/.codex-plugin/plugin.json`).
- **Inference:** Repository membership does not imply a uniform reuse license; every adapted asset needs package-level verification.

## Applicable to RSP

- Start with a canonical RSP skill suite; introduce an RSP plugin only if it later bundles tools, hooks, apps, or cohesive UI/install metadata.
- Define one source for author, version, license, description, capabilities, and default prompt, then validate projections.
- Keep marketplace/catalog metadata in packaging/release surfaces.
- Validate plugin references and capability claims against actual bundled assets.

## Rejected

- Packaging the first RSP skills as a plugin solely for discoverability.
- Copying the repository marketplace or plugin directory conventions wholesale into the project protocol.
- Treating commands and hooks as required companions to skills.
- Assuming all example content is MIT because some manifests say MIT.

## License and Reuse

- No uniform root license was present in the configured evidence. Individual plugin manifests declare their own licenses, including non-MIT terms.
- Restrict this source to tooling/interface study and independent implementation. Any future direct reuse must verify the exact plugin's license and notices first.

## Recommendations

- **R1 — Keep Skill Suite and Plugin Package as separate domain concepts (`model-only`).** A plugin is optional distribution around one or more skills and integrations.
- **R2 — Define canonical package metadata and generated host presentation (`independent-reimplementation`).** Include author, independent version, license, capabilities, and default prompt only where supported.
- **R3 — Delay plugin packaging until a concrete integration need exists (`model-only`).** Plain Agent Skills remain the smallest interoperable product.
- **R4 — Enforce per-asset license review (`model-only`).** Catalog location is not reuse permission.
