# Upstream Distillation: planning-with-files

## Source Position

- **Evidence:** planning-with-files is a persistent planning skill that keeps task plan, findings, and progress on disk so multi-step agent work can recover after context loss, clearing, or crashes. It also offers opt-in autonomous and gated modes (`README.md`, `.agents/skills/planning-with-files/SKILL.md`).
- **Evidence:** Its planning files are explicitly ephemeral working memory rather than deliverables or durable project truth. They are gitignored by default, are not automatically archived, and lasting facts must be promoted deliberately to code, specs, ADRs, or other durable owners (`docs/workflow.md`).
- **Evidence:** The repository contains a canonical Agent Skills package plus numerous host adapters, hooks, scripts, templates, tests, install routes, and parity tooling. Its recent history documents failures caused by plan resolution, platform path differences, mirrored copies, hook behavior, and one-shot sessions sharing a working directory (`README.md`, `scripts/sync-ide-folders.py`, `tests/**`).
- **Inference:** This is valuable as a model for L3 controller memory, recovery, and guarded completion. It is not a suitable replacement for RSP's focused Change, and its distribution tree is evidence of adapter cost rather than a directory template.

## Extracted Mechanisms

### M1 — Working memory is distinct from durable truth

- **Evidence:** The source models the context window as volatile memory and planning files as disk-backed working memory. It asks agents to reread the plan before decisions and records findings, progress, errors, and recovery state (`.agents/skills/planning-with-files/SKILL.md`).
- **Evidence:** Completed plan files have no built-in archive transition and are ignored by default; durable outcomes must be copied deliberately into their actual owners (`docs/workflow.md`).
- **Inference:** RSP's Change and durable rules/specs should remain authoritative, while a future controller may keep ignored recovery/checkpoint state outside `.rsp/`.

### M2 — Active-plan resolution is explicit but has ambiguity costs

- **Evidence:** Plan resolution checks `PLAN_ID`, an `.active_plan` pointer, the newest scoped plan by modification time, and finally root files. Slug directories isolate concurrent work (`.agents/skills/planning-with-files/SKILL.md`, `scripts/resolve-plan-dir.sh`, `docs/workflow.md`).
- **Inference:** Explicit handles and isolated run directories are reusable. Newest-by-mtime fallback and shared root mode are unsuitable as authoritative selection because they can choose the wrong run; RSP should retain `focus.d/` plus an explicit Selected Change.

### M3 — Completion gating is guarded by progress evidence

- **Evidence:** Gated mode blocks stopping only when multiple conditions hold together: gated mode, an `in_progress` phase, no recursive stop, block count below a cap, and ledger progress since the previous block. An incomplete plan alone is insufficient (`README.md`, `scripts/gate-stop.sh`).
- **Evidence:** Codex's adapter is advisory rather than hard-blocking where the host cannot safely enforce continuation (`README.md`, `docs/codex.md`).
- **Inference:** A managed RSP loop needs bounded continuation, positive progress evidence, recursion protection, a block cap, and host-capability-aware fallback. It must stop rather than fabricate progress when evidence stalls.

### M4 — Append-only ledgers support recovery and concurrency

- **Evidence:** Autonomous/gated modes use an append-only JSONL run ledger, fixed-shape summaries, phase transition records, and per-agent/single-writer conventions instead of repeatedly injecting an unbounded progress tail (`README.md`, `scripts/ledger-append.sh`, `scripts/ledger-summary.sh`, `templates/task_plan.md`).
- **Evidence:** Slug-mode isolates files; attestation uses atomic replacement and optional advisory locking, while the documentation warns that locking an attestation does not make a shared plan safe for concurrent writers (`docs/attestation-locking.md`).
- **Inference:** A future controller should isolate each run, prefer one writer for controller state, append evidence events, and compute compact summaries. This state remains operational evidence, not RSP lifecycle.

### M5 — Attestation and containment bound injected instructions

- **Evidence:** The source can pin a plan body by SHA-256, refuses unattested or modified plan injection in stronger modes, uses path containment checks, and supplies a doctor command for silent resolution/injection failures (`README.md`, `docs/attestation-locking.md`, `scripts/attest-plan.sh`, `scripts/plan-doctor.sh`).
- **Inference:** Tamper detection and diagnostics are useful for an always-on hook system, but RSP's normal guided flow does not justify their cost. A future L3 experiment should first avoid implicit hook injection; attestation is optional hardening only if an actual cross-process trust boundary appears.

### M6 — Opt-out and cache-stable summaries are part of correctness

- **Evidence:** `PLANNING_DISABLED=1` was added after one-shot, CI, and nested sessions sharing a working directory were hijacked by an incomplete plan. The source also normalizes/fixes summary shape to reduce KV-cache churn (`README.md`).
- **Inference:** Any ambient controller integration needs an explicit per-invocation opt-out, a no-plan/no-effect default, and bounded stable context. Optionality is behavioral, not merely an installation choice.

### M7 — Eval scope must match the claimed outcome

- **Evidence:** The published evaluation measures creation and maintenance of the three-file pattern, not goal drift during long autonomous runs; the source states this limitation (`README.md`, `docs/evals.md`).
- **Inference:** File-pattern fidelity cannot validate RSP correctness, delivery autonomy, or drift resistance. RSP evaluations must assert intent fidelity, evidence quality, stopping behavior, authority restraint, and context cost.

## Applicable to RSP

### Current agreement

- RSP already separates durable truth, open work, and archives. planning-with-files independently demonstrates that controller working memory should not automatically become durable project history.
- `focus.d/` and an explicitly Selected Change are stronger authoritative work handles than mtime-based plan discovery.
- The L3 concept should be a removable controller over the existing engineering journey, with ignored run-local state, bounded evidence, and explicit stop conditions.

### Useful L3 model

| planning-with-files mechanism | RSP translation | Boundary |
| --- | --- | --- |
| Scoped plan directory | Isolated controller run directory outside `.rsp/` | Never selects or owns a Change |
| Active plan pointer | Explicit controller run ID associated with one Selected Change | No mtime fallback for authority |
| Task plan | Derived run snapshot referencing Change tasks and current slice | Must not duplicate the full Change as truth |
| Findings/progress | Append-only evidence and recovery notes | Promote lasting facts deliberately to existing owners |
| Run ledger and summary | Bounded event log plus fixed-shape recovery view | Controller-local and ignored |
| Completion gate | Continue only with verification/progress evidence and remaining authorized work | Cap retries; stop on stalls, blockers, or authority boundaries |
| `PLANNING_DISABLED` | Per-invocation bypass/no-effect mode | Required for one-shot and nested agents |
| Plan doctor | Controller self-check for resolution and gates | Only if an L3 implementation exists |

### Concrete limitation corrected

RSP currently defines L3 conceptually but has no tested controller contract. The upstream supplies evidence for the missing constraints: isolated run identity, single-writer state, append-only evidence, stable summaries, positive-progress gating, bounded retries, opt-out, and host-specific fallback. These belong in a future experiment specification, not in Core Protocol files today.

## Rejected

- **The three planning files as RSP core artifacts:** they duplicate Change `Tasks`, `Verify`, decisions, blockers, and progress, producing a second current-work authority.
- **Persisted `pending/in_progress/complete` phases in `.rsp/`:** these are controller execution observations and would expand RSP's deliberate `open -> archived` lifecycle.
- **Newest-by-mtime plan selection:** convenient recovery is not deterministic authority. A run and Change must be selected explicitly.
- **Mandatory plan creation and the two-action write rule:** simple tasks should remain simple, and write frequency should follow information value rather than a universal tool-count heuristic.
- **Per-tool hook reinjection as the default:** it raises context/cache cost and can redirect unrelated or nested work. Explicit stage reads and compact summaries are safer.
- **A stop hook that treats an incomplete plan as sufficient evidence:** stale or impossible plans can trap an agent. Continuation requires progress, remaining authorized work, bounded retries, and no blocker.
- **SHA attestation for ordinary RSP use:** it protects an ambient injection mechanism RSP does not currently need. It should not become protocol ceremony without a demonstrated threat boundary.
- **Session scraping as durable recovery:** platform conversation history is not an RSP authority; recover from explicit artifacts and evidence.
- **Copying IDE mirrors, hook adapters, installers, or parity machinery:** host proliferation creates ongoing maintenance and drift risk. Start with one capability-neutral controller interface and add adapters only for demonstrated hosts.
- **Accepting benchmark or version claims as capability proof:** the source itself limits its evaluation to file-pattern fidelity, and release/badge surfaces can drift independently. RSP needs behavior-focused local evals.

## Recommendations

- **R1 — Preserve the working-memory/durable-truth split (`model-only`).** Keep `.rsp/` as protocol truth and any future plan, ledger, summary, or checkpoint in an ignored controller-owned run directory. Promote only selected lasting facts through the normal Change and durable-decision process.
- **R2 — Specify an L3 controller experiment before implementation (`independent-reimplementation`).** Bind one explicit run ID to one Selected Change; execute one bounded slice; append verification/review evidence; derive a fixed-shape summary; continue only with positive progress and authorized remaining work; stop on blocker, stall, retry cap, user decision, external approval, or Git/publication authority.
- **R3 — Require safe ambient behavior (`model-only`).** If hooks or automatic discovery are ever tested, no run must mean no effect; every invocation needs an opt-out; resolution must reject ambiguity and path escape; nested/one-shot agents must not inherit controller behavior accidentally.
- **R4 — Evaluate drift and restraint, not file compliance (`model-only`).** Seed long tasks with a changed requirement, an impossible acceptance check, a failed verification, a stale run, ambiguous focus, and a request requiring commit/push. Compare guided RSP with the controller on correct stopping, source-of-truth fidelity, recovery accuracy, fabricated progress, token/context cost, and clean-case restraint.
- **R5 — Do not adopt planning-with-files directly (`reject direct adoption`).** Reuse its proven constraints and failure lessons as a design model. A future RSP controller should be independently implemented around RSP's owners rather than modifying the upstream three-file protocol.
