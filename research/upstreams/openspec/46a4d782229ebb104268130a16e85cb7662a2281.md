# Upstream Distillation: openspec

## Source Position

- **Evidence:** `docs/concepts.md` presents OpenSpec as a Git-native specification workflow built around two primary artifact classes: current `specs/` as accepted behavioral truth and isolated `changes/` as proposed modifications. Its default change is a directory containing proposal, delta specs, design, tasks, and optional metadata.
- **Evidence:** `schemas/spec-driven/schema.yaml` and `src/core/artifact-graph/types.ts` define a configurable dependency graph for those artifacts, while `src/core/artifact-graph/state.ts` derives completion from filesystem outputs rather than a separate workflow database.
- **Evidence:** `docs/editing-changes.md` treats Markdown artifacts as the live plan and permits iteration at any time; `docs/workflows.md` layers optional exploration, verification, synchronization, and expanded command flows around the same files.
- **Evidence:** `openspec/work/simplify-context-and-workspace-model/goal.md` and `roadmap.md` are especially relevant counter-evidence to OpenSpec's own earlier initiative/workspace experiment: the current direction deliberately simplifies the product back to “Specs are what is true; Work is what is in motion,” Git roots, read-only references, and personal views.
- **Scope:** This initial review is pinned to revision `46a4d782229ebb104268130a16e85cb7662a2281`, strategy `model`, and evidence hash `sha256:4b35797aebdf0504c0ae89f4f7192479e3f0fc49566479a74d7bbc53847411d5`. OpenSpec is used as a domain-model peer, not as a compatibility standard or a source tree to reproduce.
- **RSP comparison boundary:** Current RSP authority remains `.rsp/rules/rsp-rules.md` and `.rsp/specs/design.md`: one single-file change, `focus.d/` as the only current-focus source, durable `rules/` and `specs/`, and only `open -> archived`. Historical discussion about path abstraction, initiatives, and a durable-decision gate is treated here as design input, not as evidence of current RSP behavior.

## Extracted Mechanisms

### Two-layer truth model

- **Evidence:** `docs/concepts.md` separates current accepted behavior in `specs/` from proposed modifications in `changes/`. The important mechanism is not the directory names; it is the distinction between durable truth and work in motion.
- **Evidence:** `docs/writing-specs.md` bounds durable specifications to observable, verifiable behavior and keeps implementation choices in design and task artifacts. Requirements and scenarios provide a reviewable behavioral contract.
- **Evidence:** `docs/editing-changes.md` says change artifacts remain editable living plans, but they must be reconciled with the implementation before archive because archive promotes specification content into the truth of record.
- **Inference:** RSP already implements the same high-level separation more broadly: `rules/` and `specs/` are durable truth, while one file in `changes/` carries the complete work record. OpenSpec supports this separation but does not imply that RSP needs OpenSpec's per-capability spec syntax.

### Artifact graph and derived guidance

- **Evidence:** `schemas/spec-driven/schema.yaml` declares `proposal -> {specs, design} -> tasks -> apply`. Dependencies describe which artifacts provide context for another artifact; they do not require a separate persisted status field.
- **Evidence:** `src/core/artifact-graph/types.ts` models artifacts as `id`, output path, template, instructions, and `requires`. `src/core/artifact-graph/state.ts` marks an artifact complete when its declared output exists. `openspec/specs/artifact-graph/spec.md` requires cycle detection, dependency validation, topological ordering, ready-artifact discovery, and reporting of unmet dependencies.
- **Evidence:** `openspec/specs/cli-artifact-workflow/spec.md` and `docs/agent-contract.md` expose `done`, `ready`, and `blocked` as derived command output, including missing dependencies, resolved output paths, context files, allowed edit roots, and plain-language next steps.
- **Inference:** The reusable mechanism is a derived path from artifact dependencies to next-action guidance. The four-file graph itself is not required where RSP deliberately co-locates the same concerns in six sections of one change file.

### Delta, promotion, and archive

- **Evidence:** `docs/concepts.md`, `docs/writing-specs.md`, and `openspec/specs/openspec-conventions/spec.md` define ADDED, MODIFIED, REMOVED, and RENAMED requirement deltas. A modified requirement carries its complete replacement content, not a fragment.
- **Evidence:** `src/core/archive.ts` validates change deltas, applies them to current specs, validates resulting specs, and then moves the complete change directory into a dated archive. Conflicts or invalid results block the mechanical promotion path.
- **Evidence:** OpenSpec archive owns both truth promotion and historical movement. Git owns the surrounding history and review; OpenSpec does not introduce an independent event store for this lifecycle.
- **Inference:** This supports the need for an explicit pre-archive truth decision, but not automatic delta application in RSP. RSP's durable facts and rules are less mechanically matchable than OpenSpec's header-addressed behavioral requirements, so semantic review remains the safer owner.

### Path abstraction and initiative lessons

- **Evidence:** `openspec/initiatives/context-store-and-initiatives/direction.md` records an earlier hierarchy of context stores, collections, initiatives, workspaces, and repo-local changes. It explicitly marks that direction as historical rather than current authority.
- **Evidence:** `openspec/work/simplify-context-and-workspace-model/goal.md` says the product should not require context stores, workspaces, or another state system as primary concepts. Its roadmap records that new initiative links and workspace-owned planning were removed in favor of normal roots and references.
- **Evidence:** `openspec/work/simplify-context-and-workspace-model/slices/store-references/spec.md` keeps upstream context as a live one-level index: references never redirect writes, never inline or copy source content, never recurse, and never create managed per-change relationship objects. A downstream artifact cites what it uses in prose.
- **Evidence:** `openspec/initiatives/context-store-and-initiatives/work-items/09-add-initiative-resolve/decision-review.md` rejects repo scanning, path search roots, Git-remote matching, cloning, worktree/branch creation, backlinks, and availability dashboards from initiative resolution.
- **Inference:** This is strong experiential evidence for correcting the earlier RSP idea of making `path`, `initiative`, or a cross-repo coordination object part of the lightweight core. Paths are resolution results and ownership boundaries; they should not become durable product identity. Larger coordination can remain an optional system layered over repo-owned RSP changes.

### How the historical RSP discussion is affected

- **Supported:** The proposed boundary between `AGENTS.md`/context navigation and RSP-owned durable/current work matches OpenSpec's separation between discovery/action context and the selected root's owned artifacts. `docs/agent-contract.md` demonstrates that resolved paths and allowed edit roots can be supplied as derived action context rather than embedded into every artifact.
- **Supported:** The durable-decision gate is justified by OpenSpec's strict archive boundary: current truth should not change merely because implementation tasks appear complete.
- **Corrected:** “Path” should describe where an owner or resolved artifact lives, not become a first-class lifecycle object. OpenSpec's own simplification removed richer path/workspace mapping from its primary workflow.
- **Corrected:** An initiative can be a useful external coordination concept, but it should decompose into or reference repo-owned changes. It should not alter RSP's single-change ownership, focus truth, or archive lifecycle.
- **Refuted for RSP core:** Managed backlinks, recursive cross-root graphs, workspace-owned plans, automatic repo discovery, and an initiative state machine add a competing authority. OpenSpec's current simplification explicitly removes or rejects these mechanisms.

## Rejected

- **OpenSpec's multi-file change directory:** rejected because RSP's single-file change is a deliberate compactness and context-loading constraint. Proposal, spec delta, design, tasks, verification, and blockers already have stable owners inside that file.
- **Configurable artifact schemas in RSP core:** rejected because RSP prioritizes cross-project predictability over per-project workflow freedom. Optional skills may choose richer execution paths without redefining the protocol.
- **Persisted `ready`, `blocked`, `verified`, or review lifecycle states:** rejected because both systems can derive useful readiness from artifacts. RSP must preserve only `open` and `archived`; intermediate observations belong in command output.
- **Automatic application of change `Spec` deltas into durable files:** rejected because RSP durable documents contain project facts and rules without OpenSpec's globally unique requirement headers. Mechanical replacement would turn advisory planning syntax into unsafe semantic writeback.
- **A first-class RSP initiative tree:** rejected because OpenSpec's own initiative/workspace experiment accumulated stores, collections, links, maps, and resolution behavior before being simplified. Coordination should remain an optional layer over normal project-owned changes.
- **Path-derived durable identity:** rejected because checkout paths are machine-local and movable. RSP's owners are the project root and named files; any future cross-project relationship should use explicit stable references and resolve them locally.
- **Inlining or copying upstream/context content into active instructions:** rejected because it increases context and creates stale duplicate truth. An index with explicit fetch/read steps and citations preserves ownership.
- **Recursive reference graphs or managed per-change links:** rejected because they introduce hidden action redirection, cycle handling, synchronization state, and ambiguous write ownership.
- **OpenSpec's requirement/scenario syntax as a universal RSP spec format:** rejected because it is valuable for observable product behavior but too narrow for architectural facts, boundaries, defaults, and project rules that RSP also stores durably.


## Recommendations

- **R1 — Model the RSP engineering path as a derived, optional journey.** In the cross-source model, map `intent -> Proposal -> Spec -> Design -> Tasks -> implementation -> Verify -> durable decision -> archive/delivery`. Each step should point to an existing section, command, or semantic owner. Do not add files, section-state metadata, or lifecycle states. Candidate future owner: `skills/rsp/SKILL.md`, only if synthesis with spec-kit and later engineering-skill research confirms a concrete usability gap.
- **R2 — Preserve the durable-decision gate instead of adopting automatic delta merge.** Treat OpenSpec archive as evidence that truth promotion needs an explicit boundary, while retaining RSP's semantic choice among no durable update, updating an existing durable file, or creating a justified new spec. Candidate owners: existing `skills/rsp/SKILL.md` and `rsp ready/show` guidance; no change is recommended until the cross-source model identifies missing guidance.
- **R3 — Define path as ownership plus resolution, not as a new domain entity.** Any future path guidance should answer: which artifact owns this fact, which deterministic command resolves it, and which root may be edited. Keep machine-local checkout paths out of durable identity. Candidate owner: the cross-source engineering-path model; future product change only if a specific multi-root use case survives review.
- **R4 — Keep initiatives outside the lightweight protocol.** If an autonomous engineering layer later coordinates large or cross-repo work, model it as an optional orchestrator that references normal repo-owned RSP changes and derives rollups. It must not replace `focus.d/`, create a second change lifecycle, redirect writes implicitly, or become required for small projects. Candidate owner: a future optional workflow skill, not `.rsp/rules/rsp-rules.md`.
- **R5 — Prefer live context indexes and prose provenance over copied context.** For any future external-context feature, expose a bounded one-level index, explicit read command/path, warning on unresolved context, and citation in the consuming change. References remain read-only unless the user explicitly operates in the referenced root. Candidate owner: future research and a normal RSP change only after a local need exists.
- **R6 — Use OpenSpec's artifact graph as an evaluation lens, not an implementation blueprint.** When reviewing Matt, Ponytail, or other engineering skills, require every mechanism to identify its inputs, outputs, prerequisites, next action, owning RSP surface, and whether readiness is deterministic or semantic. This provides the path discipline sought in the historical discussion without importing OpenSpec's directory graph. Candidate owner: the planned cross-source model and subsequent skill-distillation rubric.
