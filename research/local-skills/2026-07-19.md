## Extracted Mechanisms

### L1 — Routing follows task class and repository maturity

- **Evidence:** `engineering-flow` classifies tiny, small, large, and strategic work, then selects setup, specification, slicing, implementation, review, handoff, and capture behavior (`skills/engineering-flow/SKILL.md`).
- **Inference:** RSP can use the same progressive principle while deriving state from the focused Change rather than creating a global workflow router.

### L2 — Authority is layered explicitly

- **Evidence:** The flow treats global instructions as policy, repository rules as authority, project artifacts as the first landing point, and LifeOS as selective durable capture (`skills/engineering-flow/SKILL.md`).
- **Inference:** Future RSP skills must declare precedence and returned ownership. A skill does not become authoritative merely because it is invoked.

### L3 — Local issues demonstrate the small grouped-work shape

- **Evidence:** `local-issues` uses one shallow feature directory with `PRD.md` and direct issue files, selects exactly one unblocked issue, validates readiness/completion, and rejects ambiguous focus (`skills/local-issues/SKILL.md`).
- **Inference:** The useful experience is deterministic selection, explicit gates, and one-level grouping; RSP should not copy the separate `.scratch` status vocabulary or create a competing tracker.

### L4 — Verification and Git authority remain outside capability enthusiasm

- **Evidence:** Both skills require focused validation and explicit commit authorization; review fixes are scoped and dirty/untracked files are audited (`skills/engineering-flow/SKILL.md`, `skills/local-issues/SKILL.md`).
- **Inference:** These constraints belong in shared RSP capability contracts and tests.
