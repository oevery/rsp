# RSP Capability Coverage

## Purpose and Decision Rules

This ledger proves that the complete candidate research baseline was considered by capability rather than by repository popularity. It is intermediate maintainer research, not product truth and not authorization to create or modify a published Skill.

The accepted upstream baseline is closed. Current product identities are reconciled against `.rsp/specs/skill-system.md`; historical source classifications remain evidence for why a capability was selected, deferred, externalized, or rejected.

The six decision values are intentionally closed:

- `adapted`: compare or derive narrowly from an MIT-eligible exact path, retaining notice and attribution if source text or code is reused;
- `independent-reimplementation`: preserve the evidenced contract while writing RSP-owned behavior independently;
- `model-only`: use the mechanism as a design or evaluation constraint, not as runtime content;
- `external`: compose with an existing project or host capability instead of duplicating it in RSP;
- `defer`: a demonstrated idea whose owning layer is outside the minimum suite or whose need is not mature;
- `reject`: no RSP owner because the behavior conflicts with RSP boundaries, is fixture-only, or lacks an RSP gap.

Evidence depth is `deep` when the source report analyzes the exact path and mechanism, `medium` when the report establishes the suite mechanism and the exact Skill contract supplies the classification, and `inventory` when the path is present only to prove an explicit exclusion. Grouped rows share one decision, target, and reason; every grouped path remains explicit.

## Demonstrated RSP Gaps

| Gap | Need | Minimum owner |
| --- | --- | --- |
| G1 | Derive one next action from user intent, focus, readiness, blockers, and available capabilities without a router overlay. | `rsp` |
| G2 | Turn unclear non-trivial intent into one authorized six-section Change or shallow Group with executable vertical slices; progressively deepen explicit or high-risk clarification and return one material design question through the same WorkRef. | `rsp-shape` |
| G3 | Implement one selected Change within project authority and return fresh, truthful verification evidence. | `rsp-implement` |
| G4 | Review code and documents against fixed scope and authority while remaining report-only. | `rsp-review` |
| G5 | Validate, evaluate, package, and promote host-neutral Skills without leaking research or provenance into runtime context. | Skill promotion gate |
| G6 | Recover and coordinate long autonomous runs without moving RSP truth or inferring Git/publication authority. | `rsp-manage` |
| G7 | Disposition fixed review findings, correct accepted findings under explicit authority, require fresh verification and re-review, and recover one bounded pass without hidden state. | `rsp-resolve-findings` |
| G8 | Establish a confirmed cause or truthful unresolved diagnosis before production correction while preserving one selected Change and read-only investigation authority. | `rsp-diagnose` |
| G9 | Drive one clear behavior through observed RED, minimal GREEN, optional safe REFACTOR, and fresh verification without taking review or delivery authority. | `rsp-tdd` |
| G10 | Resolve one bounded domain-model, module/seam, or reversible-exploration question before or within tracked work from project evidence without implementing it or creating a second artifact owner. | `rsp-design` |

The 3.0 readiness review originally demonstrated RSP-specific diagnosis, TDD, and tracked design gaps. Later product Changes added bounded verification, finding resolution, managed coordination, workspace isolation, local commit, exact landing, and release-document capabilities without importing an upstream lifecycle. Broad architecture audits, teaching, browser, platform, product, knowledge capture, deployment, and generic remote publication remain external unless later evidence establishes another RSP owner.
