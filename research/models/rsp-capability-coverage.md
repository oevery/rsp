# RSP Capability Coverage

## Purpose and Decision Rules

This ledger proves that the complete candidate research baseline was considered by capability rather than by repository popularity. It is intermediate maintainer research, not product truth and not authorization to create or modify a published Skill.

The six decision values are intentionally closed:

- `adapted`: compare or derive narrowly from an MIT-eligible exact path, retaining notice and attribution if source text or code is reused;
- `independent-reimplementation`: preserve the evidenced contract while writing RSP-owned behavior independently;
- `model-only`: use the mechanism as a design or evaluation constraint, not as runtime content;
- `external`: compose with an existing project or host capability instead of duplicating it in RSP;
- `defer`: a demonstrated idea whose owning layer is outside the minimum suite or whose need is not mature;
- `reject`: no RSP owner because the behavior conflicts with RSP boundaries, is fixture-only, or lacks an RSP gap.

Evidence depth is `deep` when the source report analyzes the exact path and mechanism, `medium` when the report establishes the suite mechanism and the exact Skill contract supplies the classification, and `inventory` when the path is present only to prove an explicit exclusion. Grouped rows share one decision, target, and reason; every grouped path remains explicit.

## Demonstrated RSP Gaps

| Gap | Need | Minimum owner |
| --- | --- | --- |
| G1 | Derive one next action from user intent, focus, readiness, blockers, and available capabilities without a router overlay. | `rsp` |
| G2 | Turn unclear non-trivial intent into one authorized six-section Change or shallow Group with executable vertical slices; progressively deepen explicit or high-risk clarification and return one material design question through the same WorkRef. | `rsp-shape` |
| G3 | Implement one selected Change within project authority and return fresh, truthful verification evidence. | `rsp-implement` |
| G4 | Review code and documents against fixed scope and authority while remaining report-only. | `rsp-review` |
| G5 | Validate, evaluate, package, and promote host-neutral Skills without leaking research or provenance into runtime context. | Skill promotion gate |
| G6 | Recover and coordinate long autonomous runs without moving RSP truth or inferring Git/publication authority. | Optional host/external orchestration; `rsp-manage` remains research-only with `revise` |
| G7 | Disposition fixed review findings, correct accepted findings under explicit authority, require fresh verification and re-review, and recover one bounded pass without hidden state. | `rsp-address-review` |
| G8 | Establish a confirmed cause or truthful unresolved diagnosis before production correction while preserving one selected Change and read-only investigation authority. | `rsp-diagnose` |
| G9 | Drive one clear behavior through observed RED, minimal GREEN, optional safe REFACTOR, and fresh verification without taking review or delivery authority. | `rsp-tdd` |
| G10 | Resolve one bounded domain-model, module/seam, or reversible-exploration question before or within tracked work from project evidence without implementing it or creating a second artifact owner. | `rsp-design` |

The 3.0 readiness review demonstrated RSP-specific diagnosis, TDD, and tracked design gaps: external capability names were not installed with the package, while inline fallbacks duplicated partial discipline behavior. RSP now owns one bounded design question, semantic artifact routing, response continuation, and a compact in-scope conflict fallback. Broad architecture audits, teaching, generic Git delivery, browser, platform, product, knowledge capture, managed orchestration, and specialized diagnosis/testing branches remain external unless later evidence establishes another RSP owner.

## Selection for the Assisted Suite

The original minimum ledger supported four owners. The tightened 3.0 release review and native-design validation demonstrate eight RSP-specific owners:

1. `rsp` absorbs G1 as compact derived next-action guidance from C01 and C45.
2. `rsp-shape` independently implements G2 from C05, C10, C20, C36, and C46. Its progressive deep clarification passes the five same-case terminal journeys and returns one material design question through the same WorkRef.
3. `rsp-design` independently implements G10 from the user-observed real-project need plus bounded mechanisms in C03 and C07; it resolves tracked domain, module/seam, and reversible-exploration questions without becoming a durable owner or implementing production behavior.
4. `rsp-implement` independently owns G3 from C06, C21, C37, C47, the compact C04b fallback, bounded C12 continuation, and the restraint contract in C14; it returns changed evidence to the diagnosis or TDD seam rather than reproducing those disciplines.
5. `rsp-review` remains the stable G4 report-only capability informed by C02, C15, C19, and C38.
6. `rsp-address-review` independently owns G7 from the resolution contracts evidenced by C31 and C39, returning the shared bounded continuation when work remains.
7. `rsp-diagnose` independently implements G8 using the evidence-gate constraints retained from C04 and C40.
8. `rsp-tdd` independently implements G9 using the red-green-refactor and restraint constraints retained from C04 and C40.

G5 remains maintainer infrastructure rather than a published user capability. G6 still names generic long-running coordination, budgets, retries, and delegation, but the evaluated `rsp-manage` candidate remains research-only with recommendation `revise`: it matched baseline outcomes while adding material cost and did not demonstrate a promotion-worthy delta. Native bounded continuation does not satisfy G6; explicit host/external orchestration may compose current Skills only while RSP artifacts and authority boundaries remain unchanged. Every other discovered Skill path has an explicit external or rejected disposition, so catalog breadth does not become suite scope.
