### The remaining deterministic failure is another oracle defect

The noise repair passes eight of nine private behavior checks, including ACK/readback serialization, quarantine, reconnect recovery, no replay, recovery ordering and failed-readback protection. It rejects an out-of-range recovery observation and keeps the last confirmed display value. Its rejection is `RangeError: invalid level`. The private test instead requires `/unconfirmed level/`. CONTEXT.md specifies valid levels and rejection/state behavior but no error message for this newly handled case. The deterministic check therefore rejects an equivalent correct implementation. The semantic judge accepted the source, retained tests and supported verification.

The separate `error-contract-probe.log` verifies rejection without a message restriction and confirms that level 2 remains unchanged after observing invalid level 4. It is a behavior characterization, not a regrade. No agent output or original verifier artifact was edited.

There is also a test-discrimination confound. The task swaps the entire controller with each authored mutant. The retained agent test expects RangeError for invalid recovery values, while both mutants throw ordinary Error there. Running only that validation test rejects both the ACK-only and ineffective-refresh mutants. Thus a killed mutant does not, by itself, prove coverage of its intended transaction/recovery regression. `mutant-confound.log` retains both failures. The actual retained tests do contain explicit read gates, write-history assertions and recovery checks, so this confound does not establish that those agent tests miss the target behavior. It limits the measurement method.

The RangeError assertion in the retained agent test is itself worth examining: the chosen class is observable, but this task supplies no consumer that needs that exact class. It is a potential maintenance constraint rather than a demonstrated functional defect. Either establish the public error contract or verify rejection together with display and wire effects. Do not equate every error assertion or interaction count with a bad test.

## Primary upstream practices and their limits

Sources were selected for this question, not ranked by popularity. Live web documents were read and retained through the existing research import mechanism on 2026-10-19. Pinned community captures are historical primary material, not claims about their latest branches. Source instructions were inspected as data and were not activated as workflows.

### Evaluation must distinguish outcomes, traces and graders

OpenAI's skill-evaluation article separates outcome, process, style and efficiency goals, recommends a small set of important checks, and pairs structured execution traces with artifacts and adjacent negative controls. Its example command checks are appropriate only when that method is actually required; they are not a reason to gate RSP acceptance on one read command or package manager. Local Harbor already supplies the necessary execution and evidence machinery. Source: `https://developers.openai.com/blog/eval-skills`, retained as `quality-openai-eval-skills@20261019T061403212Z`.

Anthropic's agent-evaluation guidance distinguishes graders, transcripts and outcomes, recommends starting from real failures, and warns that rigid grading can reject valid alternate solutions. Apply that directly here: include a correct alternate rejection form before trusting the error grader, and isolate the property each negative control is meant to change. This is an evaluator correction, not a new installed-agent obligation. Source: `https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents`, retained as `quality-anthropic-evals@20261019T061403435Z`.

### Tests should protect behavior and use independent expectations

Google's unit-testing chapter connects maintainability with tests that survive behavior-preserving refactors and verifies behavior rather than private method structure. Its review guidance asks whether tests really fail on the relevant break and treats unnecessary complexity as future capability without a present need. These support RSP's existing consumer/consequence rule; they do not imply deleting useful concurrency or side-effect assertions. Sources: `https://abseil.io/resources/swe-book/html/ch12.html` and `https://google.github.io/eng-practices/review/reviewer/looking-for.html`, retained as `quality-google-unit-testing@20261019T061403392Z` and `quality-google-review@20261019T061403349Z`.

At Superpowers commit `bb92a77741419a4ab5f06e711a283343f1ada0c3` (v7.0.0), `skills/test-driven-development/writing-good-tests.md` explicitly asks which real break a test catches, derives expected values independently, rejects source-text/change-detector tests and allows argument/count/order assertions when those are the contract. Its parent `SKILL.md` mandates test-first development much more broadly. Distill the test-value criterion; retain RSP's risk-selected test-first policy. Repository: `https://github.com/obra/superpowers`.

Matt Pocock's captured `skills/engineering/tdd/tests.md` similarly prefers public behavior and independent expected literals. Its call-count warning is a red flag, not a universal rule: the noise case needs to prove that no forbidden write or replay occurs. The same capture's `codebase-design/SKILL.md` asks whether deleting a layer removes complexity or disperses it into callers. That fits RSP's existing structural-review method without importing a new fixed module vocabulary. Commit `24fe0ef7737efae15c87225755e9f6f5965e4888`, repository `https://github.com/mattpocock/skills`.

### Comments preserve information code cannot carry

Google's review guidance distinguishes explaining a non-obvious reason from restating operations and suggests simplifying confusing code before adding explanatory prose. DeepSeek Harness's captured `.agents/skills/dsh-prose-standard/SKILL.md` makes timing, ownership, surprising failures and misuse-preventing rationale explicit, while rejecting control-flow narration. That is a useful refinement of RSP's existing local accuracy/clarity check, not a reason to comment every function.

An independently written example for this domain would explain that an ACK has no request identity, so a timeout requires reconnecting before accepting another write. A comment saying only that an uncertainty flag is being set adds no such information. If CONTEXT or an owning protocol definition already supplies the necessary local explanation, a short reference may be sufficient. This matrix does not separately establish that current agents mishandle comments; treat this as a targeted clarity candidate and coverage gap.

## Recommendations, without changing Skills

**First repair the evidence, not the installed workflow.** A later fixture correction should remove the undocumented error-message/type requirement, retaining assertions for rejection, unchanged confirmed state and forbidden writes. Keep exact error assertions when an actual consumer or agreed API requires them. Add an equivalent-correct alternative before trusting that grader. Make each mutation change only its named behavior; swapping a reference implementation must not let an unrelated validation test earn transaction/recovery credit. These are recommendations only: this investigation does not edit the frozen matrix or rerun/regrade its agents.

**Make one existing test-admission rule more operational, if a Skill candidate is selected.** The possible delta belongs in Implement's current permanent-test rule and the corresponding Review judgment, not in a new testing Skill or global AGENTS layer. Proposed meaning:

> Derive expected values and failure checks from the consumer's agreed contract or an independent example. When error type or wording is not part of that contract, verify rejection and its effects instead of freezing an implementation choice.

This would clarify a narrow oracle gap in the wording. It should replace or refine overlapping prose, preserve risk-selected test-first behavior and add no mandatory evidence form, report field or independent worker. The confirmed problem is failure to ground an authored assertion; the current run does not establish that a stronger general prohibition would improve agents.

**Clarify the ordinary-comment check at its existing owner.** A possible Doc/Implement refinement is to retain comments explaining otherwise invisible constraints or rationale needed for correct use or modification, while removing local code restatement. Keep public inputs, failures, timing and ownership in the correct API/project owner. This is lower confidence than the oracle issue because the matrix did not isolate comment quality. Do not adopt a universal comment quota or a rule that code must always explain everything without prose.

**Preserve the current mechanism-admission and simplicity rules.** The practical question is which real consumer, boundary or lifecycle consequence would break after removal. It keeps reconnect recovery, mixed-protocol grouping and independently trusted artifact integrity when required, while permitting removal of per-handset protocol machinery and duplicate capture identities under different contracts. Do not add universal bans on hashes, defensive code, mocks, call-count assertions, helpers or nearby tests.

**Put missing business facts near their real project owner.** For the original protocol and noise cases, preserve receiver identity ownership, whether mixed protocols are deployed, ACK correlation limits and the consumer of any digest. Use the existing CONTEXT/Spec and conditional source-reading path. A generic Skill cannot recover a fact that has no accessible authority. This is project knowledge maintenance, not a requirement to reread all hardware or history for every change.

**Use a later complex holdout for the remaining uncertainty.** Complexity should come from the real consumer path, multiple owners and retrieval of an implicit domain constraint, not simply more files. One useful future case would require discovering receiver-owned protocol selection from the SDK/protocol source while preserving mixed-protocol behavior in a separate deployment. Another would judge whether comments preserve the late-ACK rationale while removing mere narration. Such cases and a matched candidate comparison need separate selection and execution authority. A no-Skills arm would answer causal contribution differently; this baseline has none.

The defensible attribution is therefore layered: broad test-value and boundary rules already exist; the observed oracle and mutation mistakes are evaluation-authoring failures; a small independent-expectation clarification is a plausible rule-precision candidate; comment policy has a static clarity opportunity and an execution-evidence gap. Performance in the original larger repositories remains unestablished. Nothing here justifies another workflow layer or an automatic Skill rewrite.
