# Evidence guidance: two live pairs and one recovery supplement

The correction-continue baseline and candidate both passed without an exit-code
recovery rerun. The interruption-recovery baseline passed; its first candidate
run ended with ApiRateLimitError and a missing final report. One separately
authorized candidate supplement completed successfully. These observations
support completion feasibility, not reliable efficiency improvement or default
adoption. Both candidates remain isolated.

## Recovery, reading strategy and retained failures

Both original recovery arms and the supplement preserve native evidence of
the original command exiting, the first worker completing and the parent
observing completion before dispatching a distinct continuation worker. Each
continuation runs resume once, completes and is awaited. Artifacts show A
then B exactly once, correctionCount 1, completed true, and paused events
as an unchanged prefix. These cessation and ordering observations are narrower
than whole-task completion.

The recovery baseline prints broad first-worker trajectory data in parent and
continuation calls, each retaining 65,536 output bytes. The original candidate
selects event types, line ranges and keyword matches instead, but its
continuation inspection still retains 50,860 bytes before a narrower
3,469-byte extraction. The supplement also uses keyword filtering yet retains
65,536 bytes in one continuation call before a narrower extraction. The
[reading observations][reads] and supplement observations locate these calls.
Selections include different scopes and large nested payloads; retained native
output can be capped. File or output bytes are not delivered token counts,
and no savings percentage follows.

The original recovery candidate has two pre-dispatch JavaScript syntax
failures and one dispatched Python syntax failure during final evidence
validation. That Python module body does not run, so its planned finalization
is not completed evidence. A separate earlier partial-file existence probe
exits 1 before partial output appears; this is not a construction failure.
The executor subsequently ends with exceeded retry limit, last status:
429 Too Many Requests. Native result records ApiRateLimitError, report.json
is absent, checks score 0 and judge scores 1. The missing deliverable and
native error prevent acceptance regardless of the judge's narrower criteria.
Do not attribute all omissions solely to 429 or erase the preceding failures.
Host-native sessions remain retained despite incomplete workspace finalization.

The supplement has no native execution exception and retains report.json with
all referenced evidence files present. It still has one dispatched Python
syntax failure and a subsequent finalize.py AttributeError from treating a
list as a dictionary; later calls complete successfully. Those failures and
successors remain in the sessions. A full score is not error-free execution.

The original candidate's shorter duration and lower usage reflect incomplete
delivery and cannot establish equivalent-work efficiency. The successful
supplement provides additional completion evidence but does not replace the
original 0.5/error result or retroactively turn the first pair into two passes.
Its different execution time, cache history and command workload likewise
prevent a causal comparison with the earlier baseline.

## Adoption assessment

The exit-status guidance has value as an optional local hint where mixed
commands obscure a check's own result. Its rationale comes from the earlier
observed extra execution and offline attribution controls described in the
cost assessment, not an incremental benefit demonstrated by this pair. Both
arms already obtained separate check results without recovery reruns. The
candidate preserved independent execution, but lower input tokens alongside
higher output and elapsed time do not establish a net efficiency benefit.

The most useful operational point is to retain the check's own result on its
first execution. The full 543-byte append also adds prompt reading, repeats
the independent-execution reminder and requests target/result attribution.
Those obligations have a cost that this experiment does not isolate. If
separately authorized for local use, it should not grow into a mandatory
receipt schema or another verification phase. It does not justify default
loading or a new Core/Commit rule.

The evidence-reading principle remains useful, but adopting the current
743-byte append is not recommended. The candidate changed how it selected
records without reliably making the output compact: original and supplemental
continuation reads retained 50,860 and 65,536 bytes respectively. Filtering
for a keyword or event type can still return a large nested payload. The
supplement proves completion feasibility under the unchanged contract, not
reliable minimal reading or repeated stability.

This guidance adds selection decisions and potentially script construction,
parsing and evidence-management work. The supplement's Python syntax and
parsing-type failures show that this work is not free of execution problems;
they do not establish that the guidance caused those failures. Its input,
output and duration exceed the earlier baseline's observations, but differing
order, cache history and command workload likewise prevent concluding that
the guidance caused a regression. The original incomplete run cannot supply
an equivalent-work savings comparison either.

Keep both candidates isolated. The exit-status hint has a bounded possible
use case; the current evidence-reading text lacks sufficient benefit for
default adoption. No further run is needed merely to reach that present
recommendation. Future local adoption remains a separate decision, and this
assessment authorizes neither adoption nor another experiment. Preserve
independent verification, native cessation evidence and complete original
records. Output bytes are not model tokens; no net fee or savings percentage
is established. The supplemental 1.0 remains separate from the original
0.5/429 outcome. Core/Commit, task baselines, scoring and candidate labels
remain unchanged.

## Preservation, review and stopping decision

The original [integrity record][integrity] verifies 47,798 historical files,
1,463 tracked sources and all four frozen input sets unchanged. The
[supplement integrity record][supplement-integrity] verifies the 654 files
then present in the original experiment, the same tracked sources and the
71 supplemental input files. These inventories cover different boundaries,
not additional trials. Original trajectories, failures, scores and frozen
inputs remain available; all 11 calibration labels remain candidate.

The original preparation's orchestration parse rejection and two rejected
post-run analysis patches remain separately recorded. They are not native
executor failures or Harbor retries. Independent evidence and document review
results, mechanical checks and final protection checks are retained in the
[review directory][review]; they are not new behavioral runs.

Stop after the four original executions and one authorized supplement. The
exit-status pair has no targeted redundancy to discriminate. Recovery has
successful completion evidence, but continued broad output, construction
failures and an earlier environment-interrupted outcome. Neither result
justifies default adoption or a reliable efficiency claim. Both guidance
candidates and the separate command-construction candidate remain isolated. No
main task baseline, Core/Commit or scoring change follows, and no further
execution is authorized by this record.

Raw artifacts are Git-ignored and local. This tracked synthesis preserves
the findings and limits; a fresh clone without those artifacts cannot
independently reconstruct the audit.
