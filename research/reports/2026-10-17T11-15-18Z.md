# Offline verification cost and an isolated Reward Kit lazy-loading prototype

Repeated provider-library initialization dominates the five measured delivery
shell entries. An isolated lazy-loading prototype reduced their combined observed
time from 5.525s to 0.894s while preserving the exercised task, type, registration
and scoring contracts. It is **not adopted**: missing-dependency errors occur
later, and the copied runtime type definition requires a durable ownership and
drift strategy. These are bounded local observations, not general performance,
model-cost or reliability claims.

## Candidate and evidence boundary

The inspected RSP candidate is fb33f16b19c4f9724a947004170058bdff0d57b5, with no
tracked implementation changes during these experiments. The [dependency lock][lock]
selects harbor-rewardkit 0.2.2 and LiteLLM 1.103.4. The source inspected was the
locally installed package and its retained copies, not a newly fetched upstream
revision. [Source hashes][import-sources] and the [prototype design][design] locate
the exact import boundary and Literal definition examined.

This report consolidates three separate observations: a four-method profile, a
deeper five-entry profile and a baseline/prototype comparison. Their instrumentation
and scope differ; their durations must not be treated as a before/after series.
Original logs, failed probes, package copies, summaries and review verdicts remain
under ignored private evidence directories. This tracked report neither replaces
those records nor makes their private artifacts available in a fresh clone.

No experiment used a real executor model or semantic judge. Existing mocked SDK
boundary tests remain distinct from provider acceptance. No dependency declaration,
installed package, Core/Commit rule, scoring rule or task assertion was modified.

## Four-method offline profile

The [observational driver and records][method-profile] executed each unchanged
method once. All four passed, with no skipped methods, in 33.156s. Module loading
took a separate 1.094s. Main-thread and verification-thread observations retained
command arguments, results and nesting.

| Method scope | Preparation | Reference solution | Verification | Total |
| --- | ---: | ---: | ---: | ---: |
| Workspace preservation | 2.215s | 1.762s | 7.514s | 11.721s |
| Delivery boundaries | 0.547s | 0.322s | 6.892s | 7.953s |
| Outcome/report controls | 0.719s | 0.154s | 4.226s | 5.176s |
| Workflow/product controls | 0.631s | 1.027s | 6.490s | 8.306s |

Preparation totals 4.112s, reference solutions 3.265s and verification 25.122s;
cleanup and other parent/control work account for the remaining 0.658s. The
[phase analysis][method-analysis] checks that these categories reconcile.

There were 351 observed subprocess calls: 165 exits zero and 186 expected negative
verifier exits. Caller-side process construction/exec handshake took 1.306s,
already nested within the phase durations. It does not measure complete interpreter
startup. Separate one-shot Python, Node, bash and Git references were diagnostic
only; multiplying their times by call counts would not establish avoidable cost.

The methods protect different contracts even where task setup repeats: undeclared
writes and protected files; product regressions and object identity; equivalent or
malformed reports; and actual delivery, repeated execution and input drift. The
negative outcomes cannot be deleted as noise. Observed outer directory copies
totaled only 0.314s, so avoiding copying alone offered little measured opportunity
while potentially changing isolation.

## Five-entry import and assertion profile

The next [profile][entry-profile] retained the complete delivery-boundary method
and all five task entries. Each entry invokes the real shell script, which starts
support/grade.py, Reward Kit, checks.py, the isolated verifier and private task
assertions. All five entries returned exit zero and reward 1.0; the complete
method, including its negative controls, passed.

Diagnostic Python profiling and import-time logging measured 10.401s across the
five entries. Reward Kit import intervals totaled 8.641s, containing 8.443s of
LiteLLM import intervals. Actual grade calls totaled 0.408s, including 0.150s in
assertion modules and 0.128s in 19 Git commands. These are nested measurements,
not additive costs. [Detailed analysis][entry-analysis] retains the intervals.

The inspected chain is support/grade.py importing rewardkit.runner, package
initialization importing rewardkit.models, and models importing REASONING_EFFORT
from LiteLLM. The judge and trajectory modules also import LiteLLM eagerly. Thus
offline entry execution loads provider dependencies even without calling a judge.

The 19 Git commands check distinct HEAD/parent, index, committed path/content and
untracked-file facts. Their small measured cost does not justify removing them.
Likewise, identical shell script bytes do not make the five task-specific inputs
interchangeable. This heavier profile adds observer/import-log overhead: its
10.401s total cannot be compared directly with the earlier lighter measurement or
quoted as recoverable savings.

## Isolated prototype and controlled comparison

The [prototype][prototype] copies the installed Reward Kit into separate baseline
and prototype directories. Only three files in the prototype differ:

- models.py uses the exact installed LiteLLM Literal assignment without importing
  the provider package for that type. Its values and source hash are retained.
- judges.py and trajectory.py defer LiteLLM until dependent function use; public
  dependency attribute access resolves to the real module.

The [patch][patch] is confined to those copies. Removing the inserted import guards
restores the original function ASTs. No persistent grader, substituted scoring
engine, skipped shell entry or reduced task coverage was introduced.

Three fresh-process import observations per arm used the fixed order baseline,
prototype, prototype, baseline, baseline, prototype. No heavy profiling hooks
were enabled; both arms used the same interpreter and diagnostic offline guard.
Each task then ran once per arm in baseline-then-prototype order.

| Measurement | Baseline | Prototype |
| --- | ---: | ---: |
| Median package import, three processes per arm | 0.734s | 0.060s |
| Five real delivery shell entries combined | 5.525s | 0.894s |

The [comparison][comparison] records approximately 4.631s less entry time in this
paired run. All five baseline entry processes loaded LiteLLM; none of the five
prototype entry processes did. This supports the identified import-cost mechanism.
The first semantic-dependent use still pays the import cost. Small sample size,
serial ordering and environment effects preclude a general CI speedup or reliability
estimate; none of these measurements represents paid-model savings.

## Exercised equivalence and retained failures

The paired checks established the following bounded results:

- All 17 runtime model field/type descriptions and schema outcomes match. Sixteen
  export JSON Schema; Criterion produces the same existing unsupported-Protocol
  schema error in both arms. The error was compared, not skipped.
- All 24 valid/invalid reasoning-effort cases across LLMJudge and JudgeConfig match,
  including validation errors. The extracted alias equals actual LiteLLM's alias.
- The 23 builtin criterion factories, three registered agent backend names, public
  exports and custom criterion registration/execution match. Direct criterion-handle
  calls retain their TypeError; calls through the module factory succeed.
- Deferred attribute access resolves to canonical LiteLLM. Token/media helper
  behavior and unsupported-media errors match through external SDK mocks.
- Both arms pass the same six unchanged repository test methods, including all
  five delivery tasks, partial-score and unsafe-aggregation rejection, verifier
  errors versus task failures, malformed reports and native-child evidence transport.
- All 49 observed grading outcomes match in order: 38 expected zero rewards,
  six full rewards and five expected RuntimeErrors. Exception messages, semantic
  status and error presence match. Temporary task-directory names alone are excluded
  from this signature comparison; complete traceback equivalence is not claimed.

Two baseline probe failures remain recorded. The first incorrectly assumed every
model exports JSON Schema; the second directly invoked a criterion handle. Separate
later probe versions compare the existing schema error and direct-call rejection.
Original scripts, failed logs and summaries were not overwritten. Completed cold
import observations and task runs were not replayed after those probe corrections.

An explicit [missing-dependency pair][missing-baseline] produces the same
ModuleNotFoundError type, name and message. The [prototype result][missing-prototype]
differs in timing: baseline fails during package import, prototype at first dependent
function use. **Error timing is not equivalent.** Normal offline contract results
do not erase this difference.

## Applicability and decision boundary

The experiment supports investigating lazy loading at the dependency boundary,
while keeping all task inputs, fresh verifier processes, assertions and error
classification. Moving an import inside grade() alone would not avoid it when
every entry calls that function. Bypassing Reward Kit, mocking the core grading
path or reducing five integrations to one is not supported by this evidence.

Adoption remains separate. It requires a durable owner or explicit drift check for
the copied type, a decision about deferred dependency-error timing, and proportionate
compatibility evidence. Actual provider behavior, concurrent first use, broad
introspection/import compatibility and container behavior remain unaccepted here.
No product Spec or architecture decision is changed by retaining this research.
