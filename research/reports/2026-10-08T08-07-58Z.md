# RSP after the research and evaluation rebuild: upstream distillation

RSP has coherent responsibility boundaries in the inspected contracts, but the available evidence does not establish whole-system completeness or efficiency. The initial comparison was too narrow for that judgment: correspondence between upstream guidance and local rules, followed by one successful task pair, cannot establish natural routing, recovery, delivery or Skill contribution. Expanded inspection found a reproducible Harbor/Codex helper incompatibility, evaluator calibration and runtime-provenance gaps, and several untested interactions. The strongest next step is to improve execution fidelity, then measure selected behavior and cost before changing the workflow model.

The findings below describe the inspected state. A subsequent authorized implementation repairs helper creation, adds initial image/source agreement checks and explicit zero-Skill selection; its validation and remaining limits are recorded under [implementation follow-up](#implementation-follow-up). Historical executions and original verdicts remain unchanged.

The subsequent [live model comparison](#live-model-comparison-after-the-host-fix) found that the first host fix was incomplete: helper creation succeeded, but the model's login-shell command still could not find `apply_patch`. Six fresh trials preserved correct judgments without establishing an overall efficiency improvement. The later [stable command-path repair](#stable-command-path-repair) addresses the observed invocation failure.

## Expanded assessment: breadth, depth and confidence

This extension examines the complete path from intent to durable outcome. It uses current local contracts and implementation, retained native executions, pinned upstream sources and credential-free container probes. It adds no paid executions and adopts no product changes. The six successful reassessments below remain evidence for one completion boundary, not an overall acceptance result.

Across sources, the comparison asks the same questions: what failure does the mechanism address, who owns the decision and effect, what evidence proves success, how does interruption change that evidence, and what operating cost or additional state does the mechanism introduce? Similar wording is weaker evidence than a traced production path; a successful output is weaker evidence of contribution than a matched comparison.

This is a cross-boundary assessment, not an exhaustive security, performance, CLI/TUI or concurrency audit. Most native fixtures are small controlled workspaces. Larger repositories, different models and actual host interruptions remain outside the observed behavior. Wider reading increases the range of hypotheses; it does not increase the statistical strength of the six trials.

### Confirmed: the evaluation host breaks Codex helper creation

All six original executions in `2026-10-08T08-44-56.585158Z` contain the startup warning `Refusing to create helper binaries under temporary dir` and later encounter `apply_patch: command not found`. Agents recover with ordinary file-writing commands, so the correct reports conceal a degraded execution environment. These are host/tool failures, not six failures of the completion policy.

The causal chain is local and inspectable. Installed Harbor 0.24.0 sets `Codex._REMOTE_CODEX_HOME` to `/tmp/codex-home`. The [RSP adapter](../../tests/skills/support/agent.py) inherits that location and only repairs routed model identifiers. In the current `rsp-eval-agent:2026-10-08` image, Codex CLI 0.150.1 rejects helper creation under that temporary root. A credential-free `docker run --rm --network none` probe running `codex --version` reproduces the warning with that home. Using `/root/rsp-probe-codex-home` in the same disposable container removes the warning and creates an `apply_patch` helper under its `tmp/arg0/` directory. No executor or judge was called.

The minimal candidate is a compatible home location in the existing adapter, with a regression on the actual native setup path. Acceptance must cover helper availability and retained configuration, sessions, Skills and artifact collection; a successful version command alone does not prove those lifecycle properties. Teaching Skills to fall back from the broken helper would encode an environment defect in the wrong owner. This report identifies the fix boundary but does not implement it.

### Confirmed evidence limitation: passing tasks do not establish Skill contribution

The paired completion campaign demonstrates six correct assessments under the captured default selection. It has no matched baseline or narrower-capability arm. It therefore cannot show whether RSP caused the successes or whether the same outcomes would be obtained with less context. The normal wrapper also lacks an explicit zero-Skill selection; direct native Harbor configuration can express it. That is a wrapper limitation, not a new evaluation-engine requirement.

Task design affects the claim. A literal prompt scan finds RSP or `rsp-` in 11 of the 18 task instructions; this is a discoverability clue, not a measure of prompt leakage. [Shape-cache](../../tests/skills/tasks/shape-cache/instruction.md) explicitly supplies the injected clock, expiry equality and before/equal/after cases. [Native-coordination](../../tests/skills/tasks/native-coordination/instruction.md) explicitly requires worker independence and order. These are useful compliance tests, but weak evidence that an agent would discover the need unaided. [Implement-checkout](../../tests/skills/tasks/implement-checkout/instruction.md) provides a more natural symptom; the whole catalog should not be dismissed as coached.

Skill-Use-Bench distinguishes trigger, compliance and boundary behavior; SkillOpt provides a useful model of bounded edits checked on held-out work. Transfer the experimental distinction, not their reported performance or an automatic optimization loop. Reuse a few existing tasks with neutral user intent, matched baseline/selected-capability/default-suite arms and cases where coordination should stay inactive. Judge outcomes and authority, not literal Skill reads or a prescribed routing trace. Keep model, tools, project policy and environment fixed. The default evaluation configuration injects eight Skills including optional structural audit, whereas the published default suite has seven; state the tested selection when making product claims.

### Measured cost, unresolved cause: inspect the chosen route before shortening prose

The six original native executions report **1,026,260 total input tokens**, with per-trial totals from **138,818 to 226,431** and median **148,901.5**. These are accumulated native usage values, not unique context size, uncached billed tokens or a monetary bill. The campaign took 21 minutes 39 seconds at concurrency one. Those measurements justify investigating cost; there is no matched efficiency baseline establishing waste.

Command requests repeatedly mention Core, Review, Verify and their references. Repeated read requests are diagnostic evidence, not proof of repeated full consumption: the inspected output does not establish whether host capture, loading behavior or model choice explains each repetition. A local run of [the context scanner](../../scripts/scan-skill-context.mjs) found all scanned references reachable and only one exact repeated-paragraph group. Entry word counts range from 758 to 1,617 across the eight packages; words are not model tokens, and standalone packages legitimately retain their authority safeguards. Static duplication alone is a poor target.

A narrower route is a testable alternative. [Review](../../skills/rsp-review/SKILL.md) already owns fixed-scope semantic assessment and authorized checks; [Verify](../../skills/rsp-verify/SKILL.md) owns a selected WorkOwner's declared evidence boundary. Core already rejects forced handoffs. Compare Review-led assessment with the observed multi-capability loading while preserving required checks and findings. Only demonstrated equivalent outcomes with lower cost justify simplifying selection or guidance. Fix the host helper first so environment-recovery overhead does not confound that comparison. Do not merge Review and Verify merely because both appear in a trace.

### Confirmed calibration limit: the evaluator needs independent discrimination evidence

The completion pair exposed three distinct evaluator defects: unnecessarily literal report assertions, missing native execution input, and missing transport of that input to a separate verifier container. Schema checks and deterministic oracle/nop runs could not detect all three. The repaired test now uses the native artifact upload path and the actual RewardKit prompt consumer, mocking the model boundary. This is stronger evidence of input delivery; it is not independent evidence that every semantic judgment is correct.

All nine [retained calibration samples](../../tests/skills/calibration/README.md) have `label_status: candidate`, covering doc-export, shape-cache and review-staged. Agreement with those labels is author-label agreement. Original completion judges also differed when native evidence was absent: four rejected execution claims and two accepted while noting the gap. This demonstrates sensitivity to evidence availability and rubric interpretation. It does not prove that the judge is generally unreliable. Executor and judge sharing a model family adds a possible correlated-error risk, not an observed bias estimate.

The smallest useful improvement is human examination of selected positive and negative cases through the existing calibration process: plausible but false execution claims, equivalent valid wording, wrong candidate evidence and unauthorized effects. Distinguish unavailable evidence from observed behavioral failure. Use real transport checks where rubrics depend on native evidence; do not add transcript requirements to artifact-only judgments. A second scoring platform or compulsory second-model review is not justified.

### Code-supported prevention gap: bind the initial image to the claimed inputs

[Evaluate](../../tests/skills/evaluate.py) snapshots selected Skills, tasks, support, lockfile and source identity; injected Skills are copied to immutable sibling inputs. Resume checks support/lockfile and Docker image identity. It would be incorrect to claim that these runs consume mutable live Skill files. However, [image construction](../../tests/skills/build_image.py) separately bakes the CLI and support into the image. The initial run records the image ID without checking that embedded files match the newly captured local sources.

Thus changing support or rebuilding the CLI without rebuilding the image could produce a fresh source snapshot paired with old execution bytes. This is a reachable prevention gap, not an observed stale-image incident: current SHA-256 comparisons found all five embedded support files and the packaged CLI identical to the corresponding host files. It does not invalidate the retained campaign.

Prefer a small build-provenance check or direct comparison at initial execution. Acceptance should deliberately change a relevant input without rebuilding and establish that the mismatch is detected, then pass with matched bytes. Image ID alone identifies an image but cannot establish the relationship to the claimed source. Reuse the existing snapshot and build owners; no new global provenance registry is needed.

### Coverage gap: exercise recovery and terminal outcomes as composed behavior

The [readiness implementation](../../src/core/readiness.ts) deliberately returns `semantic: needs-review` even when deterministic gates permit archive. [Archive](../../src/commands/archive.ts) checks gates under a lock, moves the record and then clears focus; a cleanup warning must preserve the actual archive outcome. Core owns durable writeback and semantic convergence. Commit owns exact authorized delivery and its failure boundary. This separation is deliberate, not a missing semantic check in the CLI.

[Lifecycle integration tests](../../tests/code/integration/cli-lifecycle.test.ts) already cover declared verification gates, Group child requirements and recovery restrictions. The [migration inventory](../../tests/skills/migration.md) nevertheless records behavioral gaps. No inspected task demonstrates the complete sequence of current Spec writeback, required review, archive, then commit failure or uncertain effects. Nor does the happy-path coordination task prove recovery after a required worker partially mutates files and its live identity is lost.

Select one or two composed scenarios. First, after archive succeeds and commit fails, continuation should report archived-but-undelivered, inspect effects and preserve the Commit retry boundary instead of reopening or replaying automatically. Second, after an interrupted required review, recovery should preserve completed work and staged user bytes, re-establish current authority and evidence, and either obtain attributable independent acceptance or report its absence. Changed candidate bytes must invalidate affected old results. A seeded fixture tests interpretation; only controllable live interruption establishes runtime recovery.

Planning-with-files provides useful questions for recovering location, goal and next action, but its additional planning ledgers would duplicate RSP ownership. LangGraph demonstrates why runtime identity belongs to the executing host. Keep worker liveness, cancellation and isolation there; neither a persisted worker registry nor a phase engine inside RSP follows from these gaps.

### Usability opportunity: test knowledge after the author context disappears

Doc already requires reader navigation, factual consistency and correct ownership. Anthropic's doc-coauthoring method suggests a targeted fresh-reader check: after a meaningful Change closes, can a reader using only stable context and linked Specs identify the current behavior, prerequisites, command and known limits? A polished Change is not proof that its lasting knowledge is findable. This is an unmeasured usability hypothesis, not a demonstrated documentation defect. Use it selectively when writeback materially changes a consumer path; do not add a mandatory phase or a second memory ledger.

Research preparation already has pinned captures, per-source progress and effect-aware resume in [research operations](../README.md) and [refresh](../../scripts/research/refresh.mjs). Preserve the distinction between material acquisition and reading depth. The adoption question should remain source practice → local problem → alternative → bounded change → acceptance, using the existing Change owner. A refresh count or longer source list is not evidence of improved RSP behavior.

## Candidate 1: test omitted acceptance despite passing declared checks

**Observation.** OpenSpec's verification template starts from requirements and scenarios, while Spec Kit's analysis explicitly looks for requirements with no associated task. RSP has equivalent intent distributed across Shape and Review, and deliberately narrower Verify semantics. At the inspected baseline, the examined native tasks did not isolate the boundary where all declared checks pass and all Tasks are checked, but one settled Spec requirement was omitted from both implementation and verification.

The nearby tasks cover different failures: [verify-boundary](../../tests/skills/tasks/verify-boundary/instruction.md) has an observed product failure and an unavailable external check; [owner-decision](../../tests/skills/tasks/owner-decision/tests/judge.toml) has an unresolved choice and old-snapshot evidence; [workflow-catalog](../../tests/skills/tasks/workflow-catalog/environment/workspace/.rsp/changes/catalog-refresh.md) has an explicitly unfinished generation step; [shape-cache](../../tests/skills/tasks/shape-cache/instruction.md) supplies the required edge cases in the prompt. These remain useful tests, but their passes do not answer the omission question.

**Risk and uncertainty.** An agent might treat the declared checklist as exhaustive and overstate completion. This is an untested hypothesis, not an observed RSP failure. [Work model](../../.rsp/specs/work-model.md#evidence-and-closeout) already says CLI readiness is not semantic acceptance; a Verify pass alone would be correct within its declared boundary. The suspected failure would be the owner's overall completion claim or a missed Review finding.

**Smallest investigation.** Add one native fixture with a clearly settled requirement, an implementation missing that behavior, and a passing but incomplete Required check. Keep authority and expected behavior unambiguous. Ask for a fixed-scope completion assessment, with repair and lifecycle mutation forbidden. Judge whether the agent identifies the omitted contract, limits the passing check, and withholds whole-outcome completion. Use an otherwise equivalent fully implemented control to detect invented gaps. Score findings and authority preservation rather than exact wording or a mandatory traceability table.

**Next owner and decision.** Shape should settle that task's evidence boundary before task authoring. Run the existing Skills first under separately authorized evaluation. Change Skill guidance only if the task demonstrates a repeatable failure; place any correction in the existing planning/review/completion owner. There is no current basis for broadening Verify into a semantic reviewer.

## Candidate 2: make contribution distinguishable from successful execution

**Observation.** Anthropic's Skill Creator pairs new Skills with a no-Skill baseline and revised Skills with their previous version. Its analyzer asks whether assertions pass in both conditions and whether time/token costs rise without an outcome benefit. Superpowers' pressure-testing reference also starts from observed behavior without the Skill. Their mechanisms motivate a contribution question, not a requirement to force a baseline failure.

In RSP's [run implementation](../../tests/skills/evaluate.py), an empty `args.skill` selects the default Job's Skills; the CLI offers repeated `--skill` paths but no explicit empty selection or per-run Job file. A no-Skill executor run is possible by editing the shared native Job configuration, or by direct Harbor configuration. The documented direct-native path lacks the wrapper's input snapshot and cannot use wrapper resume. This is a confirmed per-run selection limitation, not a claim that Harbor cannot run a baseline. An oracle or nop control answers a different question and cannot replace a capable executor without injected Skills.

The inspected nine-pass mixed-workflow run establishes successful execution with the recorded Skills. It contains no matched no-Skill arm, so it cannot establish how much RSP improved those outcomes or whether a narrower Skill selection would suffice. The [earlier consolidation](2026-10-07T14-19-03Z.md#useful-investigation-leads) already identified task benefit and coordination cost as open questions. This study grounds that lead in the current native runner; it does not present it as a newly discovered product defect.

**Smallest investigation.** Select a task where responsibility or authority matters and a concrete capability whose contribution is in question. Compare the current selection with a targeted ablation or, where meaningful, zero injected Skills. Keep the business prompt, project policy, task, model, effort, tools, grader and environment matched. A prompt explicitly requiring a named installed Skill needs a neutral version shared by both arms before the comparison is meaningful. Preserve the same CLI and project policy in both arms, and describe the result as an injection ablation, not the absence of all RSP influence.

Read outcome, authority violations, failures and time/token use together. A repeated pass in both arms is useful evidence against adding instructions for that task; token reduction alone is not improvement. Use varied observations proportionate to the claim, without making a small repetition count a reliability threshold.

**Next owner and decision.** Shape should choose the comparison and whether repeated use warrants a small per-run empty-selection capability in the existing wrapper. A single investigation can use the existing native configuration with its documented retention limits. Do not build a baseline registry, another matrix engine or a new release gate. Product simplification needs measured evidence after the comparison, not an assumption that less guidance is equivalent.

## Candidate 3: cover interrupted independent-worker recovery

**Observation.** Superpowers' recovery notes explicitly address completed work being dispatched again after context loss. RSP's current recovery contract already handles the underlying problem more generally: inspect effects before replay, preserve owner and authority, distrust transient liveness across sessions, and require attributable independent-worker evidence.

The native [coordination task](../../tests/skills/tasks/native-coordination/instruction.md) exercises a successful implementation worker followed by a fresh reviewer. [Recovery-export](../../tests/skills/tasks/recovery-export/instruction.md) exercises continuation when an optional helper is unavailable. The [migration inventory](../../tests/skills/migration.md#old-case-disposition) explicitly retires interrupted multi-worker recovery and unavailable worker acceptance. Passing the first two scenarios does not establish the retired behavior.

**Risk and uncertainty.** After interruption, an agent could repeat an already completed mutation or claim independent acceptance from a stale reviewer message. Neither behavior was observed in this study. Native Harbor job-resume preservation tests concern the evaluation infrastructure; they are not evidence that RSP agents recover their own multi-worker task correctly.

**Smallest investigation.** Exercise a completed implementation with preserved staged user work and an unfinished or unavailable independent review. Require evidence inspection, preservation of completed bytes/index, and either a fresh attributable review or an explicit incomplete-acceptance result. Observe real worker identities and command effects where claimed. A seeded interrupted-state fixture can first test interpretation; it must not be described as a demonstrated live interruption/resumption. A real interruption campaign should follow only if the host exposes the needed controllable lifecycle.

**Next owner and decision.** Shape should select the host-supported evidence boundary. Start with one high-value recovery case, rather than restoring all retired cases or expanding the recovery prose. A demonstrated failure should be corrected in Core's existing recovery guidance or the responsible host adapter.
