# RSP reliability, execution cost and rule burden

The retained evidence supports keeping RSP's core authority and recovery
boundaries. The strongest remaining execution-quality concern is repeated
command construction failure. Smaller evidence reads and fewer fragmented
acceptance cycles are plausible cost improvements; neither a broad Core rewrite
nor additional rules is justified by these observations. This assessment closes
the bounded inspection, not the remaining reliability questions.

## Scope and applicability

This read-only assessment examines candidate
4077abfafd8770c633790f423bbbfacc787694f5 against retained native tasks,
root/worker trajectories and frozen inputs. All 41 files in the seven core
Skills captured for the [full run][inputs] match the current authored Skills,
with no added files in those seven directories. That supports applicability to
the current Skill text; it does not make old task, grader, runtime or model
inputs equivalent to every current input.

The full run used AI-HUB/gpt-6.1-sol at medium effort, with semantic judging by
openai/AI-HUB/gpt-6.1-sol at high effort, one sample on 38 tasks. Harbor was configured for
one attempt per task and zero automatic task retries. This assessment uses those
observations, not a new execution, regrade, judge call or performance experiment.
Report exception boundaries, production telemetry and the unadopted lazy-loading
prototype are outside scope.

missing records. These are observed counts for one frozen run, not a general

These follow-ups changed task inputs. Their passes cannot replace the original
scores, be combined into a new full-suite pass or establish that Skill behavior
improved. Each remains limited evidence of the clarified contract.

The full run also passed prerequisite-stop, correction-limit,
commit-tracked-restraint, natural/continued correction and interruption recovery
tasks. A prior
[interruption observation][interruption] retains partial output, original writer
exit and worker completion before a fresh continuation worker starts, without
duplicate output or correction-count reset. This supports cooperative cessation
and continuation under that contract, not arbitrary crashes or every recovery
mode.

Command construction failures recur across separate retained runs. The
[original corpus][commands] contains JavaScript wrapper and Python string
failures; the later [call-chain addendum][chain] identifies both a pre-dispatch
wrapper failure and a dispatched Python syntax failure in a finally successful
commit-restraint trial. The release/tracked-restraint validation retains another
pre-dispatch wrapper failure. Final reward 1 does not mean error-free execution.
Expected negative checks, these unexpected failures, and Harbor retries remain
different categories. No corpus-wide failure rate or Core-level cause follows.

## Execution cost

Reaggregation of the original full-run root/descendant sessions reproduces its
executor totals; all 41 trial usage records are available.

| Job wall time | 5,631.722 seconds, about 93.86 minutes |
| Median trial duration | 120.3 seconds |
| Executor input tokens | 7,463,347 |
| Included cached input tokens | 6,180,480 |
| Executor output tokens | 108,628 |

Cached input is included in input, not additional usage. These totals exclude
judges and do not establish fees, savings or the share attributable to Skill
text. The full-run analysis reports time-correlated judge gateway usage
separately; its correlation is not native request-ID attribution.

Some expensive work is explicitly required. [native-coordination][coordination-task]
requires an implementation worker, a different reviewer and reviewer execution
of the check. [review-evidence-reuse][reuse-task] requires distinct workers but
explicitly permits reuse of the implementer's applicable passing check. Its
[retained sessions][reuse-sessions] show the implementer running the check after
the edit and the reviewer inspecting source, contract and evidence without
rerunning it. Worker count or total tokens alone therefore cannot diagnose
over-delegation or redundant verification.

There is narrower evidence for avoidable work: failed command construction,
checks repeated to recover an obscured exit status, and whole-trajectory reads.
The [bounded evidence study][reading] reconstructs a stop/continuation chain
using 23,815 bytes selected from 711,164 bytes of three retained sessions,
with identities, call/result links and required cessation facts preserved.
It also demonstrates that collecting a check's own exit status avoids masking
it with a following successful git status command. These are offline feasibility
results, not observed future-model adoption or measured token savings.

## Rule burden and evidence gaps

Current [Core][core] allows bounded direct work without tracking preflight and
does not require a worker, separate review or rerun for every phase transition.
In the [bounded-fix trajectory][bounded-sessions], six recorded tool calls include
one Implement Skill load, a failing pre-fix check and final verification; the
model did not create a Change or dispatch workers. The added before/at/after
expiry probe is not evidence of a blind rerun merely because the check also
appears before and after a source correction.

The maintainer interaction preceding this assessment repeatedly separated
small report boundaries into individual control, fix, review and commit cycles.
That is a local process observation, not a measured general property of RSP.
Core already supports compatible finding batches and evidence reuse. Changing
that usage pattern does not require another global workflow rule.

Rule length and repeated reading remain candidates for investigation, but
there is no matched rule-ablation experiment isolating their effect. Removing
independent review, cessation evidence or exact commit snapshots merely because
their tasks cost more would remove required protections without establishing
equivalent reliability.

Other gaps remain explicit: one full round does not establish repeated
stability; follow-ups with changed inputs are not matched efficiency comparisons;
provider/model portability is untested here; and the [11 calibration samples][labels]
remain candidate. Their AI assessment and original judge agreement do not supply
human ground truth or broad false-positive/false-negative rates.

## Priorities and stopping conditions

These priorities are recommendations, not authorization for changes or paid runs.
P1 here denotes the next useful work, not a release-blocking severity claim.

| Priority | Question or action | Evidence boundary and stopping condition |
| --- | --- | --- |
| P1 | Treat recurrent command construction failures as execution-quality work. | Existing syntax and byte-preservation evidence already locates the failure layers. Stop expanding that corpus without a new failure class. Do not claim model behavior fixed, weaken commit checks or add a global prompt rule without supporting evidence. |
| P1 | Keep task reliability conclusions version- and attempt-specific. | Record the original failures and the distinct clarified-task passes. If future stability validation is authorized, predeclare tasks, configuration, attempts and budget; retain all outcomes and stop at that boundary rather than supplementing until green. No run is authorized here. |
| P2 | Reduce unnecessary evidence reading, exit-status recovery and fragmented acceptance cycles. | Use bounded evidence sufficient for the causal claim, capture the check's own result, and batch related work. Stop when required independence, provenance and checks are established; do not replay unchanged checks simply because the role changed. Cost savings remain unmeasured. |
| P3 | Consider targeted rule simplification. | Require a concrete repeated misroute, unnecessary load or redundant obligation before proposing deletion. Preserve authority, failure-stop and recovery semantics. Without such a case, stop without editing Core. |
| Deferred | Broader stability, cross-model behavior and human calibration. | Keep them as unanswered questions. Do not substitute more offline report exceptions for these experiments or promote candidate labels. |

No further rule correction is justified by this assessment alone. The next
useful intervention should be one bounded execution-quality or cost question,
with a fixed endpoint; this is not a standing instruction to seek another
testable edge case.
