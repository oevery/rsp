# Migrating from RSP 2.x to 3.0

This guide applies to projects already initialized with RSP 2.x. New projects can use `rsp init` directly.

## Before upgrading

1. Commit or back up the project's current `.rsp/` and project-owned instruction files.
2. Finish or record the state of active work so path and ownership conflicts can be resolved deliberately.
3. Note any custom content under `.rsp/rules/`; `rsp update` removes only the obsolete generated fallback and does not decide where custom project instructions belong.

RSP 2.x and 3.0 should not be used concurrently to mutate the same project. Complete the migration before resuming normal Change lifecycle operations.

## Required migration

1. Upgrade the CLI with `npx -y @oevery/rsp@latest update`. RSP 3.0.0 was not published to npm; the current stable package performs the same 2.x artifact migration and includes later compatibility fixes.
2. Run `rsp update` from the project root. This creates `.rsp/rsp-rules.md`, refreshes the managed RSP block in `AGENTS.md`, rebuilds generated indexes, and removes the obsolete generated `.rsp/rules/rsp-rules.md`.
3. Inspect any remaining `.rsp/rules/` entries:
   - Move stable scoped operating instructions to the nearest project-owned `AGENTS.md` outside the managed RSP block.
   - Move stable current design facts to the smallest relevant file under `.rsp/specs/`.
   - Move lasting rationale only to the configured authoritative Decision Record directory when it records a real hard-to-reverse tradeoff.
   - Remove residual files only after their durable content has been preserved or deliberately judged unnecessary.
4. Flatten work paths deeper than `.rsp/changes/<group>/<change>.md`. RSP 3.0 supports flat Changes and one direct Change Group level only.
5. Resolve every `.rsp/changes/<name>.md` and `.rsp/changes/<name>/` identity collision manually.
6. Review `.rsp/config.yaml`. Only `kinds` and `decisions` are supported:
   - Omitted or empty `kinds` uses the built-in kinds.
   - A non-empty `kinds` list replaces the built-in kinds.
   - `decisions.path` selects one project-relative authoritative Decision Record directory outside other `.rsp/` core locations.
7. Run `rsp doctor`, then `rsp check`. Resolve every error before focusing, creating, or archiving work.

## Behavioral changes to account for

- `.rsp/rsp-rules.md` is the only runtime fallback protocol. Project-specific instructions no longer belong in generated RSP rules.
- The `rsp init --with-project-rules` option and `rsp add rules` command are removed.
- WorkRefs are typed and bounded. Unsupported directories, symlinks, missing targets, recursive Groups, and ambiguous identities fail visibly instead of being normalized or skipped.
- Exact prerequisites use ``- requires `<change-work-ref>`: <reason>`` in `## Blockers`; readiness and execution waves are derived by `rsp status`.
- Change templates still use the six canonical sections, but Tasks now describe executable outcomes and Verify records evidence plus omitted or unavailable coverage. Durable review is a separate semantic decision.
- Invalid or unsupported `.rsp/config.yaml` values now fail closed across ordinary CLI consumers and `rsp doctor`.

## Validate the migration

Run:

```bash
rsp doctor
rsp status --json
rsp check
```

Confirm that:

- `doctor` reports a healthy setup and the intended authoritative Decision Record directory;
- every focus marker resolves to an executable Change;
- `status --json` reports the expected ready work, blockers, dependency edges, and waves;
- `check` reports no invalid Change structure or unresolved migration error;
- project-owned instructions and Specs contain the durable content intentionally retained from `.rsp/rules/`.

## Recovery

If validation fails, stop normal RSP mutations. Restore the pre-upgrade snapshot when a quick rollback is required, or correct the reported path/configuration issue and rerun `rsp update`, `rsp doctor`, and `rsp check`. Do not use `doctor --fix` to make semantic decisions about custom rules, path conflicts, current facts, or rationale.

For unresolved migration defects, open an issue at <https://github.com/oevery/rsp/issues> with the CLI version, failing command, redacted diagnostics, and the relevant non-secret `.rsp/` structure.
