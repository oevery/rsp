# Migrating from RSP 2.x to 3.0

This guide covers the original 2.x-to-3.0 artifact transition using the current stable CLI, including later compatibility changes. The filename identifies the artifact transition, not a pinned CLI version. New projects can use `rsp init` directly.

Historical 3.0 created generated navigation indexes and supported only `kinds` and `decisions` configuration. The current CLI reads Specs directly, removes only recognized generated indexes, and also supports `manage` and `language`. Follow the current steps below; retained 3.0 release claims remain historical.

## Before upgrading

- Use Node.js 22 or newer before invoking the upgraded CLI; the historical 3.0 runtime requirement is not sufficient for current versions.
- Commit or back up the project's current `.rsp/` and project-owned instruction files before migration edits. Keep a recoverable copy of unsupported legacy configuration as well as custom rules.
- Finish or record the state of active work so path and ownership conflicts can be resolved deliberately.
- Note any custom content under `.rsp/rules/`; `rsp update` removes only the obsolete generated fallback and does not decide where custom project instructions belong.

Do not use old and upgraded CLIs concurrently to mutate the same project. Complete the migration before resuming normal Change lifecycle operations.

## Required migration

1. Select the upgraded CLI and confirm its version before mutation. With package-fetch authority, `npx -y @oevery/rsp@latest --version` discovers the stable version but does not upgrade an independently installed `rsp`. Record the returned version, then use `npx -y @oevery/rsp@<version> <command>` throughout, replacing `<version>` with that exact value; do not repeatedly resolve `@latest`. Alternatively, explicitly upgrade and verify the installed CLI, then keep that executable/version unchanged. The commands below use `rsp` as notation for this selected invocation. RSP 3.0.0 was not published to npm; the stable package performs the original artifact migration and later compatibility changes.
2. Diagnose configuration compatibility before `update` with the selected CLI's `config --json`. Current top-level keys are `kinds`, `decisions`, `manage` and `language`. Invalid legacy fields such as `required_sections` prevent both a successful projection and update. On failure, read the diagnostics and backed-up YAML; preserve unsupported settings' meaning in an appropriate project-owned instruction or contract, or obtain an owner decision before removing them. Retain valid settings and rerun `config --json` until it succeeds; raw YAML is diagnostic input, not an effective configuration summary.
   - Omitted or empty `kinds` uses the built-in kinds; a non-empty list replaces them.
   - `decisions.path` selects one project-relative authoritative Decision Record directory outside other `.rsp/` core locations.
   - `manage` selects activation and a qualified closeout ceiling, not mutation or Git authority.
   - `language` selects durable artifact/commit prose, not response language.
3. Run the selected CLI's `update` from the project root. This creates `.rsp/rsp-rules.md`, refreshes the managed RSP block in `AGENTS.md`, and removes the obsolete generated `.rsp/rules/rsp-rules.md`. Current versions do not rebuild navigation indexes: they remove only recognized generated indexes after safe preflight. If a reserved path contains owner-controlled content, preserve or relocate that content deliberately before retrying; do not force deletion to obtain success. Use `rsp specs` for current navigation.
4. Inspect any remaining `.rsp/rules/` entries:
   - Move stable scoped operating instructions to the nearest project-owned `AGENTS.md` outside the managed RSP block.
   - Move stable current design facts to the smallest relevant file under `.rsp/specs/`.
   - Move lasting rationale only to the configured authoritative Decision Record directory when it records a real hard-to-reverse tradeoff.
   - Remove residual files only after their durable content has been preserved or deliberately judged unnecessary.
5. Flatten work paths deeper than `.rsp/changes/<group>/<change>.md`. RSP supports flat Changes and one direct Change Group level only.
6. Resolve every `.rsp/changes/<name>.md` and `.rsp/changes/<name>/` identity collision manually.
7. Run `rsp doctor`, then `rsp check`. Resolve every error before focusing, creating, or archiving work.

## Behavioral changes to account for

- `.rsp/rsp-rules.md` is the only runtime fallback protocol. Project-specific instructions no longer belong in generated RSP rules.
- The `rsp init --with-project-rules` option and `rsp add rules` command are removed.
- WorkRefs are typed and bounded. Unsupported directories, symlinks, missing targets, recursive Groups, and ambiguous identities fail visibly instead of being normalized or skipped.
- Exact prerequisites use ``- requires `<change-work-ref>`: <reason>`` in `## Blockers`; readiness and execution waves are derived by `rsp status`.
- Change templates still use the six canonical sections, but Tasks now describe executable outcomes and Verify records evidence plus omitted or unavailable coverage. Durable review is a separate semantic decision.
- Invalid or unsupported `.rsp/config.yaml` values now fail closed across ordinary CLI consumers and `rsp doctor`.

## Validate the migration

Keep using the selected executable/version. For the registry-selected route, replace `rsp` below with `npx -y @oevery/rsp@<version>` using the exact version recorded before migration; do not fall back to an older installed binary.

Run:

```bash
rsp doctor
rsp status --json
rsp check
```

Confirm that:

- `doctor` reports a healthy setup and the intended authoritative Decision Record directory;
- every focus marker resolves to an executable Change;
- `status --json` reports the expected ready work, blockers, dependency edges, and waves;
- `check` reports no invalid Change structure or unresolved migration error;
- project-owned instructions and Specs contain the durable content intentionally retained from `.rsp/rules/`.

## Recovery

If validation fails, stop normal RSP mutations. Restore the pre-upgrade snapshot when a quick rollback is required, or correct the reported path/configuration issue and rerun `rsp update`, `rsp doctor`, and `rsp check`. Do not use `doctor --fix` to make semantic decisions about custom rules, path conflicts, current facts, or rationale.

For unresolved migration defects, open an issue at <https://github.com/oevery/rsp/issues> with the CLI version, failing command, redacted diagnostics, and the relevant non-secret `.rsp/` structure.
