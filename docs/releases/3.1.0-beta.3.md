# RSP 3.1.0-beta.3

RSP 3.1.0-beta.3 makes project history easier to navigate and incomplete work safer to recover, while tightening managed closeout and clarifying the published Skill surface. It is intended for opt-in evaluation of repository-native lifecycle work without granting remote delivery or publication authority.

## Recoverable history and bounded navigation

- Use `rsp history` as the authoritative bounded archive query instead of a generated global Archive Index. TUI History and status archive trends consume the same validated inspection path.
- Navigate Specs through generated per-directory `00-index.md` files that list only direct child Specs and populated child directories. Decision Records remain outside the Specs projection.
- Run `rsp update` to migrate recognized generated Archive and Specs indexes. Unrecognized files at reserved paths are preserved for explicit owner review rather than overwritten or removed.
- Restore an archived executable Change with `rsp reopen <work-ref> --reason <text>` when fresh evidence disproves its original acceptance. The archive remains immutable, multiple matches require exact `--from` selection, and genuinely new scope still belongs in a new corrective Change.

## Deterministic managed closeout

- Qualify long-running continuation and interruption recovery independently from parallel work, and rederive routing when a direct task materially expands into a larger implementation boundary.
- Invoke local Commit once for an eligible, qualified, clean, verified non-small terminal boundary. Small terminal work, recovery checkpoints, lifecycle mutation, push, tag, and publication keep their separate authority requirements.
- Gate automatic lifecycle and local closeout on the current Manage qualification so configuration cannot grant closeout after Core declines or stops selecting Manage.

## Skill identities and migration

- Use `rsp-resolve-findings` instead of `rsp-address-review` for correcting accepted findings and requesting re-review.
- Use the optional `rsp-structural-audit` instead of `rsp-codebase-audit` for report-only evidence-backed structural risk discovery.
- Existing obsolete package-owned directories require an explicit force-gated transactional migration. Preview and apply it with the exact prerelease package:

```bash
npx -y @oevery/rsp@3.1.0-beta.3 skills install --dry-run --force
npx -y @oevery/rsp@3.1.0-beta.3 skills install --force
```

The installer preserves unrelated Skills, rejects unsupported obsolete targets, and restores prior directories if replacement activation rolls back. Full upgrade details are in the [3.1 migration guide](../migrations/3.1.md).

## Readiness and structural audit

- Use `rsp ready <work-ref>` as the canonical read-only readiness projection. `rsp archive <work-ref> --dry-run` remains a deprecated compatibility route to the same human result.
- Structural Audit now distinguishes selection heuristics from Findings: history may select a candidate chain, and shallow indirection may be tested by deletion reasoning, but every Finding still requires a reachable trigger, concrete impact, and owner evidence.
- Published Skill tests now protect portable metadata and semantic behavior rather than imposing mechanical body word caps.

## Opt-in usage

Pin the exact prerelease identity rather than relying on a moving dist-tag:

```bash
npx -y @oevery/rsp@3.1.0-beta.3 init
npx -y @oevery/rsp@3.1.0-beta.3 update
npx -y @oevery/rsp@3.1.0-beta.3 doctor
```

RSP 3.1 requires Node.js 22 or newer. Users upgrading directly from a registry-installed 2.x release must first follow the [RSP 3.0 migration guide](https://github.com/oevery/rsp/blob/v3.0.0/docs/migrations/3.0.md).

## Compatibility and known limitations

- This prerelease remains opt-in; publishing it under the npm `beta` dist-tag does not promote npm `latest`.
- The exact candidate is covered by the self-host release gate and clean-install package check. Broader real-project lifecycle acceptance, provider-backed structural-audit evaluation, and comparative productivity remain unverified.
- Commit, push, tag, GitHub Release creation, npm publication, deployment, and external post-publication verification require separate authority and are not implied by the candidate itself.
