# RSP 3.1.0-beta.4

RSP 3.1.0-beta.4 makes multilingual collaboration durable without constraining conversation language, strengthens WorkRef identity for Unicode projects, and makes automatic Manage routing more decisive while preserving conservative execution boundaries.

## Durable language without conversation lock-in

- Configure one shared default for artifact and commit prose with optional per-surface overrides. Response language remains owned by each user and session rather than repository configuration.
- Reject unsupported `language.response` configuration instead of silently forcing one collaboration language across a project.
- Generate canonical RSP scaffolds with neutral `<…>` placeholders and verbatim user input so the CLI does not invent conflicting English prose.
- Keep existing artifact language stable unless translation is explicitly authorized; configuration grants no Git action or translation authority.

## Safe Unicode work identity

- Use lowercase or caseless Unicode letters, marks, and decimal numbers in WorkRef segments, including direct grouped identities such as `听说训练/模拟朗读`.
- Normalize command input to NFC, bound both code-point and UTF-8 byte lengths, and reject unsafe punctuation, traversal, unsupported depth, non-canonical stored paths, and normalization collisions.
- Preserve existing ASCII lowercase kebab-case identities without migration or byte changes.

## Lossless semantic document structure

- Route Change and Group Brief readers through stable semantic section identities instead of scattered heading strings.
- Preserve canonical Markdown as the storage format; localized or near-match headings are not accepted as protocol aliases.
- Keep source text and exact section spans so `reopen` and other surgical writers preserve unknown content, comments, whitespace, CRLF boundaries, and unrelated authored prose.
- Retain existing CLI JSON, diagnostic codes, lifecycle behavior, history, dependency, and scaffold contracts.

## More decisive automatic Manage

- Under `manage.activation: auto`, classify each selected ready continuation as either fully one-step direct work or managed non-small work; no ambiguous middle case falls back to a conservative guess.
- Requalify later implementation when an earlier report, design, tiny, or small route expands into cross-module work, real-host verification, review convergence, lifecycle delivery, or a ready successor.
- Delegate at least one implementation worker for qualified work when workers are available, while the controller retains ownership, integration verification, review convergence, lifecycle, and Git decisions.
- Keep overlapping paths, generated state, provider sessions, real hosts, hardware, and dependent verification sequential. Parallel dispatch requires isolated mutation paths and verification resources.
- Report whether Manage was selected or declined, the decisive reason, and the applicable sequential or parallel boundary without persisting controller state.

## Upgrade and opt-in usage

Pin the exact prerelease identity, then refresh both RSP-managed files and package-owned Skills:

```bash
npx -y @oevery/rsp@3.1.0-beta.4 update
npx -y @oevery/rsp@3.1.0-beta.4 skills install --dry-run
npx -y @oevery/rsp@3.1.0-beta.4 skills install
npx -y @oevery/rsp@3.1.0-beta.4 doctor
```

Users upgrading directly from a registry-installed 2.x release must first follow the [RSP 3.0 migration guide](https://github.com/oevery/rsp/blob/v3.0.0/docs/migrations/3.0.md). Language, Unicode WorkRef, and automatic Manage details are in the [3.1 migration guide](../migrations/3.1.md).

## Compatibility and known limitations

- This prerelease remains opt-in; publishing it under the npm `beta` dist-tag does not promote npm `latest`.
- No persisted Markdown format or CLI JSON schema migration is required for the semantic document model.
- The exact candidate is covered by the complete self-host release gate and clean-install package check. Automatic Manage has been dogfooded in the RSP checkout, but broader independent-project routing frequency, comparative token cost, and productivity remain unverified.
- Push, tag, GitHub Release creation, npm publication, deployment, approval, and human acceptance remain separate external actions.
