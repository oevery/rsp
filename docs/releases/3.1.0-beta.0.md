# RSP 3.1.0-beta.0

RSP 3.1 beta adds a read-only terminal workspace, bounded archive inspection, compact machine output, exact-package Skill installation, and an explicit managed-continuation Skill. It is intended for opt-in evaluation before real-project dogfooding and stable promotion.

The product is now presented as Reliable Software Practice. `Rules, Specs, Plans` remains its lightweight repository-native artifact foundation rather than the complete product identity.

## Highlights

- Use bare interactive `rsp` or `rsp ui` for a read-only Changes, Groups, and History dashboard. Non-interactive invocations remain deterministic and do not load the TUI stack.
- Query bounded authoritative archive history with `rsp history`, including exact filters and structured detail, or request one-line JSON from every inspection command with `--json --compact`.
- Read the same derived dependency facts as a human dependency forest or through `status --json` under `plan.nodes`, `plan.ready`, `plan.edges`, `plan.blocked`, and `plan.waves`.
- Treat deterministic readiness, semantic durable review, archive guidance, and Git delivery as separate authority layers. Core or a human owns the archive recommendation; archive does not grant commit, push, or publication authority.
- Explicitly invoke `rsp-manage` when a focused ready Change has genuinely independent slices, long continuation, or interruption recovery. Small or coupled work stays on the direct Core or Discipline path.
- Install the exact package's ten-Skill suite into a project with `rsp skills install`; use `--dry-run` to preflight and `--force` only to replace divergent package-owned Skill directories.

## Workflow quality

RSP now asks for the cheapest decisive verification and retains new tests only when they protect distinct observable behavior or a real boundary. Changes and durable documents keep converged requirements, outcomes, decisive evidence, gaps, and real blockers—not temporary probes, test cycles, command transcripts, correction chronology, or generic emphasis on AI.

`Blockers` parsing also ignores complete Markdown HTML comments, so template guidance cannot create a false external blocker or prerequisite edge. Incomplete comments remain visible and fail closed.

## Breaking changes and migration

RSP 3.1 requires Node.js 22 or newer. Users upgrading from RSP 3.0 must update Node before installing this prerelease; the RSP artifact model otherwise remains compatible.

Users upgrading directly from a registry-installed 2.x release must first follow the [RSP 3.0 migration guide](https://github.com/oevery/rsp/blob/v3.0.0/docs/migrations/3.0.md), including `rsp update`, residual `.rsp/rules/` review, shallow work-path migration, and `rsp doctor`.

After this beta is published, an exact-version opt-in flow will be:

```bash
npx -y @oevery/rsp@3.1.0-beta.0 init
npx -y @oevery/rsp@3.1.0-beta.0 skills install --dry-run
npx -y @oevery/rsp@3.1.0-beta.0 skills install
```

The exact version is deliberate: prerelease dogfooding must not depend on a floating tag.

## Managed continuation boundaries

`rsp-manage` is explicit-only. It snapshots stable authority once, sends compact internal envelopes only to actual workers, uses the cheapest decisive slice checks, and broadens verification only for integration risk. Dispatch, retry, budget, and process chronology are transient; RSP Changes and Specs remain the durable truth.

The Skill does not grant mutation, archive, Git, publication, deployment, environment, or human-acceptance authority. Host availability and model behavior can affect parallel execution, and prior synthetic evaluation showed orchestration overhead; this beta does not claim a cost or productivity advantage until real-project evidence exists.

## Package and verification status

- The package contains the CLI, fallback protocol, and ten Skills: the nine 3.0 capabilities plus `rsp-manage`.
- Local release preparation covers the exact `@oevery/rsp@3.1.0-beta.0` tarball, clean installation, Skill inventory, CLI help/init, `rsp skills install`, and npm-exec invocation without registry mutation.
- npm authentication, registry publication, registry-resolved `npx`, the `beta` dist-tag, boats-cloud integration, and eventual `latest` promotion are not verified by local preparation. Local preparation does not change npm `latest`.
- Publication, dist-tag changes, Git tags, pushes, and GitHub Releases require separate authority. Until publication occurs, the exact registry commands above are instructions for the future published artifact, not completed acceptance evidence.
