# RSP 3.1.0-beta.1

RSP 3.1.0-beta.1 tightens the release workflow exposed by the first 3.1 beta. It separates behavioral qualification from mutable release identity, keeps version selection late, and makes implementation delivery and release finalization independently reviewable.

The product capabilities introduced in 3.1.0-beta.0 remain unchanged: the read-only terminal dashboard, bounded archive inspection, compact JSON output, exact-package Skill installation, and explicit managed continuation are still the 3.1 beta surface.

## Release workflow integrity

- Reuse retained real-host evidence when only the package version changes, while continuing to reject Skill, Skill tree, inventory, behavior-file, input, score, or evidence-integrity drift.
- Classify package-bound documentation as publication-invariant and keep pending publication, authentication state, OTPs, and browser-authentication URLs out of durable release surfaces and retained summaries.
- Leave manifests, target changelog headings, exact-version commands, versioned release notes, and tag comparisons unchanged until the user or authoritative repository configuration confirms the release identity.
- Complete and, when authorized, commit each implementation Change independently before a dedicated Release Change and release commit finalize versioned shipped surfaces.
- Reject mismatched identities, `Unreleased` target headings, comparisons against `HEAD`, and known preparation-state markers before packaging.

## Opt-in usage

Pin the exact prerelease identity rather than relying on a moving dist-tag:

```bash
npx -y @oevery/rsp@3.1.0-beta.1 init
npx -y @oevery/rsp@3.1.0-beta.1 skills install --dry-run
npx -y @oevery/rsp@3.1.0-beta.1 skills install
```

RSP 3.1 requires Node.js 22 or newer. Users upgrading directly from a registry-installed 2.x release must first follow the [RSP 3.0 migration guide](https://github.com/oevery/rsp/blob/v3.0.0/docs/migrations/3.0.md).

## Compatibility and known limitations

- This prerelease remains opt-in; publishing it under the npm `beta` dist-tag does not promote npm `latest`.
- Real-project acceptance in boats-cloud remains unverified.
- Tagging, GitHub Release creation, npm publication, and external verification require separate authority and are not implied by this candidate.
