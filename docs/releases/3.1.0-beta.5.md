# RSP 3.1.0-beta.5

RSP 3.1.0-beta.5 makes issue-originated work traceable without provider lock-in, completes the missing recovery path for archived Change Groups, and gives managed interruption a safer, explicit continuation contract.

## Issue traceability without remote coupling

- Attach one external issue when creating a Change with `--issue`, defaulting to a non-closing `relates` relationship or accepting explicit `--issue-relation closes` intent.
- Validate optional issue frontmatter before mutation, rejecting credential-bearing URLs, fragments, duplicates, unsafe schemes, unsupported shapes, and unknown relationships.
- Project normalized relationships through plain and JSON status, show, and history surfaces while keeping existing Changes and legacy archives readable.
- Let Shape retrieve real issue content through available host capabilities or degrade honestly to authentication, pasted source data, or a link-only draft. The CLI itself performs no provider request and stores no retrieved issue body.
- Let terminal commit preparation use closing syntax only for an owned completed Change with explicit `closes` intent and safely resolved provider identity; checkpoints and ambiguous ownership remain non-closing.

## Explicit recovery for archived Groups

- Add `rsp group reopen <group> --reason <text> [--from <archive-path>]` for one exact archived Group Brief.
- Preserve the selected archive unchanged, restore the same logical Group identity, and bind new incomplete completion evidence to that retained Brief.
- Validate archive identity, ambiguity, collisions, canonical structure, empty work/focus subtrees, evidence replay, and target safety before mutation, with rollback on failure.
- Keep recovery deliberately two-step: Group reopen restores only the Brief; `rsp reopen <group>/<child>` separately restores and focuses the affected child. Other children and dependents remain untouched.

## Recoverable managed interruption

- Treat a progress question as a status update that continues an otherwise authorized run instead of a terminal stop.
- Distinguish explicit pause, explicit owner release, environmental or verification blockers, and resume without adding persisted controller state.
- Preserve the focused WorkRef by default across pause and blockers, and return the ordered continuation fields needed to recover incomplete work.
- Re-read repository authority and selected artifacts, inspect drift, requalify Manage, and refresh stale evidence before resumed mutation.

## Smaller runtime context and stronger release checks

- Move inactive managed, release, and reopen procedures behind their single conditional owners while retaining eager routing, authority, safety, fallback, and return contracts.
- Reduce representative loaded-path and provider input usage without introducing a glossary, private notation, or cross-Skill runtime dependency; fixed adjudicated behavior cases remained equivalent.
- Restore typecheck as a passing release gate and keep bounded test concurrency so full-suite and clean-install verification remain repeatable.

## Upgrade and opt-in usage

Pin the exact prerelease identity, then refresh both RSP-managed files and package-owned Skills:

```bash
npx -y @oevery/rsp@3.1.0-beta.5 update
npx -y @oevery/rsp@3.1.0-beta.5 skills install --dry-run
npx -y @oevery/rsp@3.1.0-beta.5 skills install
npx -y @oevery/rsp@3.1.0-beta.5 doctor
```

Users upgrading directly from a registry-installed 2.x release must first follow the [RSP 3.0 migration guide](https://github.com/oevery/rsp/blob/v3.0.0/docs/migrations/3.0.md). Issue relationships, Group recovery, and managed interruption details are in the [3.1 migration guide](../migrations/3.1.md).

## Compatibility and known limitations

- This prerelease remains opt-in; publishing it under the npm `beta` dist-tag does not promote npm `latest`.
- Existing Changes and archives without issue metadata remain compatible. No provider credentials, fetched issue content, or remote issue lifecycle state are persisted.
- Group recovery preserves immutable archives and requires an explicit Group-then-child sequence; it does not infer which child acceptance is incomplete.
- The exact candidate is covered by the complete self-host release gate, clean-install package check, deterministic recovery contracts, and retained fixed-case provider evaluation. Live host scheduling across a real multi-turn status or pause interaction, stochastic provider behavior, and broader productivity claims remain unverified.
- Push, tag, GitHub Release creation, npm publication, deployment, approval, and human acceptance remain separate external actions.
