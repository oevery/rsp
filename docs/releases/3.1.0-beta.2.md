# RSP 3.1.0-beta.2

RSP 3.1.0-beta.2 turns the initial managed-continuation prototype into a policy-controlled project workflow, broadens the composable Skill suite, and makes release and local Git boundaries more explicit. It is intended for opt-in evaluation of longer, multi-owner engineering work without granting remote delivery or publication authority.

## Managed execution policy

- Configure `manage.activation` as `explicit` or `auto` and choose `manage.closeout` from `manual`, `lifecycle`, or `local`. Invalid configuration fails closed, and both plain and JSON status output expose the effective policy.
- New `rsp init` projects start with automatic Manage selection and lifecycle-only closeout. Existing projects without a `manage` block preserve the compatible explicit-selection and eligible-local-closeout behavior.
- Execute ready children of a shallow Change Group in dependency waves, recover long-running goals through compact continuations, and converge bounded in-scope review corrections while keeping unrelated work untouched.
- Treat automatic routing as controller selection only. Planning, product mutation, archive, commit, push, publication, deployment, approval, and human acceptance remain independently authorized.

## Skill discovery and composition

- Use bare `rsp skills` in a dual TTY to inspect the packaged inventory and confirm one atomic project installation. Scripts and CI can use `rsp skills list` or `rsp skills list --json` for deterministic discovery.
- Install the eleven default lifecycle Skills together, or install the optional `rsp-codebase-audit` by exact name. Existing unrelated project Skills remain untouched, and divergent package-owned targets still require `--force`.
- Use report-only Pre-Change Design when the user already owns one bounded design question but no Change exists. Broader or ambiguous work still returns to Shape.
- Use the optional codebase-audit capability to report evidenced ownership, dependency, production-path, change-amplification, or verification risks before selecting implementation work.
- Use `rsp-commit` only after Core or qualified Manage has derived one exact local commit boundary with explicit authority and fresh verification. It never grants push, tag, publication, amend, rebase, or history-rewrite authority.

## Release and project integrity

- Reject a release candidate when its manifest reuses a version tag finalized at another commit, and run the complete metadata, build, typecheck, lint, test, and clean-install package gates from `prepublishOnly`.
- Keep release identity selection explicit, implementation Changes independently reviewable, and versioned shipped surfaces in a separate release boundary.
- Organize the self-hosted project model into focused domain Specs and load detailed Core procedures only when their route is active, reducing routine instruction weight without weakening fallback behavior.

## Opt-in usage

Pin the exact prerelease identity rather than relying on a moving dist-tag:

```bash
npx -y @oevery/rsp@3.1.0-beta.2 init
npx -y @oevery/rsp@3.1.0-beta.2 skills list
npx -y @oevery/rsp@3.1.0-beta.2 skills install --dry-run
```

RSP 3.1 requires Node.js 22 or newer. Users upgrading directly from a registry-installed 2.x release must first follow the [RSP 3.0 migration guide](https://github.com/oevery/rsp/blob/v3.0.0/docs/migrations/3.0.md).

## Compatibility and known limitations

- This prerelease remains opt-in; publishing it under the npm `beta` dist-tag does not promote npm `latest`.
- The exact candidate is covered by the self-host release gate. From boats-cloud, the packaged CLI started successfully, reported that the repository is not RSP-initialized, listed the exact Skill inventory, and completed installation preflight without mutation. Real-project RSP lifecycle mutation, human acceptance, and comparative productivity remain unverified.
- Commit, push, tag, GitHub Release creation, npm publication, deployment, and external post-publication verification require separate authority and are not implied by this candidate.
