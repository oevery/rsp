# RSP Shape

Do not implement the shaped work.

Follow Core's response-versus-artifact language boundary.

## Establish the boundary

Read the request, authority, Core or fallback, Change and Brief, then only decisive evidence.

A request to shape, create, or refine a Change grants artifact authority unless no-edit; advice does not. If creation focuses it, preserve the exact prior focus and restore it immediately unless selection was requested. Shaping grants no other authority to focus, implement, archive, edit durable truth, or mutate Git; preserve unrelated work.

Return the request directly to implementation when it is tiny and concrete or the selected Change is already ready. Do not rewrite settled work for style or completeness.

## Resolve material ambiguity

Inspect the repository before asking. Ask only for an owner decision whose answer can change behavior, data, interfaces, compatibility, safety, ownership, migration, or acceptance. Ask the smallest useful question set and write only authorized answers into the Change.

Read [deep clarification](references/deep-clarification.md) when the user explicitly asks for rigorous challenge, a high-risk dependent decision remains, or one bounded design question returns to Shape. Prefer the installed `rsp-design` capability; otherwise use its compact fallback against the same WorkRef.

Never invent a product decision. When a material choice or mutation authority remains unresolved, leave the work open and report the single highest-impact blocker.

## Choose the owner

Read [complex shaping](references/complex-shaping.md) before choosing the owner when material clarification needs more than one round, several direct slices share one completion contract, or independently closable owners converge on terminal delivery.

Prefer one ordinary Change only for one observable outcome sharing a consistency, focused-verification, review, archive, and rollback boundary. Use a shallow Group when at least two outcomes have independent boundaries under one goal or completion contract; an integration gate never merges them. A shared completion contract gates Group closure, not child archive unless declared there. Keep Brief `Slices`, child `Blockers`, and derived readiness. Do not create another hierarchy or tracker.

Follow the core RSP protocol for exact Change and Group structure. Keep one observable outcome per Change:

- `Proposal`: outcome, scope, and non-goals;
- `Spec`: observable requirements and acceptance scenarios;
- `Design`: affected boundaries, constraints, and settled choices;
- `Tasks`: executable implementation steps;
- `Verify`: final decisive evidence proving the outcome;
- `Blockers`: exact dependencies and unresolved external decisions, or `none`.

Plan a new test only when it protects observable behavior or a real boundary, adds distinct future confidence, avoids duplicate or implementation-detail coverage, and costs proportionately. Otherwise prefer smallest sufficient evidence and keep probes temporary.

A Change is a convergent current-plan/final-evidence snapshot, not an append-only execution log. Replace superseded evidence; keep process evidence in the response. Before archive, compress it to outcome, design, tasks, decisive verification, gaps, and risks.

Use domain language. Mention AI or agents only as real product actors, consumers, interfaces, or constraints—not authors or execution narrators.

## Apply the Shape Ready gate

A Change is ready only when:

- outcome, non-goals, and acceptance are concrete;
- product and mutation authority are settled;
- affected boundaries and material constraints are known;
- no hidden assumption can change implementation or acceptance;
- Tasks are executable without performing them;
- Verify proves the result without process chronology; Blockers are truthful;
- one Change or a justified shallow Group is the smallest sufficient owner.

After authorized mutation, run the project focused RSP check when available. Return WorkRef, changed artifacts, validation, and the next implementation action or blocker.
