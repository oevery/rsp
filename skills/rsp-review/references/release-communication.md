# Release communication checks

Load only when the fixed Document review scope includes release communication. Apply these checks alongside Document review; this method needs no installed Doc Skill and adds no writing, publication or approval authority.

## Fix evidence and intended state

Establish the released unit, range, requested surfaces and draft, final or published state from the request and authoritative project release conventions. A claimed version needs explicit user or repository release authority; do not infer it from commit ordering or a plausible next version.

Read only the direct behavior, net diff, accepted fragments and verification needed to judge the fixed claims. Generated inventories and commit summaries are leads, not delivered behavior. Missing decisive range or behavior evidence blocks dependent judgments; unknown product or operational choices follow Document review's ambiguity rule. Do not broaden the reviewed set into a repository-wide release audit.

## Check the communication

- **Net outcome:** claims describe delivered final behavior, not reverted additions, implementation chronology or rejected session-only proposals. Material public, compatibility, packaging, security and operator effects are neither invented nor omitted.
- **User action:** affected users can identify breaking changes, deprecations, old/new behavior, ordered migration steps, applicable compatibility windows, success checks and known recovery paths. Required safe commands, API forms and versions remain exact; a file link cannot replace a required action or consequence.
- **Consistency:** selected surfaces agree with authoritative versions, dates, supported environments and references. Changelogs, notes and migration guides serve their distinct audiences rather than duplicating one transcript. Public links are stable and do not expose private identifiers.
- **Evidence limits:** historical checks identify their revision or date; unavailable platform or live-release verification is not described as completed. Document correctness proves neither package verification nor release readiness.
- **Lifetime and authority:** drafts disclose unresolved identity without inventing versioned claims. Final shipped prose remains publication-invariant and uses target tags or immutable comparisons, not moving HEAD. Credentials and transient authentication/publication progress stay out of retained artifacts. A document task never grants commit, tag, push, publish or immutable-history repair.

For an explicitly scoped post-publication comparison, inspect observed public state against the selected immutable candidate. Report mutable-document corrections or an immutable discrepancy's corrective owner; never edit, move a tag or rewrite a package. An unknown external state remains unverified.

Apply project-required release checks and closeout conditions only when they govern this judgment. Do not impose a universal Release Change, separate release commit, archive requirement or publication checklist. Return findings, coverage and limitations in Review's existing report; a clean Document result is not release approval.
