# Skill authoring

Use for creating or revising a Skill. Apply Doc's language, expression and authority rules; this branch adds package-specific decisions.

## Establish the package

- For creation, resolve the goal, inputs and observable result before choosing structure.
- Honor an explicit destination; otherwise use project instructions and host constraints. Check for existing content before creating files.
- For revision, inspect the authored package and its callers. Name the failure or missing capability; preserve unrelated adaptations.
- Start with SKILL.md. Use a host initializer when useful; add resources only for a real task need.
- Preserve existing packages and global configuration. Creation is not installation or publication.

## Make discovery precise

- Describe the capability and triggering intents that distinguish it from neighboring Skills. Put detailed procedures in the body, not discovery metadata; avoid promises beyond the actual capability.
- Remove exhaustive synonyms. Add an exclusion only for a likely adjacent misroute.
- For creation or trigger changes, select useful probes by risk: direct requests, paraphrases or nearby non-triggers. Resource-only edits do not automatically need selection probes.
- Preserve invocation policy. Optional distribution does not mean explicit-only invocation; change policy only with user intent and verified host support.

## Make execution concise

- State the task-specific action, prerequisites and recognizable result. Fix order only for correctness, safety or contract dependencies; leave other implementation choices to the Agent and put peer conditions in bullets.
- Keep trigger, inputs, authority, failure, completion and output boundaries explicit. Continue ordinary authorized checks; stop for material scope or permission decisions.
- Keep shared guidance and necessary local safety context visible. Link substantial branch-only knowledge with its reading condition and purpose; a short Skill needs no router or extra files. Split or merge resources to improve the reading path, not to meet length or file-count targets.
- Retain generic teaching or old model-compensation instructions only for a current task-specific need. A newer model label alone proves neither redundancy nor safe removal of a constraint.
- Reuse tools for deterministic work; the Skill owns method selection and interpretation within its authority. Preserve named mandatory commands, provenance, independence and protected operations when replacing a tool-only method. Add a script only when repetition or fragility warrants it, and run changed helpers safely. Check incoming links before moving resources.

## Check the changed risk

1. Validate supported metadata, names, local links and package contents using existing tools. Do not import another host's schema.
2. Check instruction behavior and explanation together, including triggers, safeguards, completion and conditional resources. Use realistic task outcomes and a relevant restraint case for changed behavior. Judge artifacts and side effects, not exact wording or reading commands; formal Review selects applicable Code/Document perspectives within its own fixed scope.
3. Report structural checks separately from model execution. Explicit invocation does not prove discovery; self-checks do not prove independent review.

Use isolated inputs for write tests. Paid model calls, external effects and extra workers require actual authorization.

For an optimization claim, compare success and corrections alongside available token, call and time costs under comparable inputs. Otherwise leave the effect unverified.
